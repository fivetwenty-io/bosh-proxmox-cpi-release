# Provisioning the storage allocation journal

Set-based allocation needs a private directory on durable storage and an enrolled namespace. Set `pve.storage_allocation_journal_dir` to the directory's absolute path and `pve.storage_placement_namespace` to a stable name. The CPI never chooses a temporary fallback or moves a journal when the path changes.

On the Director, the `pve_cpi` job's pre-start runs the local provisioning command for the `vcap` execution user. For example, `/var/vcap/store/pve_cpi/allocations` keeps the journal on the Director's persistent disk. The command creates missing directories with mode `0700`. An existing journal directory must already belong to `vcap` and its primary group, with mode `0700`. The command rejects symlinks and unsafe paths without changing their permissions or ownership.

If Director workers run under BPM, expose that same directory through `director.cpi_additional_volumes` with `writable: true` and `mount_only: true`. The [Director worker template](https://github.com/cloudfoundry/bosh/blob/main/jobs/director/templates/bpm.yml) adds these volumes to the worker's filesystem. BPM otherwise gives each job its own persistent directory, as described in the [BPM runtime documentation](https://bosh.io/docs/bpm/runtime/).

For `bosh create-env`, choose a durable host directory outside `~/.bosh/installations`, the rendered CPI job, and temporary directories. Run the following command as the same user that runs `bosh create-env`, using the CPI binary built for that host.

```sh
/path/to/cpi provision-journal --directory /absolute/durable/path/allocations
```

Set the create-env CPI's `storage_allocation_journal_dir` to that exact path. The host journal and the Director journal have separate paths and lifetimes. Keep the host journal through subsequent create-env updates and teardown, and include both journals in the corresponding backup and recovery procedures. Do not reuse an old namespace after losing or restoring its journal without completing the historical allocation audit.

To provision from a rendered CPI configuration, use the following command.

```sh
/path/to/cpi provision-journal --config /path/to/cpi.json
```

Provisioning makes no PVE requests and does not enroll a namespace or claim cluster authority. [Enrollment](storage-journal-operations.md) requires an explicit historical audit, previous-writer fencing, and confirmation that previous remote tasks have settled. The normal CPI wrapper does not provision a journal.

Once `pve.storage_allocation_journal_dir` or `pve.storage_placement_namespace` is set, the CPI treats the journal as in use. Before `create_vm` and `delete_vm` touch a VM, they read the journal, even for a VM the journal never recorded, and they never fall back to the legacy paths. A journal is usable only when both properties are set and the namespace is enrolled. Until then, `create_vm` and `delete_vm` refuse with an error that names the missing property, the missing directory, or the namespace that is not enrolled. They refuse even though this namespace has no records yet, because the directory may hold another namespace's records, for example after the namespace was changed, and the legacy paths would orphan those VMs or allocate their resources a second time. When the directory holds other enrolled namespaces, the error says how many, and if this namespace replaced one of them, set it back rather than enroll a new one. Calls that only look up an existing CID, such as `has_vm`, still answer while the namespace is missing or not enrolled, because this namespace has no records for them to read. `has_disk` answers the same way for a disk the journal never allocated, and a disk that carries the journal's allocation marker gets the same setup error as `create_vm`. A directory that was never provisioned and a directory that BPM workers were never given look the same from inside the CPI, so that error names both causes, and the remedy for the second is the `director.cpi_additional_volumes` entry described above. When the Director reads only the generic evidence line for a failed `delete_vm`, the CPI logs the cause behind it at Warn.

The job refuses to render, and the CPI refuses to load, a namespace without a journal directory, because the directory is process-level and no cpi-config entry can supply it. The reverse is allowed. A journal directory without a namespace renders and loads, because a cpi-config entry can supply `pve_storage_placement_namespace` for its own cluster while the installed job supplies only the directory, as [Multi-Cluster](multi-cluster.md#storage-set-authorities-across-clusters) describes. An entry that adds a namespace to a job with no journal directory still applies. Its `create_vm`, `delete_vm`, and journal-managed disk calls refuse with an error that names the entry's namespace and the missing directory, while its other calls, such as `has_vm`, `set_vm_metadata`, and `create_stemcell`, still answer.

Enroll the namespace before any deploy creates or deletes a VM, using the steps in [Enroll a new namespace](storage-journal-operations.md#enroll-a-new-namespace). The `cpi storage-journal` commands read only the job-level values in the file you pass with `--config`, and never a cpi-config entry. To enroll a namespace that a cpi-config entry supplies, copy the rendered `cpi.json` and change its namespace, host, port, credentials, and any other `pve` properties the entry overrides to the entry's values, keeping the job's journal directory. The copy holds credentials, so make it readable only by `vcap`, run the commands with `--config` pointing at it, and delete it afterwards.

## The endpoint cache beside the journal

The same command also provisions an `endpoint-cache` directory beside the journal directory, never inside it, with the same owner and mode. For a journal at `/var/vcap/store/pve_cpi/allocations`, the cache directory is `/var/vcap/store/pve_cpi/endpoint-cache`. The CPI creates this directory at run time only when it is missing, the process runs as the journal directory's owner, and the journal's parent directory belongs to that user, grants no write access to a group or others, and sits on the same mount as the journal directory. A command run as root therefore never creates it. It refuses a directory that is not owned by the user that runs the CPI, has any group or other bits, or is a symlink. If provisioning cannot create or accept the directory, it prints one warning on standard error and still succeeds, so the Director starts. A missing directory that the CPI does not create sends it to a cache in its temporary directory. A directory the CPI refuses stops the search, so the CPI runs without a cache and discovery is off for that call. When the workers run under BPM, list the journal's parent directory in `director.cpi_additional_volumes` with `writable: true` and `mount_only: true` so that they see both directories. [Endpoint Failover and Discovery](endpoint-failover.md#beside-the-journal) explains how the CPI chooses the cache directory.
