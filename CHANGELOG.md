# Changelog

All notable changes to this project are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Entries describe operator-visible change: CPI behavior, properties, packaging, and the
documentation set. Refactors, test work, and CI plumbing appear only when they change
what an operator sees or how a release is produced. The `Unreleased` section collects
work as it lands; cutting a release renames it to the new version and dates it. See
[CONTRIBUTING](CONTRIBUTING.md#releasing-maintainers) for the release procedure.

## [Unreleased]

### Added

- `storage-journal audit` and `storage-journal audit-enrollment` take a new `--summary` flag, which prints the audit as plain text for a Director that has no `jq`. For `audit`, the first line gives `complete`, `vm_scan_complete`, `generation_index_healthy`, `cluster_continuity`, and the record count. Each finding then gets a line of its own, prefixed `conflict:`, `vm-scan issue:`, `issue:`, or `observed move:`, and the charging summary and any skipped disabled storages come last. `audit-enrollment` opens with its own line, which gives `complete`, `vm_scan_complete`, and the evidence count, and it prints no charging line. After its findings it prints one `provenance:` line per existing provenance entry. The exit code matches the JSON mode exactly, and every other action rejects the flag with exit code 2 and the usage line. See [Inspect retained allocations](docs/storage-journal-operations.md#inspect-retained-allocations).

- `storage-journal audit --summary` now prints one `record:` line for each record that needs an operator, which is any record outside `ready_to_return`, `adopted`, `cleaned`, and `deleted`, and any record that is charging. The line gives the ID, kind, state, whether it charges, the full CID or `none`, and the record's reason, and one `evidence:` line under it names each volume, node, and holder VMID that still carries the allocation. Healthy records are left out, and the records are in ID order. Before this, an operator who needed a record's CID for `adopt` had to read the one-line JSON on a Director that has no `jq`. See [Inspect retained allocations](docs/storage-journal-operations.md#inspect-retained-allocations).

- The audit report gains `vm_scan_issues`, which repeats the issues that left the VM scan incomplete. Those are the issues that block `create_vm`, so an operator no longer has to work out which of the `issues` entries is responsible. Like `issues` and `conflicts`, the field is always present.

- The audit report gains `observed_moves`, which lists each VM, persistent disk, or parker that the audit found on a node other than the recorded one and accepted as a move on shared storage. Each entry carries `allocation_id`, `kind`, `vmid`, `recorded_nodes`, `observed_node`, and `volumes`. Verification evidence that an operation retains carries the same list whenever that audit saw a move, and evidence from an audit that saw none keeps its earlier shape byte for byte.

### Changed

- The allocation audit now accepts a VM, a persistent disk, or a parker that the cluster operator moved to another node, as long as everything involved sits on shared storage that the new node can see. A live migration during a rolling patch cycle used to raise a conflict, and a single conflict blocks every `create_vm` in the namespace, so one maintenance window could freeze every deploy on a Director. A VM move is accepted only when the VM scan is complete and the record is in `ready_to_return` or `adopted`, or when `delete_vm` has since taken the record out of those states and its delete admission accepted the same move of the same VMID to the same node. The VMID must belong to the active attempt, the allocation marker must have been sighted exactly once with a matching agent digest, and every configuration volume must belong to this allocation or to a disk whose provenance the VM carries. Every volume the VM holds must sit on shared storage too, and that includes a hibernation `vmstate`, every snapshot's volumes, and every volume the active attempt recorded. Each such storage must have been shared when the plan was frozen and must keep the backing that plan froze, it must be available on the new node, and that node's listing in the same audit must show the volume. A moved disk or parker must be in its holder's configuration and meet the same storage conditions. Anything that touches node-local storage stays a conflict, and the conflict now ends with the reason the move was refused. The audit decides each move afresh on every call and never records a step for it in the journal. Resume, adoption, `delete_vm`, `detach_disk`, and every call that uses a persistent disk's parker follow the same decision, and `detach_disk` rewrites a moved disk's provenance to name its current node before the disk moves to its parker. A `delete_vm` that is still running, or that failed partway and is retried, keeps following the move, so another deployment's `create_vm` is not refused in the meantime. When a crash leaves a delete step unsettled, `storage-journal cleanup` follows the move, while a plain `delete_vm` retry refuses for a moved VM just as it does for one that never moved. The retention parker that `delete_vm` creates for retained ephemeral disks stays strict, because its entry carries no allocation ID for the audit to decide on, so its cleanup still needs the parker on its recorded node. See [An operation fails with an allocation audit refusal](docs/troubleshooting.md#an-operation-fails-with-an-allocation-audit-refusal).

- A Director can roll back from this release to 0.8.0 safely. The only new thing this release writes into the journal is the `observed_moves` list inside verification evidence that it already retains, and 0.8.0 ignores that list. A 0.8.0 CPI simply raises the old conflicts for moved VMs again and refuses `create_vm` until they go back to their recorded nodes. If we roll back to 0.8.0 while a VM holds a disk under a name that a parked disk once carried, 0.8.0 brings back the false holder conflict for the parked disk, and it refuses `create_disk` and `create_vm` for as long as that reused name exists. Rolling back below 0.8.0 stays barred for as long as grouped allocation records are non-terminal, as the 0.8.0 entry describes.

### Fixed

- Every audit-gated refusal now says what the audit found. `create_vm` used to fail with one fixed line, "VM allocation admission requires complete VM provenance inspection and consistent retained history", and about a dozen other gates in `create_disk`, `delete_vm`, `delete_disk`, the retry paths, and cleanup had fixed lines of their own. Each one now opens with the operation, the counts, and the first finding, because `bosh tasks` keeps only about the first 75 characters of a CPI error, for example `create_vm refused: 2 audit conflicts; VM 4626 on pvupvecf102, recorded pvupvecf101 (node_mismatch)`. It lists up to three findings, says how many more there are, and ends with the exact command that prints the full report on that host. On a Director that command is `sudo -u vcap /var/vcap/packages/pve_cpi/bin/cpi storage-journal audit --summary --config /var/vcap/jobs/pve_cpi/config/cpi.json`. The CPI runs there as `vcap`, the journal's owner, but we read the refusal as another user, so a CPI running from `/var/vcap/` always adds `sudo -u` with the journal owner. Under `bosh create-env` the command carries `sudo -u` only when the journal belongs to someone other than the user the CPI runs as. The CPI also logs the full report once, as an Error record named `allocation audit gate refused`, which `bosh task <id> --cpi` shows. Each finding names its allocation, VMID, recorded and observed nodes, and volume or storage, along with a reason code such as `node_mismatch` or `backing_changed`. Where an error is involved, a finding carries only a safe description of it, such as an HTTP status with PVE's own message, never raw transport text. Director messages, CLI output, and the CPI's logs now share one set of masking rules, which covers `PVEAPIToken=` and `PVEAuthCookie=` values as well as credentials inside URLs. `create_disk` keeps its `storage allocation admission` lead, and the `pve-cid storage-plan` diagnostic now lists up to three historical conflicts and issues instead of only counting them. A `create_disk` retry used to drop the reason it refused, and it now names the failed audit, the leftover rejected volume, or its audit findings. A `detach_disk` that cannot rewrite a moved disk's provenance names the audit's reason for refusing the move.

- Two VMs that raised the same kind of conflict no longer collapse into one line. The conflict strings named nothing that told them apart, so deduplication dropped all but one, and an audit of two migrated VMs reported a single disk-provenance conflict. Every conflict now carries its own identifiers.

- `cpi storage-journal` and `cpi provision-journal` no longer swallow their errors. About twenty-five failure lines used to drop the error in hand, and five output failures exited 1 with no text at all. Each one now prints its message followed by a safe description of the cause. A journal owned by another user prints `journal <path> is owned by <user>; rerun as that user:` and the exact command, which is what plain `sudo` on a Director now reports instead of an opaque failure. A missing journal directory, a namespace that was never enrolled, and a config file that is missing or unreadable each get their own message, and a config that fails validation prints no configuration values. When a config lacks a namespace or a journal directory, the CLI says which one is missing. When `initialize`, the recovery actions, or `resolve-missing-vm` refuse, they now print one `precondition failed:` line for each precondition that failed, followed by an `audit findings:` summary. A refused `adopt`, `finalize-cleanup`, or `cleanup` now carries its reason after its class, as in `allocation decision refused (identity_or_audit_evidence: adoption requires a ready_to_return record, or a disk in reconciliation_required, with the exact CID)`. When an audit gate refused, the reason is the gate's summary. For the CPI's own refusals, such as a VM or a pending allocation found outside its recorded node, the reason is the CPI's text, and for anything else it is a safe description like an HTTP status with PVE's message.

- Explicit cleanup of a retained VM no longer fails when it finishes. The cleanup records its disk deletions with the retention parker's VMID, and the allocation audit read that parker as the VM's own guest and reported that it lacked the allocation marker. The audit now treats those steps as naming the parker, so a record that 0.8.0 left stuck this way finishes when the cleanup is retried.

- Two journal-managed operations that want the same cluster lock no longer leave the slower one's allocation needing reconciliation. When a deploy runs with `max_in_flight` above 1 and two instances move persistent disks out of the same parker at once, both requests try to create the parker's `bosh-lock-vm-<vmid>` sentinel pool, and PVE refuses the second create because the first request holds the lock. The allocation guard read that refusal as an uncertain outcome, so it marked the losing allocation `reconciliation_required`, and the deploy failed with `requires reconciliation at lifecycle attach_disk Pool.CreatePool` instead of waiting its turn. The guard now accepts PVE's exact refusal for a `bosh-lock-` sentinel as proof that nothing changed, but only after it reads the sentinel back and finds that it does not hold the request's own claim. It then settles the journal step as observed and hands the refusal back to the lock code, which waits for the holder as it always has. A release or a steal that finds the sentinel already gone is settled the same way. A release whose readback finds that a waiter has already created its own sentinel still counts as an observed delete, because the guard reads the sentinel's claim just before it deletes it and the waiter's claim differs from that one. A create that PVE accepted stays observed even when a stealer removes or replaces the sentinel before the readback. The lock code now reads its claim back after every create it makes, not only after a steal, so a create that was displaced waits for the new holder instead of entering that holder's window. Every other pool failure still requires reconciliation. The bug has been present since 0.6.0.

- The CPI now recognizes the text PVE sends when a pool already exists, which is `create pool failed: pool '<id>' already exists`. The check it used before expected the text without the `create pool failed:` prefix, so it never matched a live cluster. As a result, when two `create_vm` calls created a deployment's resource pool at the same moment, the slower one's allocation ended up in `reconciliation_required`. That case now resolves as the concurrent create it is.

- A journal-managed `create_vm` that takes the anti-affinity lock no longer fails when it releases that lock. The lock is taken when `pve.placement.anti_affinity.use_ha_rules` is on and `pve.cluster_lock_mode` is `pool`. The allocation guard refused the sentinel pool's delete as an unplanned mutation, which failed the `create_vm` after the VM was built and left the sentinel behind until its TTL ran out. The guard now admits that delete for an anti-affinity sentinel, `bosh-lock-aa-<group>`, and for no other pool, including every other sentinel. When that delete or the sentinel's create loses its answer after the VM's own work has begun, `storage-journal cleanup` now settles the planned pool step that the failure leaves behind by reading each lock pool the step could have meant, including `bosh-lock-aa-<group>` when the record stored its instance group, and then closes the VM allocation the way it closes any other, while a record that stopped before any VM write keeps its attested cleanup route.

- Every journal-managed operation that takes a parker's lock now waits up to 180 seconds for another request's window, up from 15. That covers `attach_disk`, `detach_disk`, `delete_disk`, the `create_disk` park, the disk attach inside `create_vm` for a disk in `disk_cids`, the disk preservation and the ephemeral retention inside `delete_vm`, and a `storage-journal cleanup` of a disk or of a retained ephemeral volume. The 180 seconds is the lock's TTL, and a holder's window can run for most of it, so the old wait gave up on windows that were working normally. The wait is one budget for the whole queue, not a fresh allowance for each holder, so a request at the back of a long queue of instances sharing one parker can still run out. Some of these calls fail cleanly when the wait runs out before they changed the disk. That requires the lock wait to be the only failure, with every journal step observed, no disk mutation admitted before the wait, and the guard never tripped. The drive-option override note that the CPI writes onto the receiving VM before the wait does not count as a disk mutation, because the note plays no part in deciding where the disk is. `attach_disk`, `detach_disk`, `delete_disk`, the `create_vm` disk attach, and the `delete_vm` disk preservation fail cleanly in that case, both for disks the journal owns and for older stable-ID disks it does not. The call fails with a retriable error, the disk stays where it was, and the allocation is not marked for reconciliation. A wait that the request itself ends now exits the same clean way when nothing else was admitted, whether the request's deadline stops the wait with the timeout 15 seconds early or a cancellation interrupts it. The `create_disk` park and the `delete_vm` ephemeral retention still end in `reconciliation_required` after a timeout. The park has already created a volume that the next deploy's `create_disk` does not reuse, and the retention writes the volume's serial before it waits. A `storage-journal cleanup` of a disk whose wait runs out before it changed anything now leaves the record as it was and returns a retriable error, so we rerun it once the other request's window closes, and the CLI now gives `cleanup` long enough for a full 180-second wait and the window after it. A cleanup that touched the disk before its wait, or that removes a retained ephemeral volume, still ends in `reconciliation_required`. Any other failure still requires reconciliation too. A `create_vm` whose disk attach ends that way leaves its VM record with one planned persistent disk handoff step. An attested `storage-journal cleanup`, run with `--authority-id`, `--previous-writer-fenced`, and `--remote-tasks-settled`, now closes that record once the disk's own record is settled, and it parks the disk again first when the disk is still attached to the VM. The Director retries only `create_vm` within a task, so a timed-out `create_vm` is retried in the same task. Before the timeout goes back, `create_vm` disposes of the VM it built, preserving any disk it had already attached, and closes the VM's allocation, so each retry starts a new allocation and builds a fresh VM. With `pve.debug.keep_failed_vms` on, `create_vm` keeps the VM instead, and the next try resumes it. When fallback attempts are configured, `create_vm` instead disposes of the timed-out attempt's VM, preserving any disk it had already attached, and places a new one. If that disposal fails once it has begun, for example because preserving an attached disk runs out the same wait, the VM allocation requires reconciliation and the error is not retriable. By then the VM may be stopped, out of HA, or missing a disk, so resuming it as a create would not be safe. A later `create_vm` for the same agent refuses to resume it. If the disposal is refused before it begins, for example because the allocation audit is incomplete, the VM and its allocation stay as they were and the next try resumes them. When every one of the Director's tries runs out, five by default, no guest or charging record is left behind. A timed-out `attach_disk` or `detach_disk` fails the deploy task instead, and running the deploy again reissues the call against a disk that is already back in its earlier state. A deploy never deletes a persistent disk, because the Director orphans it instead, so `delete_disk` comes only from orphan cleanup, and the Director's scheduled orphan cleanup calls it again every 30 minutes. A timed-out `delete_vm` leaves its VM allocation with every step observed in the same way, and the next `delete_vm` for that VM resumes it. A `delete_vm` that nothing calls again, such as one whose error `bosh delete-deployment --force` ignored, leaves its record charging until we run `cleanup` on it. A `create_disk` whose park runs out still requires reconciliation, because it has already created a volume, and the next deploy's `create_disk` creates a new volume under a new allocation instead of reusing it. Callers outside the allocation journal keep the 15-second wait, and the lock's TTL is unchanged. See [Multi-storage allocation requires reconciliation](docs/troubleshooting.md#multi-storage-allocation-requires-reconciliation).

- Two requests that steal the same expired cluster lock no longer both end up holding it in the ordinary case. A lock is stolen when its holder crashed or overran its TTL, and every request waiting on it at that moment judges it expired, which the 180-second parker wait makes common. A stealer now reads the lock pool again immediately before its delete and gives up when the claim has changed in any way, and a journal-managed delete checks the claim once more right before it calls PVE. If a steal takes longer than two seconds from that read to the end of its delete, it gives up instead of creating the pool again, and the next poll starts over. The parker lock and the anti-affinity lock also pause for two and a half seconds after every create, a steal's or an ordinary one, and confirm their claim a second time before they take the lock, so each of those acquires is about two and a half seconds slower. PVE has no conditional delete, so one window remains for those two locks, and two holders can overlap only when a stealer stalls between its last read and its delete for longer than that pause. The per-VMID lock that `set_vm_metadata`, `set_disk_metadata`, `delete_vm`, and stemcell reference counting take skips the pause, because a double holder there races two metadata writes, where the last one wins, or two picks of the same VMID, which PVE refuses. For that lock we accept that a stealer's late delete can still let two holders overlap. When a request releases a lock, it now leaves the lock pool alone if its claim is within a few seconds of expiring, or if the pool's comment names no owner or no expiry, and a later request takes the pool over once the claim lapses. We now measure a parker window's deadline from the claim's recorded expiry, and the window leaves 35 seconds instead of 30 for putting the parker's protection back, which covers the restore's full retry curve.

- A cluster lock acquire whose read of its own new lock pool fails no longer leaves that pool standing for a whole TTL, and a parker window no longer runs unserialized after such a failure. The acquire reads the pool again on the lock's poll cadence until its deadline, and it takes the lock as soon as a read shows its claim. The retries stay inside the acquire's existing wait, so no acquire takes longer than before. If no read answers by the deadline, the acquire fails with a retriable error saying the lock state is unknown. On the way out it reads the pool once more, and it deletes the pool only when that read proves the pool still carries its own claim, well short of that claim's expiry. The delete expects the comment that read returned, so a journal-managed delete checks the claim right before it calls PVE. A parker window treats the unknown state the way it treats a timeout, so the call fails instead of running the window.

- A journal-managed disk operation whose parker lock ends in that unknown lock state now settles its allocation the way a clean lock timeout does. That covers `attach_disk`, `detach_disk`, `delete_disk`, the `create_vm` disk attach, and the `delete_vm` disk preservation, under the same conditions a timeout needs. When the read on the acquire's way out proves the lock pool ours and PVE answers the delete, every step is observed, so the allocation goes back to `ready_to_return` and the Director gets a retriable error. When that delete does not answer, its step stays planned and the allocation is left in `reconciliation_required`. The next `attach_disk`, `detach_disk`, or `delete_disk` for the disk, such as the one a rerun deploy makes, reads the lock pool back, settles that planned delete step, and is admitted. Our old claim still stands until its TTL passes, so that call can wait on it and time out cleanly before a later one completes. The `create_vm` disk attach ends the way a timed-out one does, so `create_vm` disposes of the VM it built before it returns the retriable error, and with `pve.debug.keep_failed_vms` on it keeps the VM instead.

- A journal-managed request whose allocation needs reconciliation no longer leaves its parker lock standing for everyone else. Once a write inside a parker window fails in a way the CPI cannot account for, the allocation guard refuses every further write, and that used to include the release of the request's own lock pool, so every other request on that parker waited out the full 180-second TTL. The release now goes through when the guard's read right before the delete finds exactly the claim this request created, and any other claim, or a read that fails, still leaves the pool alone. A request whose lock create the guard refuses before it reaches PVE, because its allocation already needs reconciliation or the request has ended, now fails at that point instead of running the parker window without the lock.

- Every cluster lock owner now names the host, the CPI process ID, a random number drawn once per process, and a per-process sequence number, as in `set_vm_metadata/4242@director-0/1234-9f2c1a7e-1`. That covers the per-VMID locks that `set_vm_metadata`, `set_disk_metadata`, `delete_vm`, and stemcell reference counting take, the parker lock, and the anti-affinity lock. The parker lock's owner used to name only the purpose, the process ID, and the parker's VMID, so two requests in one CPI process could stamp identical claims. The per-VMID locks named only the purpose and the VMID, so two requests with the same purpose for the same VMID could stamp identical claims even from different processes or different Directors.

- A record that the old lock bug left in `reconciliation_required` can now be recovered without an operator guessing at it. Such a record's last step is a planned `bosh-lock-` pool create, for example `lifecycle_attach_disk_Pool_CreatePool`, and every refusal treated that step as unsettled, so a rerun deploy, `adopt`, and `finalize-cleanup` all refused a disk that was healthy and parked. A lock pool is an empty marker that never holds anything the allocation owns, so the CPI now settles such a step with a fresh read of the lock pool named for each VM the record's steps target. When each read answers exactly, either with the pool and its claim or with PVE's own missing-pool answer, the step is marked observed in the journal, and nothing on PVE changes. A claim that the failed request left behind stays until its TTL passes and the next request takes it over. A read that fails or answers loosely leaves the step planned. The next `attach_disk` or `detach_disk` call for the disk, which a rerun deploy makes, does this before it readmits the record, and so do `delete_disk`, `adopt`, `finalize-cleanup`, and the `cleanup` precheck. Because the Director's scheduled orphan cleanup retries a failed `delete_disk` every 30 minutes, an orphan whose delete the old bug refused is now settled and deleted by that cleanup with no action from an operator. `adopt` now also accepts a disk in `reconciliation_required` that still has its CID, after it observes the disk where its record says, and its refusal now reads `adoption requires a ready_to_return record, or a disk in reconciliation_required, with the exact CID`. Every unsettled-evidence refusal now names the first unsettled step with its step name and kind instead of asking to "reconcile task completion". An `attach_disk`, `detach_disk`, or `delete_disk` refused that way now names its own operation, as in `attach_disk has unresolved mutation evidence; step attempt-0-step-4 (lifecycle_attach_disk_Nodes_UpdateQemuConfig) is planned`, where it used to say `cleanup has unresolved mutation evidence` for a call that was not a cleanup. See [Records left behind by the old lock bug](docs/troubleshooting.md#records-left-behind-by-the-old-lock-bug).

- A record that a crash left with a planned lock step is now settled by readback whatever state the crash left it in, the same way as a record in `reconciliation_required`. A crash between a step's intent and its outcome leaves the record in the state it already had, such as `planned` for a disk whose `attach_disk`, `detach_disk`, or `create_disk` park stopped right after it planned the lock step, and the journal accepted the settlement's write only on a record in `reconciliation_required`. So every journal-managed disk operation on such a record, and every `storage-journal adopt`, `finalize-cleanup`, and `cleanup` on it, failed with `allocation requires reconciliation`, even though the record was not in that state. No `storage-journal` action could move it there either. The journal now accepts a write that only marks planned steps of the active attempt observed and adds their volumes, with the record's state, reason, and verifications unchanged. Every other write from a request that reopened the record still needs the record in `reconciliation_required` or a fresh verification first. When the journal refuses a settlement anyway, the error now names each step it was settling.

- A persistent disk that has been replaced twice no longer blocks every `create_disk` and `create_vm` in the namespace. When we detach a disk and park it, PVE frees its name, such as `vm-2353-disk-1`, and gives that name to the next disk the VM receives. The allocation audit counted a volume as a holder of every record that had ever carried its name, so the parked disk's record appeared to have two holders, and admission failed with `disk allocation <id> has 2 holders`. We now decide which allocation a volume belongs to from the drive's serial first and the VM's disk provenance second, and we fall back to the record's volume names only when neither one identifies the volume. While a VM holds the reused name, the same rule keeps that name out of the evidence that absence proofs read, so deleting or cleaning up the parked disk no longer trips over a stale sighting there. A reused name that no VM holds, including one left only as an `unusedN` entry, still counts as the old record's, so those absence proofs keep refusing until the name is gone. A true duplicate is still a conflict, whether it is one serial at two holders, one allocation at two holders, or an unidentified volume at a name the record carries. The audit also raises a new conflict whenever two VMs reference the same volume at once, on shared storage or on the same node for node-local storage, because both of them can write the disk. CD-ROM entries are exempt, since many VMs mount one ISO. The bug has been present since 0.6.0.

- The per-VMID lock that `set_vm_metadata`, `set_disk_metadata`, `delete_vm`, and stemcell reference counting take now stands for 25 minutes instead of 30 seconds. `set_vm_metadata` holds that lock while it reconciles the VM's resource pool, and the reconcile retries its pool lookup, its pool create, and its move with backoff, so on a busy cluster it could still be running when the 30 seconds ran out. Another CPI process could then take the lock over while the first was still inside it, and two metadata writes to one VM could interleave. The new TTL covers the worst case, which is about 22 minutes when every retry sleeps its longest backoff and every call takes 30 seconds, and when we lengthen a backoff curve or the transient attempt budget under `pve.retry`, the lock claims a longer TTL to match. The CPI still never cuts the lock's work short, because a write stopped partway has an unknown outcome, and the retry loop around it can't tell a write that landed from one that was lost. The cost is that a CPI process that dies while it holds the lock blocks metadata writes to that VM until its claim expires. When a call gives up waiting for the lock, its error now quotes the holder's claim in full, with the owner token that names the operation, host, and process ID, and the expiry as both Unix seconds and a UTC time. [A VM's metadata lock is held by a process that died](docs/troubleshooting.md#a-vms-metadata-lock-is-held-by-a-process-that-died) explains how to read the claim and when it is safe to clear the lock by hand.

- A parker's protection restore now has a deadline. When the CPI moves a parked disk onto a VM, or deletes a disk that is named for its parker, it clears the parker's protection for the change and puts it back afterwards, even when the request was cancelled. That restore had no deadline, so a PVE that stopped answering could hold it open past the parker lock's 180-second TTL, after which another request may take the lock and open its own window on the same parker. The deadline is the time the lock already sets aside for the restore after the window's own work, so the restore now ends inside the TTL. When the deadline cuts the restore off, or the connection fails on every attempt, nobody knows whether protection is back on, so the call fails with a retriable error that names the protection restore, says whether the disk transfer or deletion itself completed, and gives the `qm config <vmid>` and `qm set <vmid> --protection 1` commands that check and fix it. When an earlier failure has already left a journal-managed operation uncertain, the restore is never sent, and the error says it was not attempted rather than blaming PVE. When the transfer completed, the CPI first records the disk on its new VM, with its provenance and CID, and removes the parker's record of it, so a rerun deploy finds the disk where the Director expects it, whether or not the disk is journal-managed. A deletion that completed has its parker record removed the same way. When the transfer or deletion failed as well, both errors are reported, and the failure's own classification decides whether the call is retriable. For a journal-managed disk, the allocation is left in `reconciliation_required` with the restore as its only unsettled step, and the next call that touches the record settles that step by reading the parker back. That call can be a rerun deploy's `attach_disk` or `delete_disk`, `storage-journal adopt`, or the `cleanup` precheck. A `create_vm` whose attach of a disk from `disk_cids` meets a cut-off restore keeps its VM, because the disk already reached it, and returns the retriable error without a rollback or another placement. The Director's retry in the same task resumes that VM, settles the restore step once the parker reads protected, and completes with the disk already in its slot. While protection is still off, the retry is refused with the `qm set` command and the VM is kept for the next try, and when every try runs out with protection still off, the VM stays for a plain `storage-journal cleanup` once protection is back. Only a `create_vm` attach that changed the disk without landing it still takes the handoff cleanup route. A parker that reads protected lets the call carry on without any write to PVE, and one that reads unprotected refuses it with the exact `qm set <parker> --protection 1` command to run before we retry. The journal records the restore's value in the kind field of the step's parameters rather than in a new parameter field, so a 0.8.0 CPI can still read the record after a rollback. A protection write that fails without an answer from PVE no longer blocks the rest of a journal-managed operation, and one that a retry then lands is settled before the operation completes. A restore that PVE answers with a failure now leaves a journal-managed disk's allocation usable, because the write provably did not apply, and it still logs a warning and nothing more, as before. See [A parker's protection restore timed out](docs/troubleshooting.md#a-parkers-protection-restore-timed-out).

- A `delete_vm` that fails partway through disposing of a journal-managed VM no longer invites a retry that can only be refused. When the failure itself was retriable, such as a destroy task that timed out, the Director read that retriable error and retried the delete, and the retry was refused because the VM's allocation already required reconciliation. For a retriable failure, the first error the Director sees now says that the allocation requires reconciliation, and it is not retriable, while the original cause still follows it in the same error. A failure that was never retriable, such as an audit refusal, keeps its own message first, so the Director still shows what the audit found. A failure with no CPI error type of its own used to show only the reconciliation notice, and it now shows its own text as a non-retriable error ahead of that notice.

## [0.8.0] - 2026-09-15

### Added

- Every set-managed create now charges what its in-flight siblings have already claimed. Placement ranks members against the capacity PVE reports, and PVE reports a volume only once that volume exists, so two creates that started seconds apart used to see the same free space and choose the same share, which is how several VMs of one instance group landed together. Each create now reads the allocation journal before it ranks and seeds the ranking with the bytes the other open allocations have claimed on each member and each capacity domain. See [Charge in-flight siblings against a placement](docs/multi-storage-placement.md#charge-in-flight-siblings-against-a-placement).

  Four record states charge their bytes, and they are `planned`, `submitted`, `observed`, and `reconciliation_required`. In those four the volume is neither absent nor yet counted in any storage status. The resting states charge nothing, because in `ready_to_return`, `adopted`, and `vm_deleted_retained` the volume exists and the capacity snapshot already carries it, while in `deleted` and `cleaned` it does not exist at all.

- The bytes one sibling charges come from two sources, and for each capacity key the CPI takes the larger of the two rather than adding them. The first source is the plan's own claim, which a record in `planned` carries before it has written any step, and the second is the sum of the record's step charges. Once a step exists, its charges restate what the plan claimed, so adding the two would double the sibling's weight. Outstanding bytes always count, and acquired bytes count only when the record was last updated less than two minutes before the capacity snapshot started, or at any time after it. That two-minute tolerance absorbs clock offset between the host that wrote the record and the host that took the snapshot.

- A `create_vm` that places for the first time now leaves no window for a peer to slip through, because the journal read, the ranking, and the record write all run inside the journal's exclusive index lock. A retry is different, since it lists the journal with no index lock held, re-plans from that listing, and then writes the new attempt under its own record lock, so it keeps a narrow window of its own. On `create_disk` the read runs before planning while the record is written after it, so a persistent set with more than one member keeps a window of the same shape in this release.

  The journal already holds the index lock for the whole of its own body on a disk create, while discovery, ranking, and the PVE calls all run outside it, so a later release can close these windows the way the first VM placement closes its own.

- Sibling bytes change feasibility under every strategy, but they change the order only under `least_utilized` and `weighted_free_space`. A `spread` set ranks by rendezvous hash and never reads free space, so it gets its spreading from anti-affinity instead.

  The `pve-cid storage-plan` diagnostic opens no journal for its ranking, so it charges no in-flight sibling. It reads no sibling record either, which leaves every sibling count empty and skips the band partition altogether, so what it explains is the strategy's own order over all the candidates. A placement it explains can therefore differ from one a live create makes while peers are in flight.

- A storage set can now declare `anti_affinity`, which asks the planner to prefer a member that does not already hold another allocation of the same instance group. `scope` takes `instance_group`, `deployment`, or `none`, and `utilization_band_pct` takes an integer from 0 to 100. The defaults are `instance_group` and 20 points, and they are read where they are used rather than written onto the set, so a set that declares nothing spreads by default while its policy fingerprint and its context-override cache key stay byte-identical to what they were before the upgrade. The opt-out for one set is `anti_affinity: {scope: none}`. Every `create_vm` plan now records the group its allocation belongs to as `deployment--<name>/instance-group--<name>`, each half sanitized to the CPI's tag alphabet. The group is empty whenever the environment names no instance group, which is the usual `bosh create-env` shape. Records written before this release carry no group, so they count for nothing and a namespace starts spreading from its first create after the upgrade. The preference is bounded by the band. Candidates whose projected utilization sits within the band of the least utilized candidate are bucketed by sibling count. Each non-empty bucket is ranked on its own with the set's strategy, and the buckets are concatenated with the fewest siblings first. Candidates outside the band are ranked once and appended after them, so a much fuller member never wins on a sibling count alone. The partition orders the root disk of a `create_vm` only, and never a dedicated ephemeral disk or a `create_disk`. The winning candidate's reason string now names the band, the bucket, and the sibling count. One consequence is worth planning for. Source choice is per target, so a partition that promotes a member holding no replica of the stemcell turns a linked clone into a full clone, with only a warning in the CPI log. That makes the replica listing a precondition of any deploy onto a share that has not hosted that stemcell before. See [Spread an instance group across members](docs/multi-storage-placement.md#spread-an-instance-group-across-members).

- `storage-journal audit` now timestamps every retained record and says whether its state charges bytes against new creates. Each record summary gained `CreatedAt` and `UpdatedAt` in RFC 3339 and a boolean named `charging`, which comes from the same predicate the planner uses, so the operator's view cannot drift from the ranking's arithmetic. The output also gained a `charging_summary` object holding the number of charging records, the identifier of the oldest one, and its age. Nothing ages a record out of an in-flight state, so a CPI that dies between writing its record and running its first step leaves a `planned` record charging its bytes against every later create until an operator resolves it. This command is what names that record. The output is JSON and the new fields are additive, so a consumer that decodes loosely keeps working while one that decodes strictly has to be updated. See [A crash-abandoned allocation keeps charging capacity](docs/troubleshooting.md#a-crash-abandoned-allocation-keeps-charging-capacity).

### Changed

- A Director must not roll back below this release while grouped allocation records are non-terminal. A plan this release writes for a `create_vm` carries the allocation's anti-affinity group whenever that group is non-empty, and a CPI decodes its own plans with unknown fields disallowed, so an older binary reading one of those plans fails it with an audit-required error rather than mis-parsing it. Every plan carrying a non-empty group is affected that way. A plan whose group is empty omits the field altogether, which is the usual `bosh create-env` shape, and an older binary decodes such a plan without trouble. Records an older binary wrote carry no group at all and are unaffected too. The same hazard does not arise again in the other direction, because each create now decodes a sibling's plan leniently and only its own plan strictly, so a field a later release adds to the plan does not break this release's creates.

- `create_disk` now opens the allocation journal before it plans, so the admission audit that authorizes the create scans every node in the cluster rather than only the nodes the discovered inventory covered. That costs one cluster-wide scan per disk create, and it strengthens the absence proof the audit rests on. The narrower node lists that decide where a disk lands are unchanged, because they follow the hinted VM's node or the availability zone's candidates, and they are the planning scope rather than the audit scope.

- The `cpi.storage.candidate_rejections` counter reads higher after this release without anything being wrong. Sibling bytes push more candidates through the capacity gate's rejection path, and that gate now records a rejection where it used to drop a member silently, so a member the ceiling excluded leaves a trace in the plan instead of dropping out of it unremarked.

## [0.7.3] - 2026-09-15

### Added

- An empty storage content listing no longer proves an absence on its own. The CPI settles whether a volume is gone by reading the storage's content listing, and on NFS and CIFS it trusts an empty listing, because PVE refuses to activate those storages when their backing is unreachable. An export that mounts but serves the wrong tree defeats that rule, because the mount succeeds and the listing comes back empty while the real content sits somewhere else. That is how a filer which lost its dataset, and now exports the empty parent directory, looks from the API. When a listing comes back empty on a storage the CPI would otherwise trust, it now asks three sources whether anything contradicts that emptiness, and it stops at the first source that answers. The cluster's VM configs come first, and a config that still references a volume on the storage is a contradiction. That check costs no extra call on `delete_disk`, `attach_disk`, and a `create_vm` carrying `disk_cids`, because those calls already read every VM config to find the disk's holder, and it has nothing to say on the callers that never run such a scan. The allocation journal comes next, and it contradicts an empty listing when the CPI recorded allocating some other volume on the storage and never recorded deleting it, because the journal still holds an open allocation record for the disk whose absence we are proving, whether that volume is gone or not, so that disk never counts against itself. That source answers on every caller without touching the cluster. Both record-based sources judge per node on node-pinned storage, because a storage name such as `local-lvm` is a different tree on every node, and on shared storage a record from any node counts. The storage's own status on the node comes last, because it is the only source that spends an API call, and it contradicts an empty listing only when the storage is not active on that node. A used figure cannot contradict a listing, since PVE reports the used bytes of the whole mounted filesystem while the listing covers only the content types the storage is configured for, so one export carrying a backup storage's `dump` directory beside an images storage would have made every honest empty listing on the images storage look contradicted. A status that reports at least 1 GiB in use with nothing listed is logged as a warning naming the storage, the node, and the byte counts, and the proof then succeeds. A wrong-tree export that no config references and no journal record names therefore still proves absent, and that warning is the trail to it. A source that fails rather than answers leaves the absence unproven, and every refusal names the source and what it saw. A storage that nothing contradicts still proves an absence exactly as before, and the rule for a plain `dir` storage with no `is_mountpoint` is unchanged. See [Absence unproven because an empty listing was contradicted](docs/troubleshooting.md#absence-unproven-because-an-empty-listing-was-contradicted).

### Fixed

- The local-backend cluster scan now classifies a storage from a live read of the PVE storage index rather than from the classification its backend was built with. That scan proves a volume absent on node-pinned storage, and how much an empty content listing proves depends on the storage's type and on its `is_mountpoint` flag, so a stale classification decided the question. One CPI process can outlive an operator's `storage.cfg` edit, because the multi-request stdin loop keeps a process alive across calls while the classification cache holds its entries for a TTL, and `pvesm set <storage> --is_mountpoint yes` now takes effect on the next call instead of waiting for that cache. The live read happens at most once per backend and only after a point probe has already failed, so a scan that never reaches a content listing never pays for it. When the index lookup misses, the CPI hands the backend a fabricated record holding nothing but the storage name. The scan used to report that as a successful classification of a storage with no type, which the proof read as an unrecognized storage rather than as one we never classified at all. It now reports no classification, which leaves the absence unproven and keeps the caller failing closed.

- `delete_disk` no longer refuses a parked-anchor disk whose volume is already gone from `dir`, NFS, or CIFS storage. PVE does not answer a missing file on those backends with a 404. It answers with an HTTP 500 that names `volume_size_info` and reports no format. That same wording also covers a denied read, a stale NFS handle, an unmounted export, and an I/O error, so the CPI could not read the reply either way, and it failed closed. The CPI now settles the question with a storage content listing rather than with the error text. A volid that is absent from a listing the CPI was allowed to read counts as proof that the volume is gone. The same proof unblocks `has_disk`, which `bosh cck` relies on to learn that a disk no longer exists. It also unblocks the stale-unused-slot check in `delete_vm` and the local-backend cluster scan that used to turn a deleted volume into a retriable error. An absence the CPI cannot prove still leaves the refusal in place, and the CPI now logs a warning that names why the proof did not land. Proving an absence needs `Sys.Audit` at `/access` on the CPI's token, because the listing has to be one PVE did not filter by permission. On a plain `dir` storage with no `is_mountpoint`, an empty listing counts as unproven. When the mount under such a storage drops, PVE lists the storage as empty rather than failing the call, so operators who run `dir` storage should set `is_mountpoint` on it.

- `create_vm` and `attach_disk` now report that the data is gone when a disk's CID promises a parker anchor, no VM in the cluster references the volume, and the volume is provably not on storage. Both calls used to point at `pve.parked_anchor_strict: false`, which cannot bring back a volume that is not there. The new message asks the operator to remove the disk from the Director's records with `bosh -d <deployment> cck`, or to drop it from the create-env state file, and then to redeploy so that a fresh disk is created. The refusal stays permanent and non-retriable, and an attach whose volume is not provably gone keeps the original message and its strict-mode advice.

- The orphan sweeps that run after a failed `create_disk` or a failed ephemeral disk create now use the same content-listing proof to decide whether a partial volume was left behind. Both used to ask the bare existence probe. On `dir`, NFS, and CIFS storage the `volume_size_info` reply made them skip a sweep they should have run, and on `lvmthin` and `zfspool` the missing-volume text did the same, so the partially committed volume stayed on storage. A volume the listing shows is swept as before, a proven absence skips the sweep, and an absence the CPI cannot prove skips it with the same warning as before, which now names where the CPI looked.

On a shared journal that surfaced as a `create_vm` failing outright, because the managed storage path inspects the journal before it does anything else. The check now rejects a link count above one, which is the hard-link case it always claimed to catch and the only one an attacker can create; a reader that loses the rename race reopens the file instead. ## [0.6.0] - 2026-09-14

### Added

- Multi-storage placement spreads a deployment's disks over a named group of shared NFS storages, rather than over the single storage name every role used to resolve to. `pve.storage_sets` declares the groups. A storage set names existing PVE storage IDs, either as a list or through a Go RE2 `name_pattern`, and pairs them with a versioned selection strategy. Three strategies ship at version 1. `spread` places by deterministic rendezvous hashing, `weighted_free_space` biases each pick toward the members with more room, and `least_utilized` takes the member whose projected utilization after the allocation is lowest. A set can narrow what it will accept through `types` (which has to be exactly `[nfs]`), `shared` (which has to be true), `min_free_mb`, and `max_utilization_pct`, and it can carry an `encrypted` assertion the operator makes about the backing. `pve.ephemeral_storage_set` binds the placement of new VM root disks and dedicated ephemeral disks, `pve.persistent_storage_set` binds every new persistent disk including one created with no VM to hint from, and `pve.root_storage_set` splits the root disk off from the ephemeral one for a deployment that wants them apart. A `disk_type`'s own `storage_set` cloud property then picks a named set inside whichever global boundary applies, so a deployment can steer one disk class without moving the rest. `pve.storage_capacity_domains` groups storage IDs that share physical capacity, so a set whose members live on one filer counts that free space once. It takes the most conservative observation among the members rather than counting the same space once per member. `pve.require_disjoint_storage_sets` keeps persistent disks and VM-lifetime disks on different backings, and it defaults to true whenever both global bindings exist, so an operator who wants them to overlap has to say `false` and accept the combined capacity accounting that comes with the overlap. `pve.storage_placement_namespace` names the allocation authority that set-managed placement records its allocations under. `pve.storage_allocation_journal_dir` gives the CPI an absolute, durable directory for the allocation journal it keeps while a set-managed placement is in flight, and on a Director that directory belongs on the persistent disk at `/var/vcap/store/pve_cpi/allocations`. A set-managed allocation refuses to run until the namespace is not blank and the journal directory is an absolute path the process can lock. `pve.storage_status_max_age_seconds` bounds how stale a storage observation may be when a strategy reads it, accepts 1 through 60 seconds, and defaults to 5 when it is omitted. Eight of the nine properties are overridable per cpi-config entry, as `pve_storage_sets`, `pve_storage_capacity_domains`, `pve_ephemeral_storage_set`, `pve_persistent_storage_set`, `pve_root_storage_set`, `pve_storage_placement_namespace`, `pve_require_disjoint_storage_sets`, and `pve_storage_status_max_age_seconds`, so one cluster in a multi-cluster deployment can run on storage sets while the rest stay on their scalar storage names. The journal directory is a process-level setting that no request context can redirect. Strict validation at load rejects a set that gives both `names` and `name_pattern` or neither, a pattern that does not compile, a blank or duplicated storage ID, a `types` list that is anything other than `[nfs]`, `shared: false`, an unknown strategy or version, a `max_utilization_pct` outside 1 through 100, a binding that references a set nobody defined, a capacity domain with no members, and a storage ID two domains both claim. Nothing here changes a deployment that sets none of these properties, and that deployment keeps resolving storage from `pve.vm_storage`, `pve.disk_storage`, and their cloud-property layers exactly as it did before. Declaring a set that no binding references does not turn placement on either. See [Multi-storage placement](docs/multi-storage-placement.md) for the model and the worked scenarios under `manifests/examples/multi-storage-placement/`.
- New properties `pve.parker_prefix` and `pve.parker_pool` name the parker VMs that hold detached persistent disks and place them in a PVE resource pool of their own. A parker is called `<prefix>-parker-<vmid>`, and the prefix resolves from `pve.parker_prefix` when it is set, from `pve.vm_prefix` when it is not, and from the literal `bosh` when neither is set, so a deployment that sets neither property still gets the `bosh-parker-<vmid>` names that every earlier release produced. A value set on `pve.parker_prefix` itself has to match `^[A-Za-z0-9]([A-Za-z0-9-]*[A-Za-z0-9])?$`, stay within 46 bytes, and keep clear of the `bosh-lock-` prefix that belongs to the cluster-lock sentinel pools, while a prefix that arrives by inheritance from `pve.vm_prefix` is sanitized to the VM name character set and truncated to 46 bytes with a warning instead, since that property answers to rules of its own. `pve.parker_pool` names the pool as a template whose only token is `{prefix}`, which stands for the resolved parker prefix and not for the `{prefix}` of `pve.vm_pool_template`, and its default `{prefix}-parker` renders to `bosh-parker` on a stock deployment. The CPI creates that pool the first time it needs one and writes into its comment the same `managed by bosh-proxmox-cpi` provenance it writes on every other pool it owns. A configuration whose parker pool renders onto `pve.vm_pool` or `pve.stemcell_template_pool` is refused at load, and a workload pool that renders onto the parker pool is refused at `create_vm`, because a workload VM sharing the parker pool would hold that pool open long after the deployment that created it is gone. Both properties are overridable per cpi-config entry, as `pve_parker_prefix` and `pve_parker_pool`, and `pve.parker_pool: ""` turns parker pool assignment off altogether. See [Parker VM properties](docs/persistent-disk-strategy.md#parker-vm-properties) for the resolved shapes and [PVE API permissions](docs/pve-api-permissions.md) for the grants the pool needs.

### Changed

- The library behind the OCI stemcell source, go-containerregistry, moves from v0.22.0 to v0.22.1. That patch release verifies a manifest against the digest algorithm the reference names instead of assuming SHA-256, refuses an image reference that carries an `http://` or `https://` scheme with a message that says to drop it, no longer writes an empty `auth` field into a Docker config that has no username or password, and classifies loopback, link-local, and private registry addresses before it follows a redirect or a bearer challenge to them. Pulling a stemcell from a public registry behaves as before.
- Parkers now take their name from the resolved parker prefix, join the pool `pve.parker_pool` names, and carry a `vm-prefix--<prefix>` identity tag. The rendered default is unchanged only for a deployment that leaves `pve.vm_prefix` empty. A deployment that already sets `pve.vm_prefix` and does not set `pve.parker_prefix` inherits it here, so every parker created from the upgrade onward is named `<vm_prefix>-parker-<vmid>` and lands in a `<vm_prefix>-parker` pool, and nothing renames the parkers that same deployment created before the upgrade. Such a cluster carries both shapes side by side, and no deployment fills both. A park reuses only a parker whose prefix matches the deployment's resolved prefix, so two deployments share parkers only when their resolved prefixes are equal, and a deployment creates a fresh parker rather than filling a parker that another prefix created. A parker's prefix comes from its `vm-prefix--<prefix>` tag, or from its `<prefix>-parker-<vmid>` name when it carries no such tag, and a parker that has neither counts as a `bosh` parker, so an untagged parker from before this release belongs to the `bosh` prefix. The old parkers keep holding the disks they already hold, and those disks attach, unpark, and delete exactly as they did. Pool assignment happens in a best-effort sweep that runs after every successful park, once the guarded allocation window around that park has closed. It creates the pool when the pool is missing. It then asks the pool itself which parkers already belong to it, rather than trusting the cluster index, which lags by minutes, and it assigns the parkers on that node that share the deployment's resolved prefix and are not in the pool yet. Every failure in the sweep, a permission denial among them, logs a warning and leaves the park itself successful, so the sweep can never fail a `create_disk` or a `detach_disk`. Nothing moves a parker out of a pool it already belongs to, so renaming `pve.parker_pool` later leaves the existing parkers in the old pool until an operator moves them by hand, and the disk movers that carry a disk across nodes take the same prefix but stay out of every pool on purpose. The reduced pool-scoped token described in [PVE API permissions](docs/pve-api-permissions.md) still cannot park, because the parker create passes its tags and PVE checks those against `/vms/{vmid}` before any pool registration, so pool membership arrives too late to stand in for a `/vms` grant. The pool shows up in three other places. The empty-pool reaper refuses the parker pool by name, alongside `pve.vm_pool` and `pve.stemcell_template_pool`. The startup preflight probes the parker pool whenever the parked strategy is on, and it treats a permission denial there as a warning rather than as the boot failure that a denial on either workload pool still is. `scripts/disk-audit` reports each parker's pool in its table and in every finding it raises. The `vm-prefix--` tag key joins the reserved set the CPI rewrites on every `set_vm_metadata` call, beside `director--`, `deployment--`, `instance-group--`, `job--`, and `index--`. A parker carries `vm-prefix--<prefix>` behind its `director--` tag from the moment it is created, a workload VM picks the tag up at its first `set_vm_metadata`, and filtering the PVE UI on one prefix therefore shows the workload VMs that share it and the parkers holding their detached disks in a single listing. A tag an operator supplies under that key is refused the way a `director--` tag always was, and `set_disk_metadata` drops any reserved key out of a disk's tags with a warning rather than letting it overwrite the holder VM's own. Because a parker's tag list gained a member, the managed-disk readback guard now compares the tags it sent against the tags PVE hands back as sets rather than as ordered strings, so a reordering by PVE no longer reads as a write that did not take. No migration is needed for any of this. A deployment that sets `pve.vm_prefix` and wants the old parker names back, and wants its older parkers filling again, sets `pve.parker_prefix: bosh` explicitly, and a deployment that wants no parker pool at all sets `pve.parker_pool: ""`.

### Fixed

- The `pve.vm_disk_format` job property now reaches the VM root disk and the ephemeral disk. `create_vm` resolved its format from the call's `cloud_properties`, then from a `vm_type` or `disk_type` profile, and then fell straight through to the built-in `qcow2`, skipping the job property entirely. `create_disk` and `attach_disk` had always read the same field, so the two VM-owned disks were the only ones ignoring it. An operator whose `vm_storage` is block-native (`lvm`, `lvmthin`, `zfspool`, `rbd`) sets the property to `raw` because those pools reject qcow2, and unless a cloud-config `vm_type` repeated the value, the CPI asked PVE for a format the pool cannot hold. A `cpi-config` entry overriding `vm_disk_format` for its own cluster was stranded the same way. The property now sits between the cloud-property layers and the `qcow2` default, so an explicit cloud property still wins and an unset property still lands on `qcow2`.

### Documentation

- [Operations](docs/operations.md) gains a section on where a disk format comes from, covering the four-rung resolution order, the rule that block-native pools always record `raw` while file-backed pools get the resolved format verbatim (and carry it in the volume filename), and the fact that the CPI never downgrades a requested `qcow2` to `raw`. Proxmox supports qcow2 on NFS and the CPI classifies NFS as file-backed in every format decision, so a raw volume on an NFS pool means raw was requested; the section explains how to find the layer that asked for it, starting with the `disk_type` the deployment actually uses rather than the CPI job properties.

- The Dynamic Load Balancer's cluster CRS check now reads the setting PVE actually returns. `GET /cluster/options` hands back the parsed `datacenter.cfg`, so `crs` arrives as an object keyed by sub-option with its flags as unquoted integers, not as the single property string the check decoded. That decode failed on every cluster that had a CRS setting configured and was discarded silently, leaving the CPI to believe no CRS setting was configured at all. With `pve.placement.dlb.manage_cluster_crs` false, the CPI warned that CRS was not dynamic, and printed an empty current setting, on clusters where it was already correct. With the knob true, the CPI never recognized the required setting as already present, so it rewrote the cluster-wide CRS option on every `create_vm` that registered a DLB member, and because the merge started from an empty setting, any other CRS sub-option the operator had configured was dropped on the first such write. Both shapes now decode, the warning reports the setting it found, and a cluster already in the required state is left untouched. The corrective `pvesh` command in that warning now carries the operator's other sub-options too, since `pvesh set --crs` replaces the whole property string. A `crs` value the CPI cannot decode is reported as a non-fatal DLB error instead of being treated as empty, so it can never be the base of a write, and a `/cluster/options` response with no data is now reported the same way rather than passing silently.
- Every hand-written response struct the CPI decodes from PVE now accepts the scalar shapes PVE actually sends. PVE's API is Perl-backed, so a boolean the spec declares arrives as `1`, `true`, or `"1"` depending on the endpoint and version, and counters such as `maxmem`, `avail`, or an SDN `tag` sometimes arrive as quoted strings. Our structs for `/cluster/status`, `/cluster/resources`, `/nodes/{node}/qemu`, `/nodes/{node}/storage`, `/storage`, `/pools/{pool}`, `/cluster/sdn/zones`, and `/cluster/sdn/vnets` decoded those fields, and every `vmid`, as strict Go `bool` and `int64`, and the loops around them dropped any row that failed to decode without a trace. On a cluster that sent one of the alternate shapes, the cluster-peer address map could omit online nodes, placement could see a node with no memory or no storage, `calculate_vm_cloud_properties` could report a smaller cluster than it had, a shared storage could be treated as node-local, the VNI allocator could hand out a VNI an existing vnet or zone already held, and a guest whose `vmid` arrived quoted would be invisible to the authoritative guest listing, the VMID allocator, the pool membership check, the template cache scan, and the orphan sweep in `delete_vm`. Those fields now use the SDK's tolerant `PVEBool`, `PVEInt`, and `PVEFloat` scalars, which decode every shape PVE sends, and the one decode error we still tolerate, an SDN zone row whose reserved VNIs cannot be read, is logged with the zone name, once per zone, instead of being skipped silently. Because the tolerant float parser accepts `nan` and `inf`, placement now reads a non-finite `cpu` figure as unknown load rather than letting it poison every node comparison.
- Reads from a VM's raw configuration, status, and snapshot maps no longer treat a numeric-looking value as absent. PVE returns a snapshot named `42` or a VM named `123` as a JSON number, and our `.(string)` assertions on those maps saw nothing there, which could hide a snapshot from the snapshot list or make a disk, description, or name field read as missing. Those reads now go through one helper that renders any scalar value as the string PVE would show, so a numeric-shaped name, tag, or description is handled the same as any other.

### Added

- Final release metadata is now tracked on the default branch (`releases/bosh-proxmox-cpi/` and `.final_builds/`, starting with 0.5.0), so release aggregators such as bosh.io can index our releases and rebuild them from the public blobstore with `bosh create-release`.

### Fixed

- A parker's parked-disk records no longer accumulate until they fill PVE's description field. Records were only ever removed by the unpark that carried the disk away, so a disk that left by any other route (an out-of-band delete, a remove whose config write failed, a director torn down while its disks were reaped by hand) left its record behind forever. On a lab-pmx parker holding three-day-old records from a director that no longer existed, the next write crossed PVE's 8192-character description cap and both `detach_disk` and `delete_vm` failed closed rather than lose the disk. Every provenance write now collects records whose volume nothing on that parker references and whose timestamp is older than an hour, which leaves an in-flight transfer's intent record (written before the disk lands, by design) untouched. A parker whose live records genuinely fill the store now counts as a capacity condition, exactly like a parker with no free slot: the disk moves to the next parker, or to a freshly allocated one, instead of the operation failing. That decision lands before anything destructive runs, and it now covers the ordinary detach as well as a cross-node transfer. A parker with free slots and a full store used to take the disk anyway and drop its record with only a warning, discarding the disk's CID, its source VM, and its per-disk option overlay, which is also what the CPI reads to resolve a disk whose volume was renamed under it. Room for the record is now confirmed before the disk moves.

- `delete_disk` no longer fails after a re-park on shared storage. A disk that has been reassigned to its parker carries the parker's own volume name, and the deallocation that releases it from the parker is itself the delete, yet `delete_disk` issued a second storage delete behind it. On Ceph the resulting `imgdel` failed its task with `rbd: error opening image ...: (2) No such file or directory`, a shape nothing recognized as the already-gone condition it reports, so a completed delete reached the Director as a failure. The redundant delete is gone, and an `imgdel` reporting the volume absent now reads as success on rbd, as it already did on lvmthin and zfspool. The Director's retry then misdiagnosed what it found: with the volume gone and the parker holding nothing, the anchor guard blamed a parker deleted out-of-band and advised setting `pve.parked_anchor_strict: false`, pointing at a fault that was not there. Before that refusal, `delete_disk` now checks whether the volume is still on storage. Absent means the delete already happened; the refusal stands whenever the volume is present, or whenever its absence cannot be established.

## [0.5.0] - 2026-08-24

### Added

- Single-shared-template stemcell topology. On a multi-node cluster whose `vm_storage` is shared (for example Ceph RBD), `create_stemcell` now accepts a node-local file pool for the qcow2 staging (`stemcell_storage`) under the default `template` strategy: one cache template is built, its disk lands on the shared `vm_storage`, and `create_vm` clones it to any node cross-node, so neither `stemcell_replicate_local` nor a shared file storage is required. The multi-node rejection still applies when `vm_storage` is node-local, when its shared-ness cannot be determined, or under `stemcell_strategy: import` (which reads the qcow2 from every VM's own node). A `stemcell_storage` that resolves to a block-only pool (rbd, lvm, lvmthin, zfspool) is now rejected up front with guidance to stage on a file-capable pool, instead of failing later with an opaque PVE upload error. The relaxation covers every `create_stemcell` mode the same way (tarball upload, `source_url` server-side fetch, `image_url` CPI-side fetch, and pre-uploaded `image_id`), a `stemcell_template_node` that cannot read the node-local staging pool is rejected with guidance instead of failing opaquely at template build, `delete_stemcell` sweeps stray per-node qcow2 copies that the replica list cannot name, and a `create_vm` import fallback on a node the staging pool cannot serve now returns a retriable error explaining the topology and the rebuild remedy instead of misleading re-upload guidance.

- New property `pve.node_endpoints_discovery` controls `/cluster/status` node-address discovery for direct-to-node uploads independently of `verify_ssl`. Unset preserves the existing default (discovery is on exactly when `verify_ssl` is `false`); set it to `false` to keep uploads on the configured endpoint when the discovered corosync addresses are not reachable from the CPI's network, or to `true` to allow discovery on a `verify_ssl: true` deployment whose node certificates cover their cluster addresses.

### Fixed

- Transport and API errors no longer reach the Director with the wrong retriability. Mid-lifecycle connection races (a server-closed idle connection, `net.ErrClosed`) now classify as transient in the CPI's own stemcell-fetch client, not only inside the SDK; a resolved non-429 4xx is a permanent verdict even when its body contains a pushback phrase such as "got timeout"; failed task exits under adaptive polling route through the same classifier as the default poller, and a non-OK task exit delivered as a bare status field rather than an SDK error now routes through it too, so storage-lock and quorum contention in a task exit stays retriable; node-scoped template lookups and the offline-member status probe retry transient faults like every other cluster read; two internal classifier wraps now preserve the underlying error chain, keeping downstream not-found and HTTP-status detection working; and a dozen terminal wraps that flattened an established retriable classification into a permanent cloud error now preserve it, so exhausted-but-transient storage faults surface as retriable to the Director. The JSON-RPC dispatcher's fallback consults the transient classifier before minting a permanent error from a raw transport failure.

- Every destructive branch now proves VM absence with authoritative per-node config probes. The `/cluster/resources` index can trail node-local state by minutes, and an index miss was read as "the VM is gone" by `delete_vm`, `has_vm`, `get_disks`, `set_vm_metadata`, `reboot_vm`, `delete_snapshot`, `attach_disk`, and `detach_disk`. On a miss, cluster membership is now enumerated from corosync-backed `/cluster/config/nodes` and every node's own config is probed; absence is concluded only when every node answers cleanly, and any unreachable node yields a retriable error instead. On a standalone (never-clustered) host, whose corosync node list is empty, membership enumeration falls back to the node listing, so absence proofs and `delete_stemcell`'s cluster-wide template sweep complete there instead of refusing forever. The `delete_vm` straggler sweep re-reads the authoritative config and re-tests its tags before destroying, so a reused VMID with a stale index row is never destroyed, and `delete_stemcell` refuses the branch that deletes the backing qcow2 unless its cluster-wide template sweep completed.

- Retried PVE mutations no longer replay an already-committed request destructively. A POST can commit server-side while its response drops in transit; each retried site now converges on the goal state, sweeps its own committed partial, or adopts the resource it created: `resize_disk` re-reads the size and treats at-target as success instead of re-submitting a landed grow; the stemcell upload re-awaits its own task after a drop and sweeps the committed partial before re-uploading; `reboot_vm` and the `create_vm` start convert a failed start into success when the VM is already running, and a start answered without a task to await is accepted instead of failing; `snapshot_disk` accepts a fully committed snapshot on replay; the disk-migrate mover is adopted only on an exact nonce match; and a destroy rejected by a config lock waits a bounded window for the lock to clear and re-issues once before tagging the VM for the reaper.

- Cleanup paths retry through the same storage-lock contention that triggered them. Rollback destroys, template destroys, orphan and ephemeral volume sweeps, replica sweeps, pool operations, the disk-migrate submit, and the unused-slot detach sweep were all single-shot, so one cfs-lock timeout permanently leaked the resource being reclaimed; each now rides the storage-lock retry curve with a role-scoped attempt budget, and resolved 500-text verdicts (pool already exists, VM already a pool member, config already gone) short-circuit as answers instead of spending the budget.

- Cluster-wide decision paths read authoritative per-node guest listings instead of the lagging index. The VMID allocator unions the per-node listings into its used-set, so a VMID a peer created moments ago can no longer be reallocated inside the index lag window; the `create_vm` rollback sweep refuses to destroy a VM whose identity it cannot prove, and parallel attempts carry an agent-derived name discriminator so one instance's sweep can never match a sibling attempt's live VM; disk-holder scans, the advertised-route sole-owner refcount, template lookups, and the IP-conflict guards all enumerate per node, with absence proofs failing loudly on any unlistable member and advisory readers tolerating members the quorate cluster itself reports offline; `delete_stemcell` compares director refs through the create-env sentinel and feeds its orphan prune from the VMIDs this call destroyed; and anti-affinity rules drop a member only when a complete enumeration proves its guest gone. A member the quorate cluster itself reports offline no longer blocks disk operations cluster-wide: a disk located on any listed node proves its single holder, and a disk-not-found verdict is concluded only when no member had to be excluded, with a retriable error otherwise.

- A lagging `/cluster/resources` index no longer hides a freshly built cache template. On a loaded cluster the index can trail a just-frozen template by minutes, and both consumers of the cluster-scoped sha-tag lookup mistook that lag for absence: `create_vm` fell through to the import fallback (which fails outright when the staging qcow2 lives on another node's local storage), and `delete_stemcell` took the no-template branch, deleting the staging qcow2 while orphaning the live template. The sha-tag lookup itself now reads authoritative `GET /nodes/<node>/qemu` listings, which serve node-local guest configs and do not lag, so neither consumer touches `/cluster/resources` at all; on top of that, `create_vm` probes the placement node and the template's home node (`stemcell_template_node`, or the configured `node`) inside its bounded re-check and clones the template it finds, and `delete_stemcell` sweeps every cluster node (create_stemcell can legitimately build on a non-default node) so the template and all its per-node replicas are found and destroyed.

- The `create_vm` rollback no longer destroys an attached persistent disk. When a create failed after the persistent disk was already attached (agent configure, VM start, or a post-start check, including the node-fallback retry), the rollback purged the VM with disk destruction enabled and PVE destroyed every referenced volume, including the persistent disk a `bosh recreate` was re-attaching. The rollback now detaches foreign persistent disks to safety first, exactly as `delete_vm` does, and when that protection cannot complete it preserves and tags the VM instead of purging it — an orphaned VM is recoverable, a purged persistent volume is not. The fast-path delete's straggler sweep gained the same protection: a `bosh-deleting` VM whose foreign-disk detach failed on the original delete is now deferred to the `delete_vm` retry instead of being destroyed with the disk still attached. Both paths also treat pmxcfs's "Configuration file ... does not exist" answer as the vanished-VM condition it is, rather than refusing to proceed.

- A connection dropped mid-request is retried instead of failing `create_vm`. Under a bursty deploy pveproxy can close an in-flight connection (the configdrive ISO upload was the live victim, surfacing as `Post ...: EOF` after one attempt), and that shape fell through every transient classifier: the upload was not retried and the error reached the Director as non-retriable. Mid-request drops (EOF, unexpected EOF, connection reset, broken pipe) now classify as transient transport faults, so the configdrive upload retries with a fresh body stream (clearing the target filename first, in case the dropped request actually committed the file; a clear that itself hits a retryable fault rides the same backoff curve instead of pressing into a guaranteed duplicate rejection), and an exhausted retry budget surfaces retriable.

- Storage uploads no longer traverse the cross-node pveproxy hop, and they carry their own retry budget. An upload targeting storage on a node other than the configured endpoint was proxied by the endpoint node's pveproxy to the target node's pveproxy, and under a many-VM deploy burst that hop shed connections mid-request (`EOF`) while uploads to the endpoint node itself kept working; the roughly one-minute upload retry window then ran out before the burst did. Stemcell image and per-VM ConfigDrive ISO uploads now dial the target node's own pveproxy directly, resolving its address from the new `pve.node_endpoints` map (node name to `host` or `host:port`; explicit entries always win) and falling back to `/cluster/status` discovery when `verify_ssl` is `false`, since the discovered corosync address is usually absent from stock node certificate SANs. A routed attempt that fails TLS certificate verification, any other TLS handshake failure (a non-TLS listener answering the routed port, for example), the dial itself, or a network fault while the routed connection is still being established logs a warning, falls back to the configured endpoint, and skips that node's direct route for the rest of the process, so a wrong entry degrades to the proxied path instead of failing the deploy. Map entries are validated at config parse; a node name or address with surrounding whitespace is rejected. The uploads also moved to a dedicated retry class, `pve.retry.storage_upload.max_attempts`, whose built-in budget of 30 attempts (roughly six minutes on the transient curve, roughly twelve when storage-lock contention dominates) outlasts a burst window the previous 10-attempt default did not.

- Surfaced errors no longer print the underlying cause twice. Wrapped errors carried the cause text inside the wrap message while the error chain appended the same text again, producing shapes like `failed to upload ... EOF: failed to upload ... EOF` in Director output (and, on some `create_vm` paths, three copies). Wrap messages now state only their own context and the chain renders the cause exactly once; classification and retriability are unchanged.

- An unresolved task poll timeout is no longer mistaken for a transport fault. When polling a PVE task times out without a verdict the task may still be running, but the timeout satisfied the transient-transport classifiers, and the disk-move, configdrive-upload, snapshot, and stemcell-template-freeze sites resubmitted their mutation on retry, double-applying it (and, for the configdrive, deleting an upload still in flight). The timeout now carries its own classification, retriable to the Director but not transport-shaped, and each of those sites re-awaits the original task on the next attempt instead of resubmitting; the configdrive target sweep runs only on evidence that the upload actually failed or its request dropped.

- Pool assignment no longer reports success on an unconfirmed membership verdict. When the pool-membership probe could not answer (a token missing `Pool.Audit`, for example), `create_vm`'s pool assignment treated the ambiguity as "already a member" and returned success with the VM outside its pool. The probe's failure is now classified: a permanent denial falls back to the cluster-index check, a transient fault retries, and a definitive "not a member" answer from PVE's own membership endpoint is never overturned by the lagging cluster index.

- Exponential retry backoff saturates at its configured ceiling instead of overflowing into a zero-delay retry storm at very high attempt counts, and config validation now caps every `pve.retry.*.max_attempts` at 100.

- Ephemeral-disk allocation backs off in place on storage lock contention. Parallel `create_vm` calls allocating ephemeral volumes on one shared pool contend on the cluster storage lock, and the losers failed the whole call back to the Director, which re-ran clone, boot, and configure only to re-enter the same contention window. The allocation now retries in place on the same storage-lock backoff curve `create_disk` uses (with the default attempt budget), and when every attempt fails, a volume the failed request may still have committed is swept best-effort before the error surfaces, so the Director's redo does not leave an orphan behind. A replayed attempt that finds the volume its own dropped request already committed adopts it and proceeds instead of spending the rest of the budget colliding with it.

- Storage lock contention on shared pools is retried instead of failing the deploy. PVE's cluster-wide storage lock surfaces as `cfs-lock 'storage-<pool>' error: got lock request timeout` when concurrent clone, create, or destroy tasks contend on one shared pool — routine during mass VM creation from a single template on RBD. That shape now classifies as a transient storage-lock timeout everywhere the existing file-lock timeout does, so `create_vm` retries the clone rather than surfacing a terminal error.

- Retriable errors now cross the wire as classes the Director recognizes, so its own retries engage. The dispatcher previously serialized `Bosh::Clouds::RetriableCloudError`, which the Director knows only as an abstract base class: it rejected the response as `Unknown CPI error`, discarded `ok_to_retry`, and failed the task on the spot, so a transient fault that outlived the CPI's internal retries (a mass-create burst exhausting the configdrive upload budget, for example) killed the deployment instead of triggering the Director's create retry. A retriable error escaping `create_vm` now serializes as `Bosh::Clouds::VMCreationFailed` with `ok_to_retry: true`, which the Director's create step retries up to `max_vm_create_tries` (default 5) with fresh CPI calls; retriable errors from other methods serialize as `Bosh::Clouds::CloudError` with the flag preserved, since the Director has no retry loop for them. The same translation maps the internal `DetachedDisk` type to the Director's `DiskNotAttached` and the internal stemcell-validation and snapshot-guard types to plain `CloudError`, so no CPI response can surface as `Unknown CPI error`.

- A destroy task that completes with `WARNINGS: N` no longer fails `delete_vm`. PVE ends `qmdestroy` with a warnings exit when the VM was removed but a disk could not be deleted under storage-lock contention ("Could not remove disk ..., check manually"); the plain task await treated any non-OK exit as failure, turning a completed delete into a CPI error. Both await paths now accept completed-with-warnings, matching the PVE UI's own reading; any leftover volume is left to `scripts/disk-audit`.

### Changed

- The release is renamed from `bosh-pve-cpi` to `bosh-proxmox-cpi`; this is the first release published under the new name, and the GitHub repository moves to `fivetwenty-io/bosh-proxmox-cpi-release` (old URLs redirect). To a Director the renamed release is a new release, and the tarball's embedded release name must match the manifest's release name exactly or create-env/delete-env refuses with a name-mismatch error. `manifests/bosh/cpi.yml` sets the release name from a new var, `((pve_cpi_release_name))`, instead of a literal string. `scripts/bosh create-env` and `scripts/bosh teardown` read the name from the tarball's `release.MF` and supply the var automatically (`bosh-proxmox-cpi` for a release built from this repo, `bosh-pve-cpi` for a published tarball through v0.4.0), so operators using `scripts/bosh` need no manifest edits. A hand-rolled ops file that skips `scripts/bosh` must supply `pve_cpi_release_name` itself: `manifests/bosh/vars.yml.example` now sets a `bosh-proxmox-cpi` default, which we override to `bosh-pve-cpi` when deploying a v0.4.0-or-earlier tarball, then optionally run `bosh delete-release bosh-pve-cpi` once nothing references the old name. The job name `pve_cpi`, every `pve.*` property, the `PVE_CPI_RELEASE_PATH`/`PVE_CPI_CONFIG` environment variables, cpi_ids, and all CIDs are unchanged. Release assets for v0.4.0 and earlier keep their `bosh-pve-cpi-<version>.tgz` filenames, and `scripts/certify` and the acceptance workflow accept both names when fetching old versions.

### Added

## [0.3.0] - 2026-08-21

### Added

- Stable disk identity. `create_disk` mints a `bpd-` plus 16-hex identity token that rides the drive's `serial=` attribute for the life of the disk, and attach resolves a disk by serial scan first, provenance sentinel second, and birth volid last, so a disk keeps its CID across the volume renames that parking and reassignment cause. Ownership moves by `move_disk` reassignment between the holder and the parker slot rather than by config-line surgery. CIDs minted before this release carry no token and resolve by volid forever. See [Stable disk identity and ownership transfer](docs/persistent-disk-strategy.md#stable-disk-identity-and-ownership-transfer).

- `create_disk` parks fresh disks under the parked strategy, fail-closed: a disk that cannot be parked at creation is not left floating.

- The disk CID records its create-time format, and block-native storage records `raw`, so later attaches rebuild the drive string from what was actually created rather than from current config.

- Operations on a parked disk whose parker anchor has vanished are refused with the repair path named, instead of proceeding against storage the parker no longer references.

- IPv6 dual-stack networks. Networks that share a `nic_group` plan onto one NIC with both `ip=` and `ip6=` addresses, and the BATS runner grows an opt-in dual-stack pass (`--only ipv6`).

- Offline wire-protocol conformance suite. `make test` now drives the compiled CPI binary against a refused endpoint and asserts exactly one well-formed response envelope per request, exit 0, retriable error typing with `ok_to_retry`, an `api_version` handshake matrix pinned to 2, and a stdout that carries nothing but envelopes, with no lab required.

- Consolidated [Known Limitations](docs/limitations.md) page stating every scope limit in one place.

- `update_disk` option updates are now durable. Every option change is recorded as a per-disk override map, and each attach builds the drive string by merging global `disk_performance` config, then the options recorded in the disk CID at `create_disk` time, then the recorded overrides — rightmost wins, and an empty-string value deletes the key. Previously a detach/attach cycle rebuilt the drive string from config and CID options alone, silently reverting every operator update. The record lives on the holder VM's description (`bosh_disk_opt_overlays` sentinel key) while attached and rides the parker's `bosh_parked_disks` provenance entry (new optional `opts` field) while parked; `update_disk` writes it fail-closed before touching the drive, and the invariant guard (`pve.disk_perf_invariant_mode`) treats recorded updates as part of the expected baseline rather than as divergence. A parked disk can now be updated too: the change is recorded (and `size` applied to the volume directly) and takes effect at the next attach, where the old behavior wrote options onto the parker's drive string and lost them at unpark. Two paths still drop the record, with a logged warning: a detach under `detached_disk_strategy: free` (no carrier exists for it), and `delete_vm`'s plain detach of a still-attached legacy foreign disk. See [Durable disk option updates](docs/persistent-disk-strategy.md#durable-disk-option-updates).

### Changed

- The gzip-compressed `pvz-` disk CID fallback now engages automatically whenever the plain `pvd-` envelope would exceed the 255-character bound of MySQL-backed Directors, instead of failing `create_disk` unless `pve.disk_cid_compression` was set. The stable-identity field made richly-annotated envelopes overflow in ordinary configurations, so the opt-in became a trap: a default-config `create_disk` under the parked strategy could fail outright. CIDs that fit stay `pvd-` and byte-identical, decode has always accepted both forms, and `pve.disk_cid_compression` is retained as an accepted no-op.

- `pve.vm_pool_template` now defaults to `bosh-{director}-{deployment}`, so every deployment gets its own auto-created resource pool (`bosh-<director>-<deployment>`; `bosh-create-env` for `bosh create-env` environments) instead of everything landing in the single static `bosh` pool. Each VM records how its pool was resolved in a `bosh_pool` sentinel on its PVE description, and `set_vm_metadata` re-renders the template from that record on every deploy, moving a template-placed VM whose pool has drifted; VMs placed by `cloud_properties.pool`, a `vm_type` profile, or the static `pve.vm_pool` are never moved. Existing VMs sitting in the static `bosh` pool are adopted into their deployment's pool on the next deploy. Upgrade notes: the CPI token needs `Pool.Allocate` and `Pool.Audit` at the `/pool` parent (per-deployment names are dynamic, so a per-poolid grant cannot cover them); reduced-ACL clusters whose token cannot create pools should set `pve.vm_pool_template: ""` to keep the single-pool model, and `create_vm` names that exact fix when pool creation is denied. A resolved pool name equal to `pve.stemcell_template_pool` is now rejected at `create_vm` time.

- `pve.pool_reap_empty` now defaults to `true`: a per-deployment pool is deleted when the synchronous `delete_vm` path destroys its last VM. Only pools carrying the CPI's `managed by bosh-pve-cpi` provenance comment are ever reaped, the static `pve.vm_pool` and `pve.stemcell_template_pool` are refused by name, and the fast-path delete still skips the reaper. Set the property to `false` explicitly to keep empty pools; the key is now always rendered into the CPI config, so an explicit `false` takes effect (previously the template could not express it).

- The parker VMID band now resolves under every `detached_disk_strategy`, at the job level and in every cpi-config entry alike: unset bounds fill with the built-in `90000`–`90999` whether the strategy is `parked`, `free`, or stood down by a band collision. Under `free` the band is read-only: nothing allocates a parker VMID in it, a band overlap is accepted rather than rejected at load, and disks parked while `parked` was in effect are recognized and unparked on their next `attach_disk` or `delete_disk` instead of being refused until an operator restores the band by hand. Switching to `free` no longer needs the band carried forward, and the load-time warning for `free` without a band is gone with the state it warned about. The stranded-parker refusal remains for a band moved away from VMIDs where parker VMs still live.

- The vendored Proxmox API client SDK is v3.8.6.

### Fixed

- A snapshot that blocks the detach reassignment defers the park instead of failing `detach_disk`; the disk parks on its next detach once the snapshot is gone.

- `create_vm` with `disk_cids` runs the full attach guard path, so a foreign holder or a stale parker is caught at VM creation the same way `attach_disk` catches it.

- Task-await log lines follow the UPID's effective node, so logs name the node that actually ran the task.

## [0.2.0] - 2026-08-19

### Added

- BOSH Director Upgrade Test runner: `./scripts/certify`, which stands a Director up on the previous CPI release, deploys the upstream [certification release](https://github.com/cloudfoundry/bosh-cpi-certification) under it, upgrades the Director onto the latest release over the same state, and recreates the deployment, asserting that disk CIDs and the disk attachment survive the version change. Ships with the [BOSH Director Upgrade Test](docs/certification/upgrade.md) guide and a committed [run record](docs/certification/upgrade/README.md).

- Parked-disk lifecycle coverage in the integration harness: `scripts/lifecycle` drives a detached disk through both `detached_disk_strategy` settings against live PVE and verifies the parker VM, its protection flag, its provenance sentinel, and every refusal path out-of-band; `scripts/test integration` grows `tier1.parked_disk` (band and toggle) and `tier1.stemcell_replicate_local` for multi-node labs with node-local stemcell storage.

### Changed

- `pve.detached_disk_strategy` now defaults to `parked`: a detached persistent disk is held on a protected parker VM instead of floating as an unattached storage volume, so PVE shows who owns it and `protection=1` blocks an accidental delete. The previous free-floating behavior is still available by setting the property to `free`. Three consequences for existing deployments that never set the property: detach and attach each spend more PVE API calls, and `attach_disk` and `delete_disk` now resolve the volume's holder on every call, which costs one cluster listing plus a config read per VM in the cluster; each PVE node accrues one protected `bosh-parker-<n>` VM once a disk is parked there, which no CPI call ever deletes (`scripts/disk-audit` reports empty parkers along with the two commands that remove one); and the parker VMID band (`90000`–`90999` by default) must not overlap the VM, persistent-disk, or stemcell-template bands. A config that sets neither the strategy nor a parker band and whose other bands already reach into that window keeps the previous free-floating behavior for that load and says so in a warning, rather than failing to load, so the upgrade cannot take a running deployment down. Disks already detached stay free-floating and are picked up normally by the next `attach_disk` or `delete_disk`; `manifests/cpi-config.yml` shows the per-entry parker bands a shared-storage multi-cluster layout needs.

- **Before rolling back to a release older than this one, drain the parkers.** A release without the parked strategy has no unpark step, so it would attach a volume the parker still references and leave two VM configs pointing at one volume. Set `pve.detached_disk_strategy: free`; on 0.2.0 itself also set `pve.parked_disk_vmid_range_start: 90000` / `_end: 90999` explicitly so the unpark probes keep running (releases after 0.2.0 resolve an unset band on their own). Nothing drains a parker on its own: each disk comes off when the Director next attaches or deletes it, so redeploy the instance groups that own them and `bosh delete-disk` any orphans. Run `scripts/disk-audit` until it reports no parked disks, and roll back after that.

- `delete_disk` now refuses to free a volume still held by a parker VM the configuration can no longer recognize, naming the property to set. Freeing it would leave the parker's slot referencing storage that no longer exists.

- `attach_disk` now refuses a volume that is already attached to a VM other than the target, naming the holder. PVE permits two VM configs referencing one volume and nothing downstream detects it, until whichever holder is destroyed takes the volume with it. When the holder turns out to be a parker VM outside the configured band, the message says which property to set to make the disk reachable again.

- `pve.detached_disk_strategy` is overridable per cpi-config entry as `pve_detached_disk_strategy`, so one cluster whose VMID topology has no room for a parker band can opt out while the rest of the deployment keeps the default.

- Parker VMs are adopted only by the director that created them. Each carries a `director--<uuid>` tag, and a park now skips parkers attributed to another director rather than filling them, which keeps two directors sharing one PVE cluster from entangling their volumes. Parkers with no attribution tag stay adoptable by anyone.

- Unparking a disk now clears the parker VM's `protection` flag for the length of the detach and restores it immediately after. PVE treats detaching a disk as a "remove disk" operation, which that flag blocks, so `attach_disk` and `delete_disk` could not retrieve a parked disk while it was set. The flag is restored even when the detach fails, and a failed restore is logged with the command that repairs it.

- Parking a disk resolves its current holder with a single cluster scan instead of two. The scan reads every VM config in the cluster, so this halves the dominant cost of `detach_disk` under the parked strategy.

- `snapshot_disk` and `delete_vm` recognize a parker VM by its `bosh-parker` tag rather than by the configured VMID band (`delete_vm` reads the tag from the cluster-resources row, falling back to the VM config when that row carries no tags at all). An operator who turns parking off without carrying the band forward would otherwise disarm both guards over exactly the parkers that change stranded: a PVE snapshot takes the whole VM, entangling every deployment's disks held on that parker, and the fast delete path issues a purge that bypasses `protection=1`. Neither guard costs an extra API call.

- Each cpi-config entry decides the parked default against its own VMID bands. An entry that widens `pve_vmid_range`, `pve_disk_vmid_range`, or `pve_stemcell_template_vmid_range` over the built-in parker band stands the default down for that entry with a warning, rather than failing every request routed to that cluster; an entry that narrows those bands back gets the default it would have had on its own. An entry that names `parked` itself, or that sets a parker bound of its own, is honored as written. The parker band ApplyDefaults fills in is no longer inherited as though the entry had typed it, so an entry that moves one bound gets the built-in fallback for the other instead of a value meant for a different cluster.

- The parker band's overlap check now applies only under the `parked` strategy. It exists to stop the CPI allocating a parker VMID another band will claim, and nothing allocates one under `free`, where the band is read-only and every parker classification also requires the `bosh-parker` tag. A deployment that opts out precisely because its VMID layout has no room for a parker band is no longer rejected for the overlap.

- Unparking a disk re-resolves its slot inside the protection window. `DetachDisk` names a slot, not a volume, so a slot looked up before the lock was a blind write by the time the detach ran: two overlapping unparks of one disk could detach a volume a concurrent park had just placed in the freed slot, silently un-parking a disk whose own `detach_disk` had already reported success. A volume found off the active bus but still named by an `unusedN` key is swept instead, and one already gone is an idempotent no-op.

- Parking and unparking one parker VM are serialized against each other by a per-VMID lock. Both write its `protection` flag, and PVE clears a detached disk in two requests: a park restoring `protection=1` between an unpark's two halves made PVE refuse the second one, leaving the volume referenced by an `unusedN` key no probe matches on while the unpark reported a retriable failure. The same lock stops a park claiming a slot an unpark is about to detach by name. The lock is the same `bosh-lock-<name>` sentinel-pool mechanism the anti-affinity and VMID locks use, and it is taken on every park and unpark rather than behind an opt-in, so the CPI's PVE identity needs `Pool.Allocate` on `bosh-lock-*`. Without it the window runs unserialized, with a warning, rather than failing the call; see [PVE API permissions](docs/pve-api-permissions.md).

- An unpark that detaches the volume but cannot clear the `unusedN` key PVE demotes it to now fails permanently, naming the parker and carrying the `qm unlink` sequence that clears the reference. The detach has already succeeded at that point, so a retriable failure would send the Director's retry past the holder scan (which matches active-bus slots only) and on to attaching a volume the parker still references. Two paths that previously reported such a sweep as clean, a config read that failed mid-sweep and a parker band overlapping the disk band, now report it as the unswept reference it is.

- LXC containers no longer break parking, unparking, or the holder scan. The cluster listing both use covers containers as well as VMs, and every read behind it goes through the QEMU config endpoint, which answers for a container with a pmxcfs "Configuration file ... does not exist" error rather than a 404. One container in the parker band used to fail every park and unpark on its node; one container anywhere in the cluster used to fail every `attach_disk`, `detach_disk`, and `delete_disk` of a persistent disk, retriably and forever, once parking became the default.

- A park that strands a reference now fails permanently on every exit, not just the one that ran out of slots. A slot lost to a concurrent park leaves the volume on an `unusedN` key; when the sweep that clears it fails, the park used to hand back a retriable error, or `ErrNoSlots`, either of which sends the volume to another parker or another attempt while the first parker still references it. Both references are invisible to the holder scan, and destroying either parker frees a live volume.

- A sweep that removes the `unusedN` key but cannot read the config back to confirm it now fails permanently and keeps the provenance entry. It used to report success on the grounds that a later read would catch a surviving reference; no later read happens, since an unpark of a volume already off the bus returns early and a park only sweeps a slot it lost in that same call.

- A full parker that still references the volume on an `unusedN` key is swept rather than skipped. Walking past it to the next parker is what puts one volume in two parkers' configs.

- Failures on the parker paths are classified rather than reported retriable by default. A missing `VM.Config.Disk` or `VM.Audit` grant never comes right on its own, and the Director was driving the park against it forever instead of surfacing the permission to grant. Config reads and mutating calls are classified separately: a read defaults to permanent, since its failure shapes are enumerable, while a mutating call defaults to retriable, since PVE reports plenty of transient conditions as prose no classifier recognizes and a park that failed permanently on one of those would leave the disk free-floating. `detach_disk` no longer flattens the result: a denied grant or an exhausted VMID band reaches the Director as the permanent condition it is, naming what to fix.

- Work inside a parker's protection window runs under a deadline derived from the window lock's own TTL, and every retry loop inside it is bounded. Bounding the loops alone was not enough, because their worst cases compose: the storage-lock curve alone would have slept past two minutes, and a protection write under PVE pushback past four, long enough for another park or unpark to steal the lock and enter the window while the first caller was still inside it. Releasing a lock whose claim has already lapsed no longer deletes the sentinel, which used to remove a stealer's claim and let a third caller in while they were mid-window.

- `set_disk_metadata` falls back to the VM config when a cluster-resources row carries no tags at all, as `delete_vm` already did. An empty tags field cannot tell an untagged VM from a PVE that does not populate the field, and treating a parker as an ordinary holder writes deployment metadata into the description carrying its provenance sentinel.

- The `detach_disk` retry path resolves the disk's holder once instead of twice. It asked the same cluster-wide sweep two questions, "is it parked?" and "does a real VM hold it?", that are two readings of one answer.

- `attach_disk` and `delete_disk` now resolve the volume's holder on every call, whatever the strategy says, and refuse when that holder is a parker the configuration can no longer recognize. The refusal reads the tags the holder scan already returned, so it costs no extra API call and has no failure mode of its own: an earlier shape read the holder's config a second time and treated an unreadable config as "not a parker", which sent `delete_disk` on to destroy a volume a parker's slot still referenced. One consequence to plan for: because the scan reads every VM's config, a node that is down fails both calls retriably cluster-wide until it returns. A cluster-endpoint fault that outlives the retry budget is now reported retriably too, so the Director re-drives instead of giving up on a corosync blip or a quorum loss.

- Parker tags are recognized whatever separator PVE stored them with (`;`, `,`, or a space, the three its tag format accepts). A tag string the CPI failed to tokenize was a guard that silently did not fire, which for `delete_vm` meant a `skiplock` purge over a VM holding up to 31 other deployments' disks.

- `scripts/disk-audit` counts `unusedN` references when deciding whether a parker is empty, and never calls a parker empty when its config could not be read. A parker whose only remaining reference was an unswept `unusedN` key was reported as empty and offered as a teardown candidate with `qm destroy --purge`, which frees exactly that volume. A stranded reference now draws its own warning naming the `qm unlink` sequence that clears it.

- Consolidated the certification documentation under `docs/certification/`: the certification overview, the BATS guide, and the BATS run record moved there, joined by the Director upgrade guide and its run record.

- The create-env harness and example manifests now pin work to the configured node, which multi-node clusters with node-local storage require. The light stemcell manifests the harness generates carry `cloud_properties.node` (the light preuploaded validation demands one on a multi-node cluster), and `manifests/bosh/cloud-config.yml` and `manifests/bosh/cpi.yml` pin the AZ and the Director's resource pool to `((pve_node))` — without the pin, placement can pick a node that holds neither the stemcell cache template nor the VM's persistent disk, and an operator-owned preuploaded qcow2 is nothing the CPI can replicate across nodes. Single-node clusters and shared-storage layouts are unaffected; shared-storage clusters may drop the pins.

- Light stemcells in both pre-uploaded and CPI-fetch modes, with node pinning and storage requirements documented.

- Placement: availability-aware node scoring on reserved memory, same-instance-group anti-affinity spreading, disk fault-domain co-location, storage-pool selection, resource-pool assignment with create-if-missing and an opt-in reaper, and opt-in PVE 9.2 Dynamic Load Balancer awareness.

- Networking: `create_network` and `delete_network` via PVE SDN with Linux bridge fallback, layered `cloud_properties`, per-NIC overrides, per-VM firewall and security-group attachment, allowed-address-pairs VIP ipfilter, pre-create IP-conflict detection, and opt-in SDN eventual-consistency gates.

- Persistent disks: the `pvd-` CID envelope with legacy decode, per-disk performance options, creation-time performance invariants enforced on re-attach, an opt-in parked-disk detachment strategy with provenance sentinels, `get_disks` backed by attach-time recording, and the `scripts/disk-audit` tool.

- Agent bootstrap by ConfigDrive ISO with no external registry, agent-mode auto-selection, stemcell-driven disk sizing, and a boot-path agent integrity checksum assertion.

- Resilience: opt-in progress-aware adaptive task polling, per-method timeout envelopes with configurable retry and poll cadence, transport tuning for parallel deploys, opt-in fast-path delete with a self-healing straggler sweep, alternate-node retry on transient `create_vm` failures, and PVE pushback handling.

- Safety: `delete_vm` guarded against destroying attached persistent disks, `delete_disk` guarded against in-flight VMs, cross-process VMID and anti-affinity race tolerance, dispatch hooks with a rollback contract, and a keep-failed-VMs debug mode.

- Security: minimum-privilege `bosh@pve` role documentation and API-token support (preferred over password when both are set), SSRF and allow-list closure on stemcell fetch, log scrubbing of credentials and presigned signatures, strict config validation, and a frozen exec allow-list.

- Observability: opt-in `pve.otel.*` tracing, logs, and metrics with OTLP HTTP and gRPC exporters, per-request correlated logging, an opt-in redacted request/response trace at the dispatcher boundary, and duration metrics with outcome classification.

- Operations: soft and hard `reboot_vm` with graceful fallback, an `unstick-agent` subcommand, HA node-affinity pinning, multi-cluster (multi-CPI) support with disjoint VMID banding, and configurable VMID bands.

- Test and CI infrastructure: a tiered live-PVE integration harness, an end-to-end runner with per-phase timings, a JSON-RPC fuzz target, GitHub Actions check and security gates, and an 80% coverage gate.

- The documentation set: architecture, CPI methods, configuration, networks, persistent disks, permissions, best practices, troubleshooting, and the operations runbook.

### Changed

- VMs are named `{prefix}-{deployment}-{job}-{index}`.

- `create_vm` accepts `ram` as an alias for `memory` and `env.bosh.mbus` as a flat string.

- Task status polls target the node embedded in the UPID, and attach and detach target the VM's current node.

### Removed

- BOSH registry agent mode. Supported modes are `cloudinit`, `noagent`, and `auto`; `registry_*` properties now fail fast.
