# Changelog

All notable changes to this project are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Entries describe operator-visible change: CPI behavior, properties, packaging, and the
documentation set. Refactors, test work, and CI plumbing appear only when they change
what an operator sees or how a release is produced. The `Unreleased` section collects
work as it lands; cutting a release renames it to the new version and dates it. See
[CONTRIBUTING](CONTRIBUTING.md#releasing-maintainers) for the release procedure.

## [Unreleased]

## [0.9.0] - 2026-10-03

### Added

- `storage-journal audit` and `storage-journal audit-enrollment` take a new `--summary` flag, which prints the audit as plain text for a Director that has no `jq`. For `audit`, the first line gives `complete`, `vm_scan_complete`, `generation_index_healthy`, `cluster_continuity`, and the record count. Each finding then gets a line of its own, prefixed `conflict:`, `vm-scan issue:`, `issue:`, or `observed move:`, and the charging summary and any skipped disabled storages come last. `audit-enrollment` opens with its own line, which gives `complete`, `vm_scan_complete`, and the evidence count, and it prints no charging line. After its findings it prints one `provenance:` line per existing provenance entry. The exit code matches the JSON mode exactly, and every other action rejects the flag with exit code 2 and the usage line. See [Inspect retained allocations](docs/storage-journal-operations.md#inspect-retained-allocations).

- `storage-journal audit --summary` now prints one `record:` line for each record that needs an operator, which is any record outside `ready_to_return`, `adopted`, `cleaned`, and `deleted`, and any record that is charging. The line gives the ID, kind, state, whether it charges, the full CID or `none`, and the record's reason, and one `evidence:` line under it names each volume, node, and holder VMID that still carries the allocation. Healthy records are left out, and the records are in ID order. Before this, an operator who needed a record's CID for `adopt` had to read the one-line JSON on a Director that has no `jq`. See [Inspect retained allocations](docs/storage-journal-operations.md#inspect-retained-allocations).

- `storage-journal audit --summary` now prints one `planned step:` line for each planned step in the journal, after the record lines and before the charging line. The line gives the record ID, the step ID, and the step's kind, and for a parker protection step it also gives `parker_vmid` and `node`. An operator who is rolling back can read these lines to find the records that still hold a planned step, instead of running `adopt` or `cleanup`, which act on any record they admit. A journal with no planned steps prints exactly what it printed before, and neither the JSON output nor the exit code changes.

- The audit report gains `vm_scan_issues`, which repeats the issues that left the VM scan incomplete. Those are the issues that block `create_vm`, so an operator no longer has to work out which of the `issues` entries is responsible. Like `issues` and `conflicts`, the field is always present.

- The audit report gains `observed_moves`, which lists each VM, persistent disk, or parker that the audit found on a node other than the recorded one and accepted as a move on shared storage. Each entry carries `allocation_id`, `kind`, `vmid`, `recorded_nodes`, `observed_node`, and `volumes`. Verification evidence that an operation retains carries the same list whenever that audit saw a move, and evidence from an audit that saw none keeps its earlier shape byte for byte.

- `scripts/disk-audit` now lists every volume that more than one guest's config names, on an active slot or an unused entry, which is a shape earlier releases could leave behind. Each volume shows every guest and slot that names it and marks the guest that owns the volume by name, because destroying that guest, or removing its unused entry, deletes the volume while another guest still uses it. The script warns about each one on stderr, and the JSON output gains `multiply_referenced`, along with fields that say when the report may be incomplete, either because a guest's config could not be read or because the token cannot audit every guest. The exit code does not change. Operators upgrading from 0.8.x can run it to find these volumes before they deploy. See [Auditing parked disks with scripts/disk-audit](docs/operations.md#auditing-parked-disks-with-scriptsdisk-audit).

### Changed

- The allocation audit now accepts a VM, a persistent disk, or a parker that the cluster operator moved to another node, as long as everything involved sits on shared storage that the new node can see. A live migration during a rolling patch cycle used to raise a conflict, and a single conflict blocks every `create_vm` in the namespace, so one maintenance window could freeze every deploy on a Director. A VM move is accepted only when the VM scan is complete and the record is in `ready_to_return` or `adopted`, or when `delete_vm` or `storage-journal cleanup` has since taken the record out of those states and the admission it wrote accepted the same move of the same VMID to the same node. The VMID must belong to the active attempt, the allocation marker must have been sighted exactly once with a matching agent digest, and every configuration volume must belong to this allocation or to a disk whose provenance the VM carries. Every volume the VM holds must sit on shared storage too, and that includes a hibernation `vmstate`, every snapshot's volumes, and every volume the active attempt recorded. Each such storage must have been shared when the plan was frozen and must keep the backing that plan froze, it must be available on the new node, and that node's listing in the same audit must show the volume. A moved disk or parker must be in its holder's configuration and meet the same storage conditions. Anything that touches node-local storage stays a conflict, and the conflict now ends with the reason the move was refused. The audit decides each move afresh on every call and never records a step for it in the journal. Resume, adoption, `delete_vm`, `detach_disk`, and every call that uses a persistent disk's parker follow the same decision, and `detach_disk` rewrites a moved disk's provenance to name its current node before the disk moves to its parker. A `delete_vm` or a `storage-journal cleanup` that is still running, or that failed partway and is retried, keeps following the move, so another deployment's `create_vm` is not refused in the meantime, and a cleanup of a returned VM that moved finishes just as it does for one that never moved. When a crash leaves a delete step unsettled, `storage-journal cleanup` follows the move, while a plain `delete_vm` retry refuses for a moved VM just as it does for one that never moved. The retention parker that `delete_vm` creates for retained ephemeral disks stays strict, because its entry carries no allocation ID for the audit to decide on, so its cleanup still needs the parker on its recorded node. See [An operation fails with an allocation audit refusal](docs/troubleshooting.md#an-operation-fails-with-an-allocation-audit-refusal).

- A Director can roll back from this release to 0.8.1, as long as we first settle the records that hold a planned parker protection step. We don't roll back to 0.8.0, because it still has the disk-loss bugs that 0.8.1 fixed. 0.8.1 loads and validates every record this release writes. That includes the `observed_moves` list inside verification evidence, which 0.8.1 ignores, and the parameters on a parker protection step, which record the restore's value as `{"kind":"parker_protection_on","version":1}` or `{"kind":"parker_protection_off","version":1}`. What 0.8.1 can't do is settle a planned parker protection step, because it has no protection settler. After a rollback, every 0.8.1 lifecycle call on such a record refuses with `lifecycle has unresolved mutation evidence; audit required`, and the record stays in `reconciliation_required`. Before we roll back, we find these records with `storage-journal audit --summary`, which prints one `planned step:` line for each planned step, as in `planned step: record=7129cd53-7121-40ff-9712-4ddc21a4d7fe step=attempt-0-step-18 kind=lifecycle_attach_disk_Nodes_UpdateQemuConfig parker_vmid=90000 node=pve01`. We read that line instead of running `adopt` or `cleanup` to look, because those commands act on any record they admit. For each such record, we put the parker's protection back with the `qm set` command that 0.9.0's refusal names, and we rerun the call, or run `adopt`, until the step reads observed and its `planned step:` line is gone. If we have already rolled back, we roll forward to 0.9.0, which settles the step on the next call. A 0.8.1 CPI simply raises the old conflicts for moved VMs again and refuses `create_vm` until they go back to their recorded nodes. If we roll back to 0.8.1 while a VM holds a disk under a name that a parked disk once carried, 0.8.1 brings back the false holder conflict for the parked disk, and it refuses `create_disk` and `create_vm` for as long as that reused name exists. Rolling back below 0.8.0 stays barred for as long as grouped allocation records are non-terminal, as the 0.8.0 entry describes.

- After we upgrade, a cluster where some VM already references one of our volumes alongside the VM that BOSH gave it refuses every audit-gated call, from `create_vm` and `create_disk` through `delete_vm`, `delete_disk`, and `storage-journal cleanup`, until that reference is gone. 0.8.0 and 0.8.1 raised it only when a second VM held a persistent disk that a live record tracks, so nothing warned about a shared reference to any of our other volumes before. The refusal names both VMs, as in `volume <volid> is attached to 2 VMs: VM <vmid> on <node>, VM <vmid> on <node>, allocation <id>`, and for a persistent disk it leads with `disk allocation <id> has 2 holders: ...` and gives that text second. We clear it by taking the extra reference out of the configuration of the VM that shouldn't hold the disk. We stop that VM first, or confirm that it is already stopped, because removing a line doesn't unplug the disk from a running guest. Then, on the node that holds that VM, we remove only that drive's line from `/etc/pve/qemu-server/<vmid>.conf` by hand, along with the same volume's line in the file's `[PENDING]` section when it has one, and we confirm with `qm pending <vmid>` that no `unusedN` entry names the volume. A snapshot section that names the volume puts the reference back on a rollback, so we delete that snapshot or make a note of it. We never delete the volume, and we don't use `qm set --delete` or `qm disk unlink` for this, because either one can leave an `unusedN` entry that makes PVE delete the volume when it is removed. Guests outside our namespace that share a disk among themselves don't raise it, and `scripts/disk-audit` lists these volumes before we upgrade. See [An operation fails with an allocation audit refusal](docs/troubleshooting.md#an-operation-fails-with-an-allocation-audit-refusal).

- A `create_vm` that a 0.8.0 or 0.8.1 CPI admitted, and that is still in flight when we upgrade, can fail every retry under this release with `existing VM generation cannot be resumed: caller intent or journal authority differs`. That happens only when the call's arguments carry a `PVEAPIToken=` or `PVEAuthCookie=` value under a key whose name doesn't already mark it as secret, such as a plain `env` value. 0.8.0 and 0.8.1 masked no such value in the argument trees the allocation journal fingerprints, and this release does, so the retry's fingerprint no longer matches the one they stored. We avoid it by letting running deploys finish before the upgrade. A generation caught this way stays open and keeps charging capacity, so we read it with `storage-journal audit --summary` and follow [A crash-abandoned allocation keeps charging capacity](docs/troubleshooting.md#a-crash-abandoned-allocation-keeps-charging-capacity), and we never delete the VM it holds to clear it. A `create_disk` retry isn't refused, because it opens a new allocation, so the earlier record stays where it was and keeps charging.

- `storage-journal cleanup` now keeps a VM's ephemeral volume whenever `delete_vm` would have kept it, which is when the VM carries the `retain_ephemeral_on_delete` tag and its CID reached the Director, and whenever the record shows the retention already started. Such a cleanup now stops at `vm_deleted_retained`, prints `{"state":"vm_deleted_retained"}`, and exits 0. It used to destroy the volume with the VM and print `cleaned` in one call. A second cleanup of the `vm_deleted_retained` record deletes the retained volume and prints `cleaned`. A create_vm rollback never keeps the volume.

- Every managed VM destroy now refuses while one of the VM's drives carries a stable-ID serial, because a drive like that holds a disk the CPI parks rather than destroys. The refusal reads `VM destruction would take the disk on <slot>, which carries a stable-ID serial`. The Director sees it with `VM disposal failed:` in front and doesn't retry, `storage-journal cleanup` prints it after `cleanup_resource_cleanup:`, and the record waits in `reconciliation_required` with the VM and its volumes untouched. A `cleanup` that stops at a retained parker whose provenance no longer names the retained volume now says `retained parker identity differs`, where its `allocation decision refused` line used to say `unclassified error`. A retention whose stable ID already sits on another holder says `ephemeral retention token already identifies a live resource; audit recorded retention` there too, and one whose recorded parker can't be read for any reason but being gone refuses with `a retention parker the record names could not be read`. A `cleanup` that now runs a retention can run out the parker lock wait the way `delete_vm` can. It then destroys nothing, leaves the record observed, exits 1, and prints `a parker lock wait ran out before the disk moved, so nothing was destroyed; run cleanup again once the lock is free`, and the same cleanup finishes once the lock is free.

### Fixed

- A `detach_disk` of a disk with a stable ID no longer removes another disk's drive-option overrides from the VM. The cleanup after the move to a parker removed the VM's overlay entry under the disk's `create_disk` volume name. A move renames that volume, so a legacy disk created later can carry the same name and keep its overrides under it. The cleanup now reads the VM once and leaves out any name another disk still holds on a slot or an unused entry, the way the detach tail already does. When a snapshot defers the park, the disk's own unused entry keeps its old name, and the disk's entries under that name still come off. When the read still fails after its retries, we leave the entries under any name another disk could hold, remove the rest, and log a warning that names the VM, the disk, and the entries we left in place. The same cleanup now runs when `attach_disk` or `create_vm` moves a stranded disk off another VM's unused entry, because that move removed the same entries with no check. The troubleshooting guide explains how to remove those entries by hand in [A detach left a disk's notes on the VM it left](docs/troubleshooting.md#a-detach-left-a-disks-notes-on-the-vm-it-left).

- A persistent disk whose move failed before PVE answered no longer stays stuck in `reconciliation_required`. The CPI records a move step as planned before it sends the move, and when no answer comes back it can't tell whether PVE started a task, so every later call on the disk refused on that step and no command could settle it. The CPI now settles such a step as a move that never started, in whichever call touches the record next, which can be a rerun `detach_disk` or `attach_disk`, a `delete_disk`, `resize_disk`, or `snapshot_disk`, the disk attach in `create_vm`, the disk preservation in `delete_vm`, or `storage-journal adopt`, `cleanup`, or `finalize-cleanup`. It waits 10 minutes from the record's last save first, and a call inside that wait refuses and says when the wait ends. Then it lists the active move tasks on the step's node and on the node the VM runs on now, and only after that does it check that the VM still names the volume with no pending change, that the volume there is still this disk, that the volume still exists, that no other guest carries the disk's serial, and that no parker names the volume. The name alone can't prove the volume is this disk, because PVE gives a freed name to the next volume it renames onto the same VM. So a bus slot that names the volume has to carry the disk's serial and no other, and for a volume on an unused entry, exactly one parker has to keep its record of the transfer, and none of that parker's disk keys may hold a volume named for the parker with no serial. The step settles only when no move task for the VM is active and every check passes, and otherwise the refusal adds `its move could not be settled as never started because` and names the check that failed. The settlement only reads, so it never changes anything on PVE. Listing the tasks needs `Sys.Audit` on `/nodes/<node>`, and a token without it refuses with a line that names that grant. When an earlier release already removed the parker's record of the transfer, we first check that no parker holds a volume named for it with no serial, and then we put the volume back on the VM with its serial before we rerun. See [delete_vm refuses to destroy VM with attached unused disks](docs/troubleshooting.md#delete_vm-refuses-to-destroy-vm-with-attached-unused-disks).

- A `delete_disk` no longer fails for good on a disk whose detach needed a second attempt. When a `detach_disk` failed after the CPI had taken the disk off its VM, a later call finished the move to the parker, but it returned before it removed the disk's allocation entry from the VM the disk left. That VM kept the entry in its description. Once the Director orphaned the disk while the VM still existed, `delete_disk` deleted the volume, found the entry, and left the allocation in `reconciliation_required` with an error that isn't retriable. When a `detach_disk`, `attach_disk`, `delete_disk`, or the disk attach in `create_vm` finds that the move to the parker has landed, the CPI now removes the allocation entry, the attached-disk entry, and the drive-option overlay from the VM that the move took the disk off. That holds whether the move finishes in the first `detach_disk`, in a later one, or in a transfer that one of those calls resumes. `update_disk` doesn't run this step, so when it's the call that resumes the transfer, the entry stays until the next of those calls reaches the disk.

  A record that 0.6.0 through 0.8.1 left in this shape heals on its next `detach_disk`, `attach_disk`, `delete_disk`, or `create_vm` that attaches the disk, as long as the disk hasn't been attached anywhere since. The CPI finds the VM through the parker's record of that move. Each of those calls removes the entry before it moves or deletes the disk, and a failure there leaves the disk on the parker with its volume in place. When the disk has been attached elsewhere since, or the entry sits on a VM the disk was attached to before its last move, a retry of `delete_disk` removes the entry once the volume is gone. A retry does the same for a record that is already in `reconciliation_required`. The item below on stale notes describes that heal.

  When the CPI never sent the removal, the call comes back retriable. That includes a removal the CPI held back because one of its own reads just before the write failed while the request was still live. The call also comes back retriable when PVE answered that it refused the removal and a fresh read shows every note still there. In both cases the CPI leaves the allocation ready for the Director to retry, the way it does after a clean lock timeout, instead of leaving it in `reconciliation_required`. A `create_vm` also disposes of the VM it built for that attempt. Where the CPI can't prove that its removal changed nothing, the allocation ends in `reconciliation_required`, apart from the `delete_disk` lock timeout that we describe below. That covers four cases. The first is a removal whose outcome isn't known, because the connection may have dropped, the request may have ended, a gateway may have answered for PVE, or PVE may have failed with a 500 that doesn't say the VM is locked. The write may have landed, so that call fails with an error that isn't retriable. The second is a refusal that PVE gave and that a fresh read can't confirm, either because the read shows a note gone or because the read fails. The third is a removal that PVE accepted and whose readback then fails. In a `detach_disk`, `attach_disk`, or `delete_disk`, that call fails with a retriable error and the record goes to `reconciliation_required`, and the retry of that same call reads the VM, finds the entry already gone, and goes on. In a `create_vm`, the failure isn't retriable, and the VM's allocation stays in `reconciliation_required` with its handoff step planned. The recovery in [A parker lock wait runs out](docs/troubleshooting.md#a-parker-lock-wait-runs-out) covers that case. The fourth is a call that had already moved the disk, which can be a `detach_disk` that parked it, or an `attach_disk` or `delete_disk` that resumed its move onto the parker. That call fails with a retriable error, and the Director's retry of the same call reads the source VM again and removes the entry, so the record heals without us, unless the removal itself went unanswered, which leaves its step planned as in the first case. The one exception is a `delete_disk` that removes the entry and then runs out of time waiting for the parker's lock hands the allocation back to the Director, as any clean lock timeout does, instead of leaving it in `reconciliation_required`. The removal changed nothing but the VM's notes, so the timeout is still clean.

  The CPI builds the VM's new description from one read and sends it in one write with that read's digest, so when another disk's call changes the description in between, PVE refuses the write, and the CPI reads the VM again, up to three times, rather than overwrite that change. Once PVE accepts the write, the CPI checks only that the notes it removed are gone, so a change that another call makes to the description right after doesn't fail this one. A read that fails comes back retriable, unless a fresh lookup shows that the VM is gone. A VM that still names the volume on a slot, an unused entry, or a pending change fails the call with a retriable error. When a recorded move gave the volume a new name, PVE can hand the old name to another disk, so a VM that holds a disk under the old name doesn't stop the removal. No name that the VM still holds on a slot or an unused entry is removed from its notes, so that disk's notes stay as they are. An entry that names some other volume, with no recorded move that links the two, stays where it is, and the CPI logs a warning. A read that carries no digest fails the call with a retriable error, and the CPI sends no write. So does a read that shows a lock on the VM, such as the one a backup leaves, because PVE would refuse the write until the lock is gone. When PVE refuses the write for a stale digest, with a 4xx status, or with a 500 that says the VM is locked, the CPI settles the refusal only when a fresh read shows the VM still carrying every note the write meant to remove.

  The removal doesn't take the VM's own lock. So a writer that rewrites the VM's whole description without a digest, such as `set_vm_metadata`, can still write back an older copy that has the entry in it. When that happens before the call's completion audit, the call leaves the allocation in `reconciliation_required`, and the audit's evidence line names that VM. We recover the allocation the way [A disk delete is refused after its volume is already gone](docs/troubleshooting.md#a-disk-delete-is-refused-after-its-volume-is-already-gone) describes, by recreating that VM and then running the call again.

  When the lifecycle guard finds a stale digest on a description-only write before it sends it, the guard no longer records a write that was never sent. One such write is the one an attach makes to put the allocation entry on its VM.

  `storage-journal cleanup` now also settles a configuration step that an `attach_disk` or the disk attach in `create_vm` left planned, on the same attestations, task evidence, and ownership proof it uses for the steps that `detach_disk` and `delete_disk` leave. A planned write from `attach_disk`, `detach_disk`, or `delete_disk` that turns a parker's protection back on is the exception. Cleanup refuses it until the parker reads protected, and the refusal gives the `qm set` command that puts protection back. Cleanup used to admit such a write from `detach_disk` or `delete_disk` and then refuse it at a later check, with a message that didn't give the `qm set` command. The refusal for a parker that isn't on its recorded node now says that the parker wasn't found on that node, rather than that it no longer exists, because the parker may only have moved. A parker that moved to another node settles the step once we migrate it back. When a parker is gone or has lost its `bosh-parker` tag, the protection restore step stays planned, no call settles it, and the record stays in `reconciliation_required`. The troubleshooting guide says how we tell the two cases apart, and it warns against putting the tag back on a VMID that PVE may have given to another VM.

- A `delete_disk` no longer leaves a disk in `reconciliation_required` for good when another volume has since taken the disk's old name. When the CPI moves a disk onto a parker, PVE gives the disk a new name, and the old name is free for the next volume that PVE or an operator puts on that VM. If that volume has no stable-ID serial, as with a disk an operator attached by hand or a legacy disk that 0.6.0 created, the completion audit counted it as the moved disk's. So `delete_disk` deleted the moved disk's volume and then refused with an error the Director can't retry past. The audit now stops counting a volume under the old name as the disk's when a VM holds that volume on a disk slot and the journal holds an observed move that took the disk off that name and landed it under another one. On shared storage a VM on any node counts, including one that has migrated since the move, and on node-local storage only a VM on the node where the move ran counts, because only that VM sees the volume the move renamed. The audit decides this from every VM that holds the volume, after it has read the storage definitions. It applies the rule the same way to a VM's drives, to the storage listing, and to its checks for a volume that two VMs reference or a disk with two holders, so a conflict that comes from anything else, such as a second volume with the disk's serial, still refuses. Only a disk's record gives a name up, and a VM's record keeps every name its steps carry, as before. A later move that brought the disk back under the old name, or one whose outcome isn't known, keeps the old name the disk's, as before. The other volume, its slot, and its notes stay exactly as they were. An earlier release could also leave the disk's own allocation entry under the old name on the VM the disk was moved off, and that entry alone kept the record refused. When that same VM now holds the other volume on a disk slot, and either the storage is shared or the VM sits on the node where the move ran, the next `delete_disk` removes the entry after the audit's first pass and before its second, and ends `deleted`. It also removes any attached-disk note that names the disk's CID from that VM, unless the note is filed under a volume the VM still holds. It does that in one write that carries the digest of its read, so PVE refuses it rather than overwrite a newer description. A refused write, a lost answer, or a failed read comes back retriable, and the next call reads the VM again. Notes that name any other disk stay as they are. When a different VM holds the old name, or no VM holds it, the next `delete_disk` removes the entry too, as the item below on stale notes describes. The heal doesn't run when the old name is also the disk's birth name and another VM holds it on a slot with no serial, because the identity check refuses that delete first. On node-local storage, when the VM that holds the old name has migrated to another node since the move, this release leaves the record refused, and a later change heals it. A volume that sits under the old name only as an unused entry still counts as the disk's, because it could hold the disk's own data, and the troubleshooting guide says how we sort it out before we rerun the delete.

- A `delete_disk` now clears our stale notes from a VM that doesn't hold the disk's volume. An earlier release could leave a disk's allocation entry, its attached-disk note, and its drive-option overlay in the description of a VM that the disk left through a move or a reattach, or of the VM that the disk's record still names. Once the volume was gone, the completion audit counted those notes as the disk's and refused every `delete_disk`, so the allocation stayed in `reconciliation_required` until we recreated that VM. A VM holds the disk when one of the disk's names appears in its current config, in its pending changes, on an unused entry, or in one of its snapshots, or when it has a drive with the disk's serial. Before it acts on the audit's result, `delete_disk` now removes those notes from every VM that carries them and holds the disk nowhere, as the audit's first run, the one before any removal, finds them. It does that only when that run found no VM holding the disk and no volume of the disk on any storage, so while any VM still holds the disk, every VM keeps its notes. The one exception is the disk's old name on a disk slot, when a recorded move took the disk off that VM under that name. That holds whether the slot is in the VM's config or in one of its snapshots, because PVE may have given the name to another disk since. On node-local storage, a VM that holds that name in its config and has migrated off the node where that move ran isn't an exception. The heal checks the audit's first run before it reads any VM, and that check fails for such a VM, so every VM keeps its notes. A VM that holds that name only on an unused entry still holds the disk. The CPI also reads every one of those VMs before it writes to any of them, so a hold that only one VM's read turns up, such as a snapshot, keeps the notes on all of them. The CPI removes only an allocation entry that is filed under the disk's own stable ID and names its allocation, namespace, backing, a node the record names, and one of the disk's names. With that entry it removes the overlay filed under the stable ID and the attached-disk notes that name the disk's CID, except any note filed under a volume the VM still holds. Notes that belong to any other disk stay exactly as they are, even when that disk's volume has taken our disk's old name. The CPI makes the removal in one write that carries the digest of its read, so PVE refuses it rather than overwrite a newer description. A failed or malformed read, a read without a digest, a VM that has gone since the audit, a refused write, or a lost answer comes back retriable, and the next call audits and reads the VM again. While a step of the record's active attempt has no outcome yet, as after an attach that was cut off, every VM keeps its notes, and the delete still refuses and names that step. A step of an attempt that the journal has already closed doesn't count, so a disk that `create_disk` made on a retry, after PVE rejected the first request at validation, heals like any other. A record that is already in `reconciliation_required` heals on its next `delete_disk` as well, so `bosh clean-up --all` or `bosh delete-disk` closes it.

- A parker now keeps a stale transfer record past the grace hour when the record's own slot holds a landed volume that nobody has claimed. When a move lands after the answer to it is lost, PVE has already renamed the volume onto the parker, but the serial that ties it to the disk's stable ID was never written, and the old volume the record names is gone. The record is then the only link to the disk, and the next park on that parker used to collect it an hour later. The record is now kept while its slot holds a volume named for the parker, in both the current and the pending view, with no stable-ID serial, and while no other record on the parker names that volume. Every other release rule is unchanged. A kept record counts toward the parker's description budget like any other, so a parker that fills up routes new parks to another one, and a mistaken keep costs description bytes and never a disk.

- `update_disk` on a parked disk no longer writes a parker description that is past the size budget every other provenance write keeps. The option overrides ride in the parker's description, and every other writer stops short of the PVE limit by a reserve. The override write didn't, so on a nearly full parker it could eat the reserve, or it could cross the limit itself and fail with a PVE message that says only that a string was too long. The call now refuses before it writes anything, with a retriable error that names the parker's VMID, the node, and the byte count, and it wraps the same provenance-full error the park path already uses. It doesn't collect any of the parker's other records to make room, so they stay as they were.

- Every audit-gated refusal now says what the audit found. `create_vm` used to fail with one fixed line, "VM allocation admission requires complete VM provenance inspection and consistent retained history", and about a dozen other gates in `create_disk`, `delete_vm`, `delete_disk`, the retry paths, and cleanup had fixed lines of their own. Each one now opens with the operation, the counts, and the first finding, because `bosh tasks` keeps only about the first 75 characters of a CPI error, for example `create_vm refused: 2 audit conflicts; VM 4626 on pvupvecf102, recorded pvupvecf101 (node_mismatch)`. It lists up to three findings, taking one for each VM or volume before it repeats any. It then says how many more of each kind there are and which VMs and volumes they name, points at the runbook section, and ends with the exact command that prints the full report on that host. On a Director that command is `sudo -u vcap /var/vcap/packages/pve_cpi/bin/cpi storage-journal audit --summary --config /var/vcap/jobs/pve_cpi/config/cpi.json`. The CPI runs there as `vcap`, the journal's owner, but we read the refusal as another user, so a CPI running from `/var/vcap/` always adds `sudo -u` with the journal owner. Under `bosh create-env` the command carries `sudo -u` only when the journal belongs to someone other than the user the CPI runs as. The CPI also logs the full report once, as an Error record named `allocation audit gate refused`, which `bosh task <id> --cpi` shows. Each finding names its allocation, VMID, recorded and observed nodes, and volume or storage, along with a reason code such as `node_mismatch` or `backing_changed`. Where an error is involved, a finding carries only a safe description of it, such as an HTTP status with PVE's own message, never raw transport text. Director messages, CLI output, and the CPI's logs now share one set of masking rules, which covers `PVEAPIToken=` and `PVEAuthCookie=` values as well as credentials inside URLs. `create_disk` keeps its `storage allocation admission` lead, and the `pve-cid storage-plan` diagnostic now lists up to three historical conflicts and issues instead of only counting them. A `create_disk` retry used to drop the reason it refused, and it now names the failed audit, the leftover rejected volume, or its audit findings. A `detach_disk` that cannot rewrite a moved disk's provenance names the audit's reason for refusing the move.

- A `create_vm` or `create_disk` no longer fails because another create was running at the same moment. The admission audit read the journal once, before it scanned the cluster. When the other create wrote its record and cloned its VM or made its volume during that scan, the audit found that create's allocation with no record behind it and refused with `carries unknown allocation` or `(not_in_step)`. A deploy that started compile VMs in parallel could fail this way on a clean cluster. The audit now reads the journal again after the scan and accepts a sighting when the record it finds names that VM or volume in its active attempt. It also lists the cluster's VMs again when one VM's configuration can't be read, and it skips a VM that has been deleted since the first listing instead of refusing with `configuration could not be inspected`.

- Two VMs that raised the same kind of conflict no longer collapse into one line. The conflict strings named nothing that told them apart, so deduplication dropped all but one, and an audit of two migrated VMs reported a single disk-provenance conflict. Every conflict now carries its own identifiers.

- `cpi storage-journal` and `cpi provision-journal` no longer swallow their errors. About twenty-five failure lines used to drop the error in hand, and five output failures exited 1 with no text at all. Each one now prints its message followed by a safe description of the cause. A journal owned by another user prints `journal <path> is owned by <user>; rerun as that user:` and the exact command, which is what plain `sudo` on a Director now reports instead of an opaque failure. A missing journal directory, a namespace that was never enrolled, and a config file that is missing or unreadable each get their own message, and a config that fails validation prints no configuration values. When a config lacks a namespace or a journal directory, the CLI says which one is missing. When `initialize`, the recovery actions, or `resolve-missing-vm` refuse, they now print one `precondition failed:` line for each precondition that failed, followed by an `audit findings:` summary. A refused `adopt`, `finalize-cleanup`, or `cleanup` now carries its reason after its class, as in `allocation decision refused (identity_or_audit_evidence: adoption requires a ready_to_return record, or a disk in reconciliation_required, with the exact CID)`. When an audit gate refused, the reason is the gate's summary. For the CPI's own refusals, such as a VM or a pending allocation found outside its recorded node, the reason is the CPI's text, and for anything else it is a safe description like an HTTP status with PVE's message.

- Explicit cleanup of a retained VM no longer fails when it finishes. The cleanup records its disk deletions with the retention parker's VMID, and the allocation audit read that parker as the VM's own guest and reported that it lacked the allocation marker. The audit now treats those steps as naming the parker, so a record that 0.8.0 or 0.8.1 left stuck this way finishes when the cleanup is retried.

- Two journal-managed operations that want the same cluster lock no longer leave the slower one's allocation needing reconciliation. When a deploy runs with `max_in_flight` above 1 and two instances move persistent disks out of the same parker at once, both requests try to create the parker's `bosh-lock-vm-<vmid>` sentinel pool, and PVE refuses the second create because the first request holds the lock. The allocation guard read that refusal as an uncertain outcome, so it marked the losing allocation `reconciliation_required`, and the deploy failed with `requires reconciliation at lifecycle attach_disk Pool.CreatePool` instead of waiting its turn. The guard now accepts PVE's exact refusal for a `bosh-lock-` sentinel as proof that nothing changed, but only after it reads the sentinel back and finds that it does not hold the request's own claim. It then settles the journal step as observed and hands the refusal back to the lock code, which waits for the holder as it always has. A release or a steal that finds the sentinel already gone is settled the same way. A release whose readback finds that a waiter has already created its own sentinel still counts as an observed delete, because the guard reads the sentinel's claim just before it deletes it and the waiter's claim differs from that one. A create that PVE accepted stays observed even when a stealer removes or replaces the sentinel before the readback. The lock code now reads its claim back after every create it makes, not only after a steal, so a create that was displaced waits for the new holder instead of entering that holder's window. Every other pool failure still requires reconciliation. The bug has been present since 0.6.0.

- The CPI now recognizes the text PVE sends when a pool already exists, which is `create pool failed: pool '<id>' already exists`. The check it used before expected the text without the `create pool failed:` prefix, so it never matched a live cluster. As a result, when two `create_vm` calls created a deployment's resource pool at the same moment, the slower one's allocation ended up in `reconciliation_required`. That case now resolves as the concurrent create it is.

- A journal-managed `create_vm` that takes the anti-affinity lock no longer fails when it releases that lock. The lock is taken when `pve.placement.anti_affinity.use_ha_rules` is on and `pve.cluster_lock_mode` is `pool`. The allocation guard refused the sentinel pool's delete as an unplanned mutation, which failed the `create_vm` after the VM was built and left the sentinel behind until its TTL ran out. The guard now admits that delete for an anti-affinity sentinel, `bosh-lock-aa-<group>`, and for no other pool, including every other sentinel. When that delete or the sentinel's create loses its answer after the VM's own work has begun, `storage-journal cleanup` now settles the planned pool step that the failure leaves behind and then closes the VM allocation the way it closes any other, while a record that stopped before any VM write keeps its attested cleanup route. Settlement reads the VM's own lock pool, and `bosh-lock-aa-<group>` too when the record stored its instance group. A record stores that group only when the VM resolved a deployment pool, so for a VM without one, the read only checks that PVE answers, and the step settles because neither pool it could have meant holds anything the allocation owns.

- Every journal-managed operation that takes a parker's lock now waits up to 180 seconds for another request's window, up from 15. That covers `attach_disk`, `detach_disk`, `delete_disk`, the `create_disk` park, the disk attach inside `create_vm` for a disk in `disk_cids`, the disk preservation and the ephemeral retention inside `delete_vm`, and a `storage-journal cleanup` of a disk or of a retained ephemeral volume. The 180 seconds is the lock's TTL, and a holder's window can run for most of it, so the old wait gave up on windows that were working normally. The wait is one budget for the whole queue, not a fresh allowance for each holder, so a request at the back of a long queue of instances sharing one parker can still run out. Some of these calls fail cleanly when the wait runs out before they changed the disk. That requires the lock wait to be the only failure, with every journal step observed, no disk mutation admitted before the wait, and the guard never tripped. The drive-option override note that the CPI writes onto the receiving VM before the wait does not count as a disk mutation, because the note plays no part in deciding where the disk is. `attach_disk`, `detach_disk`, `delete_disk`, the `create_vm` disk attach, and the `delete_vm` disk preservation fail cleanly in that case, both for disks the journal owns and for older stable-ID disks it does not. The call fails with a retriable error, the disk stays where it was, and the allocation is not marked for reconciliation. A wait that the request itself ends now exits the same clean way when nothing else was admitted, whether the request's deadline stops the wait with the timeout 15 seconds early or a cancellation interrupts it. The `create_disk` park and the `delete_vm` ephemeral retention still end in `reconciliation_required` after a timeout. The park has already created a volume that the next deploy's `create_disk` does not reuse, and the retention writes the volume's serial before it waits. A `storage-journal cleanup` of a disk whose wait runs out before it changed anything now leaves the record as it was and returns a retriable error, so we rerun it once the other request's window closes, and the CLI now gives `cleanup` long enough for a full 180-second wait and the window after it. A cleanup that touched the disk before its wait, or that removes a retained ephemeral volume, still ends in `reconciliation_required`. Any other failure still requires reconciliation too. A `create_vm` whose disk attach ends that way leaves its VM record with one planned persistent disk handoff step. An attested `storage-journal cleanup`, run with `--authority-id`, `--previous-writer-fenced`, and `--remote-tasks-settled`, now closes that record once the disk's own record is settled, and it parks the disk again first when the disk is still attached to the VM. The Director retries only `create_vm` within a task, so a timed-out `create_vm` is retried in the same task. Before the timeout goes back, `create_vm` disposes of the VM it built, preserving any disk it had already attached, and closes the VM's allocation, so each retry starts a new allocation and builds a fresh VM. With `pve.debug.keep_failed_vms` on, `create_vm` keeps the VM instead, and the next try resumes it. When fallback attempts are configured, `create_vm` instead disposes of the timed-out attempt's VM, preserving any disk it had already attached, and places a new one. If that disposal fails once it has begun, for example because preserving an attached disk runs out the same wait, the VM allocation requires reconciliation and the error is not retriable. By then the VM may be stopped, out of HA, or missing a disk, so resuming it as a create would not be safe. A later `create_vm` for the same agent refuses to resume it. If the disposal is refused before it begins, for example because the allocation audit is incomplete, the VM and its allocation stay as they were and the next try resumes them. When every one of the Director's tries runs out, five by default, no guest or charging record is left behind. A timed-out `attach_disk` or `detach_disk` fails the deploy task instead, and running the deploy again reissues the call against a disk that is already back in its earlier state. A deploy never deletes a persistent disk, because the Director orphans it instead, so `delete_disk` comes only from orphan cleanup, and the Director's scheduled orphan cleanup calls it again every 30 minutes. A timed-out `delete_vm` leaves its VM allocation with every step observed in the same way, and the next `delete_vm` for that VM resumes it. A `delete_vm` that nothing calls again, such as one whose error `bosh delete-deployment --force` ignored, leaves its record charging until we run `cleanup` on it. A `create_disk` whose park runs out still requires reconciliation, because it has already created a volume, and the next deploy's `create_disk` creates a new volume under a new allocation instead of reusing it. Callers outside the allocation journal keep the 15-second wait, and the lock's TTL is unchanged. See [Multi-storage allocation requires reconciliation](docs/troubleshooting.md#multi-storage-allocation-requires-reconciliation).

- Two requests that steal the same expired cluster lock no longer both end up holding it in the ordinary case. A lock is stolen when its holder crashed or overran its TTL, and every request waiting on it at that moment judges it expired, which the 180-second parker wait makes common. A stealer now reads the lock pool again immediately before its delete and gives up when the claim has changed in any way, and a journal-managed delete checks the claim once more right before it calls PVE. If a steal takes longer than two seconds from that read to the end of its delete, it gives up instead of creating the pool again, and the next poll starts over. The parker lock and the anti-affinity lock also pause for two and a half seconds after every create, a steal's or an ordinary one, and confirm their claim a second time before they take the lock, so each of those acquires is about two and a half seconds slower. PVE has no conditional delete, so one window remains for those two locks, and two holders can overlap only when a stealer stalls between its last read and its delete for longer than that pause. The per-VMID lock that `set_vm_metadata`, `set_disk_metadata`, `delete_vm`, and stemcell reference counting take skips the pause, because a double holder there races two metadata writes, where the last one wins, or two picks of the same VMID, which PVE refuses. For that lock we accept that a stealer's late delete can still let two holders overlap. When a request releases a lock, it now leaves the lock pool alone if its claim is within a few seconds of expiring, or if the pool's comment names no owner or no expiry, and a later request takes the pool over once the claim lapses. We now measure a parker window's deadline from the claim's recorded expiry, and the window leaves 35 seconds instead of 30 for putting the parker's protection back, which covers the restore's full retry curve.

- A cluster lock acquire whose read of its own new lock pool fails no longer leaves that pool standing for a whole TTL, and a parker window no longer runs unserialized after such a failure. The acquire reads the pool again on the lock's poll cadence until its deadline, and it takes the lock as soon as a read shows its claim. The retries stay inside the acquire's existing wait. If no read answers by the deadline, the acquire fails with a retriable error saying the lock state is unknown. On the way out it reads the pool once more, and it deletes the pool only when that read proves the pool still carries its own claim, well short of that claim's expiry. That final read and the delete after it have 10 seconds of their own, so the acquire can return up to 10 seconds after its wait ends. The delete expects the comment that read returned, so a journal-managed delete checks the claim right before it calls PVE. A parker window treats the unknown state the way it treats a timeout, so the call fails instead of running the window.

- A journal-managed disk operation whose parker lock ends in that unknown lock state now settles its allocation the way a clean lock timeout does. That covers `attach_disk`, `detach_disk`, `delete_disk`, the `create_vm` disk attach, and the `delete_vm` disk preservation, under the same conditions a timeout needs. When the read on the acquire's way out proves the lock pool ours and PVE answers the delete, every step is observed, so the allocation goes back to `ready_to_return`, or to `adopted` for a disk we had adopted, and the Director gets a retriable error. When that delete does not answer, its step stays planned and the allocation is left in `reconciliation_required`. The next `attach_disk`, `detach_disk`, or `delete_disk` for the disk, such as the one a rerun deploy makes, reads the lock pool back, settles that planned delete step, and is admitted. Our old claim still stands until its TTL passes, so that call can wait on it and time out cleanly before a later one completes. The `create_vm` disk attach ends the way a timed-out one does, so `create_vm` disposes of the VM it built before it returns the retriable error, and with `pve.debug.keep_failed_vms` on it keeps the VM instead.

- A journal-managed request whose allocation needs reconciliation no longer leaves its parker lock standing for everyone else. Once a write inside a parker window fails in a way the CPI cannot account for, the allocation guard refuses every further write, and that used to include the release of the request's own lock pool, so every other request on that parker waited out the full 180-second TTL. The release now goes through when the guard's read right before the delete finds exactly the claim this request created, and any other claim, or a read that fails, still leaves the pool alone. A request whose lock create the guard refuses before it reaches PVE, because its allocation already needs reconciliation or the request has ended, now fails at that point instead of running the parker window without the lock.

- Every cluster lock owner now names the host, the CPI process ID, a random number drawn once per process, and a per-process sequence number, as in `set_vm_metadata/4242@director-0/1234-9f2c1a7e-1`. That covers the per-VMID locks that `set_vm_metadata`, `set_disk_metadata`, `delete_vm`, and stemcell reference counting take, the parker lock, and the anti-affinity lock. The parker lock's owner used to name only the purpose, the process ID, and the parker's VMID, so two requests in one CPI process could stamp identical claims. The per-VMID locks named only the purpose and the VMID, so two requests with the same purpose for the same VMID could stamp identical claims even from different processes or different Directors.

- A record that the old lock bug left in `reconciliation_required` can now be recovered without an operator guessing at it. Such a record's last step is a planned `bosh-lock-` pool create, for example `lifecycle_attach_disk_Pool_CreatePool`, and every refusal treated that step as unsettled, so a rerun deploy, `adopt`, and `finalize-cleanup` all refused a disk that was healthy and parked. A lock pool is an empty marker that never holds anything the allocation owns, so the CPI now settles such a step with a fresh read of the lock pool named for each VM that the steps of the record's active attempt target. When each read answers exactly, either with the pool and its claim or with PVE's own missing-pool answer, the step is marked observed in the journal, and nothing on PVE changes. A claim that the failed request left behind stays until its TTL passes and the next request takes it over. A read that fails or answers loosely leaves the step planned. Every call that readmits the record does this first. For a disk, those calls are `attach_disk`, `detach_disk`, `delete_disk`, `resize_disk`, `snapshot_disk`, the disk attach inside `create_vm`, and the disk preservation inside `delete_vm`, and a rerun deploy makes the next `attach_disk` or `detach_disk`. For a VM, the call is `delete_vm`, and for either kind, `adopt`, `finalize-cleanup`, and the `cleanup` precheck do it too. Because the Director's scheduled orphan cleanup retries a failed `delete_disk` every 30 minutes, an orphan whose delete the old bug refused is now settled and deleted by that cleanup with no action from an operator. `adopt` now also accepts a disk in `reconciliation_required` that still has its CID, after it observes the disk where its record says, and its refusal now reads `adoption requires a ready_to_return record, or a disk in reconciliation_required, with the exact CID`. Every unsettled-evidence refusal now names a step with its step name and kind instead of asking to "reconcile task completion". Most name the first unsettled step, and the refusal for a step that changed or appeared after cleanup admitted the others names that step instead. An `attach_disk`, `detach_disk`, or `delete_disk` refused that way now names its own operation when no lock step or parker protection write is still waiting on a read, as in `attach_disk has unresolved mutation evidence; step attempt-0-step-4 (lifecycle_attach_disk_Nodes_UpdateQemuConfig) is planned`, where it used to say `cleanup has unresolved mutation evidence` for a call that was not a cleanup. When one is still waiting, the refusal opens with `lifecycle` instead. `storage-journal cleanup` now names the step it refused on too, after its usual `cleanup refuses unresolved allocation or asynchronous mutation` refusal. When that step is a lock step, or a parker protection write that settlement left planned, the refusal also says why the step is still planned, such as the reason its lock pool read failed. See [Records left behind by the old lock bug](docs/troubleshooting.md#records-left-behind-by-the-old-lock-bug).

- A record that a crash left with a planned lock step is now settled by readback whatever state the crash left it in, the same way as a record in `reconciliation_required`. A crash between a step's intent and its outcome leaves the record in the state it already had, such as `observed` for a disk whose `attach_disk` or `detach_disk` stopped right after it planned the lock step, or `planned` for a `create_disk` park that stopped there. The journal accepted the settlement's write only on a record in `reconciliation_required`. So every journal-managed disk operation on such a record, and every `storage-journal adopt`, `finalize-cleanup`, and `cleanup` on it, failed with `allocation requires reconciliation`, even though the record was not in that state. No `storage-journal` action could move it there either. The journal now accepts a write that only marks planned steps of the active attempt observed and adds their volumes, with the record's state, reason, and verifications unchanged. Every other write from a request that reopened the record still needs the record in `reconciliation_required` or a fresh verification first. When the journal refuses a settlement anyway, the error now names each step it was settling.

- A persistent disk that has been replaced twice no longer blocks every `create_disk` and `create_vm` in the namespace. When we detach a disk and park it, PVE frees its name, such as `vm-2353-disk-1`, and gives that name to the next disk the VM receives. The allocation audit counted a volume as a holder of every record that had ever carried its name, so the parked disk's record appeared to have two holders, and admission failed with `disk allocation <id> has multiple active holders or duplicate stable tokens`. We now decide which allocation a volume belongs to from the drive's serial first and the VM's disk provenance second, and we fall back to the record's volume names only when neither one identifies the volume. While a VM holds the reused name, the same rule keeps that name out of the evidence that absence proofs read, so deleting or cleaning up the parked disk no longer trips over a stale sighting there. A reused name that no VM holds, including one left only as an `unusedN` entry, still counts as the old record's, so those absence proofs keep refusing until the name is gone. A true duplicate is still a conflict, whether it is one serial at two holders, one allocation at two holders, or an unidentified volume at a name the record carries. The bug has been present since 0.6.0. The audit also raises a new conflict whenever two VMs reference one of our volumes at once, on shared storage or on the same node for node-local storage, because both of them can write the disk. A volume is ours when its name carries our namespace, when a live record names it, or when a VM's disk provenance or drive serial ties it to one of our allocations, and the conflict counts every VM that references such a volume, including one that BOSH does not manage. Guests outside our namespace that share a volume or a passed-through device among themselves raise nothing, so a shared-disk cluster or a stopped copy of a VM elsewhere on the cluster does not block our deploys. CD-ROM entries are exempt, since many VMs mount one ISO.

- The per-VMID lock that `set_vm_metadata`, `set_disk_metadata`, `delete_vm`, and stemcell reference counting take now stands for 25 minutes instead of 30 seconds. `set_vm_metadata` holds that lock while it reconciles the VM's resource pool, and the reconcile retries its pool lookup, its pool create, and its move with backoff, so on a busy cluster it could still be running when the 30 seconds ran out. Another CPI process could then take the lock over while the first was still inside it, and two metadata writes to one VM could interleave. The new TTL covers the worst case, which is about 22 minutes when every retry sleeps its longest backoff and every call takes 30 seconds, and when we lengthen a backoff curve or the transient attempt budget under `pve.retry`, the lock claims a longer TTL to match. The CPI still never cuts the lock's work short, because a write stopped partway has an unknown outcome, and the retry loop around it can't tell a write that landed from one that was lost. The cost is that a CPI process that dies while it holds the lock blocks metadata writes to that VM until its claim expires. When a call gives up waiting for the lock, its error now quotes the holder's claim in full, with the owner token that names the operation, host, and process ID, and the expiry as both Unix seconds and a UTC time. [A VM's metadata lock is held by a process that died](docs/troubleshooting.md#a-vms-metadata-lock-is-held-by-a-process-that-died) explains how to read the claim and when it is safe to clear the lock by hand.

- A parker's protection restore now has a deadline. When the CPI moves a parked disk onto a VM, or deletes a disk that is named for its parker, it clears the parker's protection for the change and puts it back afterwards, even when the request was cancelled. That restore had no deadline, so a PVE that stopped answering could hold it open past the parker lock's 180-second TTL, after which another request may take the lock and open its own window on the same parker. The deadline is the time the lock already sets aside for the restore after the window's own work, so the restore now ends inside the TTL. When the deadline cuts the restore off, or the connection fails on every attempt, nobody knows whether protection is back on, so the call fails with a retriable error that names the protection restore, says whether the disk transfer or deletion itself completed, failed, or has an unknown outcome, and gives the `qm config <vmid>` and `qm set <vmid> --protection 1` commands that check and fix it. When an earlier failure has already left a journal-managed operation uncertain, the restore is never sent, and the error says it was not attempted rather than blaming PVE. When the transfer completed, the CPI first records the disk on its new VM, with its provenance and CID, and removes the parker's record of it, so a rerun deploy finds the disk where the Director expects it, whether or not the disk is journal-managed. A deletion that completed has its parker record removed the same way. When the transfer or deletion failed as well, both errors are reported, and the failure's own classification decides whether the call is retriable. For a journal-managed disk, the allocation is left in `reconciliation_required` with the restore as its only unsettled step, and the next call that touches the record settles that step by reading the parker back. That call can be a rerun deploy's `attach_disk` or `delete_disk`, `storage-journal adopt`, or the `cleanup` precheck. A `create_vm` whose attach of a disk from `disk_cids` meets a cut-off restore keeps its VM, because the disk already reached it, and returns the retriable error without a rollback or another placement. The Director's retry in the same task resumes that VM, settles the restore step once the parker reads protected, and completes with the disk already in its slot. While protection is still off, the retry is refused with the `qm set` command and the VM is kept for the next try, and when every try runs out with protection still off, the VM stays for a plain `storage-journal cleanup` once protection is back. Only a `create_vm` attach that changed the disk without landing it still takes the handoff cleanup route. A parker that reads protected lets the call carry on without any write to PVE, and one that reads unprotected refuses it with the exact `qm set <parker> --protection 1` command to run before we retry. The journal records the restore's value in the kind field of the step's parameters rather than in a new parameter field, so a 0.8.0 or 0.8.1 CPI can still read the record after a rollback. A protection write that fails without an answer from PVE no longer blocks the rest of a journal-managed operation, and one that a retry then lands is settled before the operation completes. A restore that PVE answers with a failure now leaves a journal-managed disk's allocation usable, because the write provably did not apply, and it still logs a warning and nothing more, as before. See [A parker's protection restore timed out](docs/troubleshooting.md#a-parkers-protection-restore-timed-out).

- A cross-node attach now keeps its migration mover when destroying it would do harm, and it logs how to remove the mover by hand. When the write that puts the mover's protection back after the disk lands was cut off, the attach used to destroy the mover anyway, with or without a journal behind the call. The cut-off error's `qm config` and `qm set` commands then named a VM that was gone, and for a journal-managed disk the restore step could never settle, so every later call on that record was refused. For a journal-managed disk on a mover that an earlier request created, the attach used to clear the mover's protection and then have the journal refuse the delete, so an attach that had landed failed as uncertain and the empty mover was left unprotected. In both cases the attach now leaves the mover alone, and its warning says why and gives the order to remove it, `qm set <vmid> --protection 0` and then `qm destroy <vmid>`. A mover kept after a cut-off restore comes out only after a retry of the attach has succeeded. For a journal-managed disk, that retry settles the restore by reading the mover back, so the mover has to be there and protected when the retry runs, and the cut-off error gives the commands to check that and fix it. A mover that an earlier request created comes out once the call has gone through. Every other mover is still destroyed after the attach lands, including one an earlier request created when no journal stands behind the attach.

- A `delete_vm` that fails partway through disposing of a journal-managed VM no longer invites a retry that can only be refused. When the failure itself was retriable, such as a destroy task that timed out, the Director read that retriable error and retried the delete, and the retry was refused because the VM's allocation already required reconciliation. For a retriable failure, the error the Director sees now says that the allocation requires reconciliation, and it is not retriable. The original cause follows it in the CPI's log line for the call, which `bosh task <id> --cpi` shows. A failure that was never retriable, such as an audit refusal, keeps its own message first, so the Director still shows what the audit found. A failure with no CPI error type of its own used to show only the reconciliation notice, and it now shows its own text as a non-retriable error ahead of that notice.

- Log and error scrubbing now also masks a `PVEAPIToken` or `PVEAuthCookie` value when the name follows a percent escape such as `%20` or an underscore, when a blank sits before the `=`, or when the value sits on the line after it. Before this, those forms reached Director messages, CLI output, and the CPI's logs with the value intact. The argument trees that the allocation journal fingerprints, and that the opt-in request trace logs, keep the narrower rule this release gave them, so this change doesn't move the fingerprints again. The upgrade note under Changed explains how they differ from the rule in 0.8.0 and 0.8.1.

- A `delete_vm` retry that refuses a journal-managed VM now tells the Director why. When an earlier delete stopped partway and left a step unsettled, the retry refuses and names that step, as in `cleanup has unresolved mutation evidence; step attempt-0-step-7 (lifecycle_delete_vm_retain_ephemeral_Nodes_CreateQemuMoveDisk) is planned`. The Director used to show only `allocation decision could not verify or persist evidence` for that refusal and for every other refusal the CPI raises before it starts deleting, such as `retired VM identity is present; audit required`, and so did the Director's orphaned-VM cleanup, which retries the delete on its own schedule. Those refusals now reach the Director with their own text, and so does the CPI's log line for the failed call, which `bosh task <id> --cpi` shows. A journal write that fails and a PVE answer the CPI does not recognize still show the generic line, so no backend text reaches the Director, and every error keeps the type and retry behavior it had before.

- A parker window no longer runs without its lock after PVE says the lock's pool already exists and the CPI then cannot read, re-read, or take over that pool. That answer means another request may be inside the window, so the call now fails with a retriable error that says the lock state is unknown. The window still runs without the lock, with a warning, when there is no pool service, or when PVE refuses the lock pool's create outright, such as when the API token lacks `Pool.Allocate` on `/pool`. A create that fails any other way, a dropped connection included, now fails the call instead of running the window.

- A cluster lock create whose answer never arrives no longer leaves the lock taken for a whole TTL, which is 25 minutes for a VM's metadata lock. PVE may have applied a create whose connection dropped or whose request ended in flight, so the CPI now reads the lock pool back on its way out and deletes it when that read proves the pool carries its own claim. That is how it already gives up on a create it could not confirm. A create that PVE answers with a server error gets the same treatment, because that answer does not prove the create failed. The call fails with a retriable error that says the lock state is unknown. The same holds for the create that takes over an expired lock.

- The reads a cluster lock makes to confirm its own create and to judge another holder's claim now have a deadline. With `pve.operation_timeout.enabled` on, they end early enough that the lock gives up at least 5 seconds before the request's deadline, where a read that never answered used to hold the call up to 10 seconds past it. With it off, a read that never answers ends 10 seconds after it started, or at the end of the lock's wait if that is later, instead of at the API client's 30-minute timeout.

- A cluster lock acquire whose read after its own create misses the new pool no longer waits on its own claim until it times out. When a later read finds a live claim that carries the acquire's own owner token, the acquire confirms that claim and takes the lock. Before, the acquire failed and its own claim blocked the lock for a whole TTL, and a VM's metadata lock error named that claim as the holder.

- Five more protection restores now use the same deadline as the transfer and deletion restores. Three put a parker's protection back after an unpark or after a sweep of a slot that a concurrent park demoted, and two put a mover VM's protection back after a failed migration. Before, a PVE that stopped answering could hold those restores open well past the parker lock's 180-second TTL. They still log a failed restore rather than fail the call, and the log now says whether PVE refused the write or the write's outcome is unknown.

- When a parker's protection restore is cut off, its error now says that the disk transfer or deletion has an unknown outcome when that change ended without a verdict from PVE, where it used to say that the change failed. It says the change failed only when PVE answered with a failure.

- When a VM's metadata lock gives up because the request's deadline left no time to wait, the read that names the holder now ends 5 seconds before that deadline, so the error that quotes the claim reaches the Director instead of a generic timeout. With less than 5 seconds left, the CPI skips the read and says the claim couldn't be read.

- The anti-affinity lock's claim now lasts at least 30 seconds however low `pve.cluster_lock_timeout_sec` is set, and the wait still follows the setting. The claim used to last twice the setting, and at a setting of 4 or less, the pause each acquire takes after its create and the margin a release leaves before a claim's expiry used up most or all of that time. At 1, a second request could take the lock while the first still held it, and from 2 to 4, the release left the lock pool standing until the claim expired.

- A request that ends while a parker window has protection off, because `pve.operation_timeout` fired or the CPI process was told to stop, now still puts protection back for a journal-managed disk. The allocation journal refused that restore once the request had ended, so the parker stayed unprotected until the next window on it, and the error said the operation was already uncertain.

- A storage listing that fails on the node a moved VM now runs on no longer blocks `create_vm` and `create_disk`. The audit read that failure as a missing volume and refused the move with `was not listed on storage`, which is the same text it gives a volume that is really gone. So one listing that timed out, or that answered that its storage was not online, could stop every create in the namespace. A failed listing proves nothing either way, so the move now stays undecided. Instead of a conflict, the audit raises an issue that says `move undecided (listing_failed)` and names the storage listing it could not read. That issue keeps `delete_vm` and `delete_disk` refused until a later audit can read the listing, and the audit accepts no move in the meantime. When the listing succeeds and the volume is missing from it, the audit still refuses the move. The audit also puts a limit on the provenance node it copies into `observed_moves` and the evidence it retains. A node longer than the 63 bytes a PVE node name can hold is now malformed provenance, and the audit reports it the way it reports any other provenance it cannot parse.

- A parker's protection restore whose checks can't finish no longer leaves a journal-managed disk stuck. Before the allocation guard sends that restore, it reads the disk's storage definition, the cluster's identity, and the parker's configuration. When one of those reads failed, whether PVE answered it with an error such as a 500 or it ran past the restore's deadline, the guard locked the whole operation. The restore was never sent, the attach could not record the disk on its new VM, and every later `attach_disk`, `storage-journal adopt`, and `cleanup` refused with `renamed managed disk lacks full ownership provenance; audit required`, which never mentions the parker. We now leave the restore planned on the record and keep the guard usable, so the attach still records the disk on its new VM, and the next call reads the parker back the way it does after a restore whose own write was cut off. The error says the restore `was not sent because the checks before it failed, so protection is still off`, or that the checks did not finish within the restore's deadline, and it gives the `qm set <vmid> --protection 1` command to run before we retry. A read that answers with a different storage backing or a different cluster still locks the operation, as before.

- An audit refusal now names the allocation behind each short form, every VM and volume it left out, and the runbook section to read. A short form that leads with a VM or a volume now gives its allocation ID after the reason, as in `VM 123 on pve2, recorded pve1 (node_mismatch), allocation <id>`, so the first 75 characters that `bosh tasks` keeps don't change. The short form of a volume that two VMs share names the allocations that our records or our disk provenance tie to it. The three findings a refusal lists now take one finding for each VM or volume first, so a VM that raised three conflicts no longer hides a second moved VM. The remainder counts each kind it left out and names every VM and volume that the hidden short forms lead with, as in `and 2 more audit conflicts (VM 7015, VM 7018), 1 more VM-scan issue`, where it used to give only a number. Every audit refusal now points at the runbook with `see "An operation fails with an allocation audit refusal" in docs/troubleshooting.md of bosh-proxmox-cpi-release`, just before the command that prints the full report. The `storage-journal` CLI puts the same pointer on its `audit findings:` line, and on its `allocation decision refused` line when an audit gate refused the decision, and `storage-journal audit --summary` prints it on a `runbook:` line after the findings whenever the audit raised a conflict or an issue. A move the audit refused because its VM scan was incomplete now says which node the scan missed and why, as in `the VM scan is incomplete because pve3 is reported offline`. That matters most for `create_disk`, whose refusal under an offline node never named the node. A `detach_disk` refusal now says the same thing. When a read in the audit's visibility check fails, the VM-scan issue now names the read, its path, and the cause's class, as in `could not read effective permissions at /access (context deadline exceeded)`, where it used to say `unclassified error`. Every refusal keeps the error type and retry behavior it had before.

- When the journal refuses to save a settlement during a `storage-journal` decision, the CLI now says which steps that settlement covered, where its `allocation decision refused` line used to say only `unclassified error`. Before `adopt`, `finalize-cleanup`, or `cleanup` judges a record, it settles any lock step or parker protection write that it can read back, and when the journal refuses to save that settlement, the line now reads like `allocation decision refused (cleanup_lock_step_settlement: the journal refused to save the lock settlement of step attempt-0-step-4 (lifecycle_attach_disk_Pool_CreatePool): allocation requires reconciliation)`. It names the first step, and how many more there are when the write settled several. It describes the journal's failure the same way the CLI already describes the journal's own errors and its failed file operations, and it describes anything else the way it did before. The error behind it now names the parker protection steps it was settling, as it already did for lock steps. The Director still shows the generic `allocation decision could not verify or persist evidence` when such a write fails inside `delete_vm`, so no journal path reaches it. A `cleanup` refused for missing attestations now names the first step it admitted and the flags we need to add, as in `pending mutation cleanup requires explicit writer fencing and independently settled remote tasks; step attempt-0-step-3 (vm.persistent.<digest>) is planned; rerun with --previous-writer-fenced, --remote-tasks-settled, and --authority-id`. A `delete_vm` refused for a planned lock step now says why settlement left it planned, as in `cleanup has unresolved mutation evidence; step attempt-0-step-2 (vm.Pool.CreatePool) is planned; its lock sentinel could not be settled because PVE did not answer exactly for sentinel bosh-lock-vm-777 (HTTP 500: <PVE message>)`. Every error keeps the type and retry behavior it had before.

- `pve-cid locate` now reports every guest that names a disk. It used to stop at the first active slot that matched, in VMID order, and it never read unused entries, so for a volume that two guests name, it could point at the wrong one. It now lists every active slot whose drive carries the disk's serial or names its volid. It also lists every unused entry that names the volume, whether under its original volid or under the name a matching slot carries, and any guest whose config it could not read. The `holder` line and JSON field still name the first match, so a caller that reads only the holder sees no change. The JSON gains `holders`, `unused_refs`, and `unreadable_vmids`, and stderr carries a warning when more than one guest names the disk or when a config could not be read. The exit code does not change. See [Auditing parked disks with scripts/disk-audit](docs/operations.md#auditing-parked-disks-with-scriptsdisk-audit).

- A `delete_vm` with `retain_ephemeral_on_delete` set no longer strands its record when the ephemeral retention runs out its parker lock wait. Before 0.9.0, a storage-journal cleanup of such a record could destroy the retained ephemeral volume, so a deployment on 0.8.0 or 0.8.1 should upgrade before it cleans these records. The retention writes the volume's stable-ID serial before it waits for the parker lock, and when that wait ran out, the record went to `reconciliation_required`. Every later attempt then refused. The Director's next `delete_vm` read the empty parker the first attempt had created as a finished transfer and refused with `retained parker identity differs`, or, on a node that already had a parker, refused with `ephemeral retention token already identifies a live resource`. `storage-journal cleanup` saw no transfer on a node that already had a parker, so it destroyed the VM together with the volume. Now a retention that waits out the lock before it moved the volume hands the Director the retriable timeout and leaves the record observed. A record an earlier release left behind closes through the Director's next `delete_vm`, through `cleanup`, or through attested `cleanup`, and each of them finishes the retention. The volume moves to a parker under the allocation's stable ID, the VM is destroyed, and the record ends in `vm_deleted_retained`. A transfer counts only when a parker's provenance entry for that stable ID names a slot and the drive at that slot holds the volume with the serial, so a parker the first attempt created and left empty is never mistaken for one. That parker stays as an ordinary shared parker, which the next park on its node can reuse. Before we roll back to an earlier release, we close every open retention record, either by letting the Director's `delete_vm` finish it or by running `storage-journal cleanup` on it. A retention that timed out leaves its record observed on purpose, so the next call can finish it, and a 0.8.0 or 0.8.1 cleanup of that record destroys the retained volume on a node that already had a parker.

- When a persistent disk's name carries the VMID of the VM it's on, and the disk is stranded on that VM's unused entry, the CPI no longer parks, attaches, or deletes it while the entry still names it. A disk lands there when its move to a parker fails after its slot is deleted, and the parker's record of the move is lost afterwards. Its name carries the VM's VMID only when the VM band was moved over VMIDs that still name disks. Before this release, `detach_disk` reported success with both a parker and the VM naming the volume, `attach_disk` attached it to a second VM the same way, and `delete_disk` deleted it while the VM still named it. The CPI now finds such a disk by the unused entry that names its volume. `detach_disk` moves it to a parker, and `attach_disk` moves it to a parker first when it sits on another VM, so either one leaves a single reference. `delete_disk` refuses and names the VM, the node, the volume, and the entry. The runbook section gives two ways out. We can attach the disk to an instance, or we can remove the entry once the checks pass. A journal-managed disk in this state is refused the same way, and so is a disk whose unused entries can't be tied to one VM. See [delete_disk refuses a disk stranded on an unused entry](docs/troubleshooting.md#delete_disk-refuses-a-disk-stranded-on-an-unused-entry).

- A disk delete that PVE could only record as pending no longer counts as a detach. On a running VM whose hotplug setting lacks disk, or whose guest still holds the device, PVE leaves the delete pending and the guest keeps the disk, while the config read the CPI used no longer shows the slot. Every release since 0.3.0 could then take the disk as detached and attach it to a parker while the guest still had it. The CPI now reads PVE's pending view wherever it decides whether a VM still holds a disk, so a slot with a pending delete still counts as attached. When one of its own slot deletes stays pending, in `detach_disk`, in `attach_disk`'s move off a legacy `scsi0` slot, in a journal-managed detach, or in `delete_vm`'s detach of a foreign disk, it reverts that delete and fails the call. `detach_disk` and `attach_disk` fail retriably when the guest is busy and permanently when the hotplug setting lacks disk, and `delete_vm` fails retriably in both cases and destroys nothing. `delete_disk` refuses a disk whose holder's slot has a pending delete, or a pending value that names another volume. It says to stop the VM if it's running, or to start it if it's already stopped, so that the change applies, and then to rerun the clean-up. A journal-managed detach records the pending delete as not applied, observes the revert, and keeps its allocation out of reconciliation, and that holds on a busy guest too, where the allocation guard now settles each busy delete instead of locking the allocation before the revert. The VM allocation guard never records a pending delete as a delete either. `delete_vm` reads both views at every site that decides what its destroy takes, on both paths and in the straggler sweep, and so does the `create_vm` rollback, so a disk slot that a crash or a kill left with a pending delete is still detached or transferred before the destroy, because PVE's destroy works from the config that still has it. When a slot's pending value names a different drive from its current one, `delete_vm` stops the VM first, which applies the change, and it refuses retriably and names both drives while the change is still pending after the stop, because the destroy frees an owned volume that either names. A legacy disk named for the VM is refused before the stop when either value names it. Every slot choice for a disk attach now counts a slot whose delete is pending as occupied, so an attach never writes a second volume onto a slot the running guest still has. When `attach_disk` targets the VM that already holds the disk on a slot whose delete is pending, it reverts that delete, confirms it, and returns the disk's own slot, and it fails retriably when it can't confirm the revert. When the disk's own slot instead carries a pending value that names a different volume, `attach_disk` fails retriably and changes nothing. Journal-managed `delete_vm` and the storage-journal cleanup and audit now read both views too. On a slot whose delete is pending, the journal-managed `delete_vm` now preserves a managed persistent disk, unlinks a legacy disk, and retains the ephemeral volume it's set to keep, and it does each of these before the destroy. The check just before the destroy covers every device either view names. A volume that a running guest still has on such a slot now counts as referenced for the cleanup and as held for the audit. After its stop, a journal-managed `delete_vm` gives a retriable refusal for a slot whose pending value names another drive, the way the legacy path does, and it leaves its allocation ready for the retry. `get_disks` lists every persistent disk either view names, so cloud check isn't told that a disk is missing while the guest still has it. The identity scan counts a slot whose pending value names another volume as holding both volumes. A slot delete there sends nothing and fails retriably until the change applies. A journal-managed operation that stops on such a slot, or on a pending delete it found and left alone, keeps its allocation out of reconciliation, unless the change appeared after the operation had already written something. A retried `detach_disk` or `attach_disk`, `delete_vm`'s retention of an ephemeral disk, and a journal-managed `delete_vm`'s preservation of a persistent disk now apply a pending delete they find on a stopped VM and finish the transfer. Nothing else would apply that delete until the VM starts, so they used to fail retriably until an operator stepped in. Like a start, the write that applies the delete also applies every other change pending on that VM. On a running VM they still leave the delete for the VM's next clean stop. See "A disk detach stays pending on a running VM" and "delete_disk refuses a disk whose slot delete is pending" in docs/troubleshooting.md.

- A disk with a stable ID whose volume isn't named for the VM holding it now parks on the first `detach_disk`. PVE keeps an unused entry for a deleted slot only when the VM owns the volume, and a volume named for another VMID loses its last reference. The transfer to a parker expected that unused entry every time, so every such disk failed its first transfer with a retriable error, and the parker's record of the transfer was the only link left to the volume. A disk ends up with such a volume after a cross-node attach, which adds the volume by config edit and keeps its name, and a journal-managed disk has one under its usual name, which carries a VMID from the disk band. The transfer now reads back what PVE left after the slot delete. When an unused entry names the volume, the CPI still moves it, and the move renames the volume for the parker. When the source VM no longer names the volume in either view, the parker takes it by config edit in the same protection window, with its serial and under the name it already has. A parker's record of such a transfer is now kept while the volume still exists and no guest names it. That way a transfer cut off between the slot delete and the parker attach finishes on the next `detach_disk`. A guest that names the volume, or a proof that the volume is gone, lets the record go. A snapshot of the source VM that still names the volume defers the park, the way PVE's move refusal already does for a volume the VM owns. `detach_disk` succeeds with the disk off the bus, and the disk parks on the next call that changes it after the snapshot is deleted. `delete_vm` refuses the first time and names the snapshot. When `delete_vm` runs again, the disk is already off the VM, so the VM goes with its snapshot, and the disk stays recoverable through the parker's record, so a later `attach_disk` picks it up. This corrects the 0.8.1 entry about a failed move to a parker. That entry says PVE leaves the volume on an unused entry of the VM, which is true only for a volume the VM owns. See "delete_vm refuses to destroy VM with attached unused disks" in docs/troubleshooting.md.

- Every move of a disk between a VM and a parker now carries the configuration digests of both VMs, including for disks that don't use storage sets. Journal-managed disks already sent them. When the CPI's move request got no answer, PVE could still run the move later, and that late move took whatever volume held the slot it had been given, even after the VM's configuration had changed. PVE now refuses a late move like that, so it can't move the wrong volume or move a disk the CPI has since handled another way. When PVE refuses a move because a configuration changed after the CPI read it, and no earlier request in the same call went unanswered, the CPI now says the disk stayed where it was and asks the Director to retry, where it used to treat the outcome as unknown. For a disk without storage sets, when an earlier request did go unanswered, the CPI first reads both VMs back, because that request's move may have landed in the meantime. A move that landed counts as done, a disk that's still where it was gets the same refusal, and anything else comes back as a retriable error that says the outcome is unknown. A journal-managed disk stops at the unanswered request instead, and its record waits for reconciliation. Another write to the same parker or VM while a move is on its way can also refuse the move, with an error that says the move was refused because a configuration changed, and a rerun of the deploy goes through. For a journal-managed disk, the refused move is recorded as settled once a readback of both views shows the disk where it was, so the allocation keeps no unsettled step and the retry finishes the transfer. A 597, 598, or 599 from PVE now counts as an unanswered request, like a 596. pveproxy relays those codes when a call it forwarded broke after the backend may have started it, so a move or a parker protection restore that gets one is treated as possibly landed rather than refused.

- When PVE refuses to move a journal-managed disk onto a parker because a snapshot still names its volume, the allocation no longer ends in `reconciliation_required`. PVE makes that check in the request, before it starts a task or changes anything, and the move's task makes it again under the configuration locks before it renames the volume, so either refusal means the disk stayed where it was. The CPI still counted the refusal as an unknown outcome, though, so it locked the allocation at the first refusal and dropped PVE's text, and `detach_disk` failed where it should have deferred the park. Now the CPI records the move as refused once a readback of both VMs shows the disk where it was, the same way it records a refusal on a configuration digest. That holds for the request's answer and for a finished task whose exit status is PVE's refusal word for word, although the configuration digests sent with every move make the task's form rare. `detach_disk` then succeeds with the disk off the bus, and the disk parks on the next call that changes it after the snapshot is deleted. The move from a parker back onto a VM in `attach_disk` is unchanged, and a snapshot refusal there still sends the allocation to reconciliation. A disk that isn't journal-managed used to send the same move request three more times with a backoff in between, even though PVE gives the same answer for as long as the snapshot exists. Its moves in both directions now stop at the first snapshot refusal, and every other error from a move is handled as before. A detach reaches this refusal only for a volume named for the VM, which is what every disk has after its first attach from a parker, and only in four cases. The first is when `pve.allow_disk_ops_with_snapshots` is true, and the second is when someone takes a snapshot after the CPI's own check. The third is when that check itself fails and `pve.require_snapshot_check_pass` is false, so the detach goes ahead anyway. The fourth is when a second disk key on the VM names the same volume. When a task ends with any other status, when its status can't be read, or when the readback shows anything else, the allocation still waits for reconciliation.

- A disk with a stable ID is now found by the serial on its drive entry or by its parker's transfer record, and a slot that carries the CID's volume name under another serial or none no longer counts as the disk. That name is the volume's name at `create_disk`, and a move renames the volume, so another volume can take the name later, for example when a legacy `create_disk` reuses a freed VMID. The CPI used to match a slot by that name before it looked at the serial, so `attach_disk`, `detach_disk`, `resize_disk`, `update_disk`, `snapshot_disk`, and `set_disk_metadata` could rewrite, move, grow, or snapshot the other volume, and `attach_disk` or `create_vm` could hand it out from a parker as our disk. Which slot won could change from one call to the next. When nothing carries the serial and no parker records a transfer, but a slot under another serial or none names the old volume, every disk call now refuses with a permanent error that names the disk, the volume, the VM, and the slot. `delete_disk` refuses the same way instead of reporting success, and `has_disk` answers false, so `bosh cck` reports the disk missing. An `unusedN` entry with that name counts as the disk only when its VM's description still holds the disk's attached-disk note, and otherwise it gets the same refusal. A disk that nothing names still resolves to its original volume. A disk whose transfer onto a parker stopped after the move landed and before the serial write still resumes from the parker's transfer record, even when the landed volume took back the disk's original name. A record that the parker keeps for another disk proves nothing for this one.

- `resize_disk`, `snapshot_disk`, and `set_disk_metadata` now finish a disk's unfinished transfer onto a parker before they act, as the other disk calls already did, because the record names the volume by its name before the move and another volume can hold that name by then. For a journal-managed disk, `set_disk_metadata` now finishes the transfer inside the disk's lifecycle, as `resize_disk` and `snapshot_disk` do. That way the detach tail runs under the journal's lock, and the lifecycle ends before the call takes the VM's lock. A disk with no transfer in flight skips the lifecycle altogether. If the tail fails, all three calls fail retriably before they change anything.

- The birth-name refusal described above now also comes first for a disk stranded on an `unusedN` entry whose VM no longer holds the note, and earlier releases left disks in that state themselves. When a snapshot defers a park, `detach_disk` still removes the disk's note from the VM as it reports success, and releases up to 0.8.0 dropped the parker's transfer record once it was an hour old. Deleting a snapshot stays the deployment owner's decision, because `qm delsnapshot` can't be undone. For a disk without an allocation journal, `attach_disk` used to recover such a disk and `detach_disk` used to park it, and both now refuse it with this error. The other disk calls used to refuse it with the stranded-disk error, and a journal-managed disk whose record already said it was deleted got the terminal-record error. Since 0.8.1, the parker keeps its transfer record while the VM still holds the volume, so the disk resumes from that record instead of reaching this refusal. A disk that an earlier release stranded without its note stays refused, and the CPI restores nothing for it. Its recovery is ours to do by hand, and the troubleshooting guide now gives the procedure. We ignore the instance, copy the volume out with reads alone, and prove that no other disk CID names the volume or the `vm-<Q>-` name it would take on the quarantine VM. Then, only when the entry is an unused entry on a VM that a Director we searched knows, we move it onto an unused entry of a quarantine VM that we never start. We stop and hand the decision to the deployment owner when the Director holds snapshots of the disk, because releasing the record deletes them. Otherwise we release the record with `bosh orphan-disk`, delete the orphan with `bosh delete-disk` once no node's storage lists the old name, confirm that the orphan is gone, and only then deploy, which gives the instance a new disk. We release the record that way and not with the delete-disk-reference resolution in `bosh cck`, because that resolution marks the disk inactive and then calls `detach_disk`, which refuses the disk, so the resolution fails and every later deploy fails on the same call. When the volume may be another disk's, or the entry is a slot, we leave it where it is and still release the record, and the Director's orphan cleanup then fails on that disk until the volume no longer carries its old name. We worked the procedure out from the code and haven't run it against a lab. See [Another entry names a disk's birth volume](docs/troubleshooting.md#another-entry-names-a-disks-birth-volume).

- `delete_vm` still retains a legacy ephemeral volume from the VM's own serial-less slot. It now refuses when another guest or a second slot of the same VM names that volume too, or when the VM's config changed between its own read and the identity resolution.

- A disk whose transfer to a parker stopped after the move and before the CPI wrote the disk's serial on the parker no longer fails every call for good. The move had already renamed the volume, so the old name that the parker's transfer record names was gone. `attach_disk` looked that old name up to find the disk's node and failed with `disk not found`, and every call on a journal-managed disk refused with `managed disk ownership provenance references a missing volume; audit required`. Retrying never got past either refusal. Now `attach_disk` finishes the transfer first and then works from the disk where it landed. Every call that checks a journal-managed disk's identity does the same when all that's left is to write the disk's serial on the parker and remove the transfer record, so a read such as `has_disk` may now finish an interrupted transfer with those two writes. It writes nothing else to the disk or its VMs, and it does this only while it holds the parker's lock. When PVE refuses that lock, the call refuses for audit with `managed disk ownership provenance references a missing volume; audit required`, followed by a reason that names the lock, so the Director doesn't retry it. An operator clears the refusal by granting `Pool.Allocate` on `bosh-lock-*` to the CPI's API token or user. Once it holds the lock, it reads the parker's transfer record again. If another call finished or changed the transfer in the meantime, it resolves the disk again instead of acting on what it read before, so a call that waited for the lock finds the disk where the other call left it. It writes the serial only when the disk's allocation record holds the observed move that landed that very volume. That landing no longer counts once the record has observed a later move that took the volume off that name, or a later migrate that started from it, because the volume isn't there to claim anymore. A slot that holds any other volume with no serial, such as another disk's landing, gets the permanent refusal for audit and is left as it is. That call doesn't remove the disk's notes from the source VM's description, and they stay until the next `attach_disk` or `delete_disk` for the disk removes them, whichever VM the attach is for. A `detach_disk` that finds the disk already parked removes them too, and while they stay, they don't make `delete_disk`'s completion audit refuse. If the source VM's config still names the volume by its old name, finishing the transfer would also move it, so the call writes nothing and checks the disk once more. When storage lists the old name again, the call goes on from there, and the next call that changes the disk, such as `attach_disk` or `detach_disk`, finishes the transfer inside the disk's lifecycle. When the old name is still gone, the source VM's entry for it is dangling, and no later call can finish the transfer either. The same holds when finishing it would apply a pending delete on the source VM or attach the released volume to the parker by a config edit, because no later call gets past the identity check to do that. In the cases where no later call can finish the transfer, the call refuses permanently with the same `managed disk ownership provenance references a missing volume; audit required`, followed by the reason. If the transfer can't be finished yet, for example because the parker's node is offline, the call fails with a retriable error, and the Director tries again later. A refusal that the transfer itself marks for audit stays a refusal that the Director doesn't retry. When a step in the disk's record isn't settled, such as a move to a parker whose answer the CPI never got, or when the record is in `reconciliation_required`, the identity check doesn't try to finish the transfer. It refuses before it writes anything, with the same permanent refusal as before, and the refusal now names the step or the record's state. A call that overlaps another call's work on the same disk can get this refusal too, and rerunning it after the other call finishes clears it. A move step's refusal also points at [A disk call refuses while a move to a parker is unsettled](docs/troubleshooting.md#a-disk-call-refuses-while-a-move-to-a-parker-is-unsettled).

- `update_disk` now finishes an unfinished transfer to a parker inside the journal-managed disk's lifecycle when the transfer's old name still exists, so the allocation journal records the landing the way it does for the other disk calls. When that name is gone, the identity check finishes the transfer claim-only before `update_disk` opens the lifecycle. It still leaves the source VM's allocation entry in place, and a later `attach_disk`, `detach_disk`, or `delete_disk` removes it.

- When the CPI finishes a move to a parker that landed before its serial write, it no longer takes another disk's volume for the disk that moved. PVE renames a volume when it moves it, so the old name the parker's record keeps is free afterwards. Another disk can then take that name on the source VM, and its own unfinished detach can leave it on one of that VM's unused entries. `update_disk`, `detach_disk`, `attach_disk`, `resize_disk`, `snapshot_disk`, `set_disk_metadata`, `delete_disk`, and a `delete_vm` that keeps a legacy ephemeral disk each finish an interrupted move before they act on the disk, and that step used to move whatever unused entry carried the recorded name and write the first disk's serial onto it. The CPI now proves which volume is the disk before it moves a volume or writes a serial onto one. The same proof runs when the identity check finishes a move by claiming its landing. Every disk call on a journal-managed disk, `has_disk` included, runs that check first. Each of those calls returns the proof's refusal as it is, so a refusal that asks for an audit never comes back retriable.

  While the parker holds a landing, that identity check now claims the landing when the proof allows, even while the source VM still names the old name. It stops at the move only when each landing on the parker, if there are any, is one it can set aside as another disk's, and only then does a dangling entry for the old name get the permanent refusal. It claims a landed volume only when that volume is the only one on the parker, in both the current and the pending view, that is named for the parker and carries no serial, and only when it sits on the slot the record names. A landing on the slot of another unfinished transfer to the same parker belongs to that transfer only when that transfer's move is proved. A move counts as proved only when two things hold. The source VM exists and names the recorded volume nowhere, whether in its configuration, its pending changes, its unused entries, or its snapshots. And the volume is either gone from a full listing of its storage or named by another guest. A source VM that still names the volume with no serial means that disk hasn't moved, and every other answer leaves its move unknown, including a source VM that's gone, a record with no source VM, and a volume that still exists while no guest names it.

  When a record's move reads as proved but some guest already carries its disk's serial, that disk's transfer finished elsewhere and the record is stale. The CPI then treats the record's move as unknown, so it never sets a landing aside as that record's. When the guest that carries the serial is the parker itself, another call finished that transfer after the CPI read the parker, so the call gets a retriable error and the next one settles it. The CPI reads each source VM once, on the node where the cluster finds it. A failed read gives a retriable error, unless the failure already carries a permanent class, such as a configuration that PVE returns malformed. The CPI refuses permanently and says audit required, naming both disks' CIDs and both slots, in each state its metadata can't settle. Five states get that refusal. In the first, a landing sits on the slot of a transfer whose move isn't proved. In the second, a transfer's move is proved but nothing sits on its slot while another landing remains. In the third, two proved moves leave landings that both wait for their serials, which includes two transfers that both landed and both stopped before their serial writes. In the fourth, a landing sits on the disk's own slot while its own move isn't proved and another transfer's slot stays empty. In the fifth, two records name the same volume on the same source VM. A transfer whose recorded volume isn't named for its source VM attaches that volume under its own name, so it never claims a volume renamed for the parker. A new transfer to a parker, and a park by configuration edit, no longer pick a slot that another unfinished transfer there names, which is how two disks used to end up sharing one. While the parker holds a landing that the CPI can't set aside as another disk's, the CPI moves nothing off the source VM. The move it does send carries the configuration digests the check read, and it goes out only while the source slot still names the recorded volume, so a change in between fails the move with a retriable error. When the disk's recorded slot is taken, the CPI writes the fallback slot into the parker's record before that move, so a move that lands and then loses its serial write leaves a landing the next call can claim. If anything else on the parker changed while the CPI wrote that record, apart from the stale records the write collected, the call gets a retriable error before it moves anything. The CPI also refuses when another parker keeps a record of the same disk's transfer, when another guest carries the disk's serial, or when any other guest names a volume the source VM has let go of. It treats a disk's own source VM as gone only when the cluster can't find it either, so a source VM that migrated to another node gets a refusal rather than a parker attach.

  When a stopped source VM's pending delete was applied before the check refused, or before the slot choice, the record rewrite, or the move failed, the error says so. Any other refusal names what it found, isn't retriable, and points to "A transfer resume can't prove which volume is the disk" in docs/troubleshooting.md. Two states still pass the check, and both follow a hand change while the parker holds no landing. In one, someone removed the disk's unused entry from its source VM by hand. In the other, someone destroyed the source VM by hand and PVE gave its VM ID to a new VM. Either way a new disk can take the freed name and be moved in the first disk's place. The troubleshooting section describes both gaps and every audit-required state, how we settle each landing by reading its contents read-only, how we prove a record stale or released before removing it, and why we never remove a disk's unused entry or destroy its source VM by hand while its transfer is unfinished.

## [0.8.1] - 2026-10-01

### Fixed

- A `delete_vm` with `retain_ephemeral_on_delete` set now keeps the ephemeral disk when the disk sits on file-backed storage, such as NFS, CIFS, BTRFS, or a directory storage. This affected deployments that don't use storage sets, because their VMs take the delete path that keeps no allocation journal. On file-backed storage the ephemeral volume's ID carries the VM's directory, as in `nfs:777/vm-777-ephemeral-0.raw`. The check that looks for the disk on the VM's active slots removed only the storage name before it compared names, so it never found the disk. The delete then reported the disk as retained without moving it to a parker, and the destroy that followed deleted it. That happened on an ordinary `delete_vm`, on a fast-path delete, and in the sweep that finishes stalled fast-path deletes. Releases 0.6.0 through 0.8.0 deleted the disk this way. Version 0.6.0 is the first release that could create an ephemeral disk on file-backed storage at all, because PVE refused the volume name that earlier releases asked for, which had no format extension. We can't recover a disk that one of those releases has already deleted, and upgrading to this release is the fix. Ephemeral disks on block storage, such as LVM, ZFS, and Ceph RBD, were never affected.

- A legacy persistent disk is no longer freed when a VM ends up with the VMID its volume is named for. A legacy disk keeps the name `create_disk` gave it, such as `data:vm-9005-disk-0`, and PVE decides who owns a volume from that name alone. Once we moved the VM band over VMIDs that still named disks, `create_vm` could hand VMID 9005 to a new VM, because the plain path looked for volumes only on `vm_storage` and the ISO storage, and the managed path didn't look at storage at all. From then on PVE counted the disk as that VM's own, so the next `detach_disk` freed the volume, and `delete_vm` destroyed it along with the VM. Both `create_vm` paths now skip any VMID that names a volume on an enabled images storage the target node can see, and a listing that fails now fails the allocation instead of letting it go ahead blind. Leftover guest volumes (`vm-N-*` or `base-N-*`) now hold their VMIDs out of the band, so enough of them can use up a narrow band and fail `create_vm` with `no free VMID`. `scripts/disk-audit` finds them. `attach_disk` refuses to put a legacy disk on the VM its volume is named for, and `detach_disk` refuses to take one off. `delete_vm` refuses to destroy a VM that holds one, on both the synchronous path and the fast path, and the fast-path straggler sweep leaves such a VM tagged for us to look at. Each refusal names the disk and says why. The `attach_disk` refusal tells us to let the Director recreate the VM, for example with `bosh recreate`, and the new VM then draws a VMID that names no disk. The `create_vm` refusal says nothing was attached and the new VM is rolled back, or kept when `pve.debug.keep_failed_vms` is set, and it names what has to change before a retry can draw a different VMID: the disk's storage becoming active on the node, or `cloud_properties.target_node` set to the node whose local storage holds the disk. The `detach_disk` and `delete_vm` refusals say how to reassign the volume by hand. One case remains. `delete_vm` tells such a disk apart from the VM's own disks by the CID that the attach records on the VM, and every release since 0.1.0 writes that record on a best-effort basis. So if an earlier release attached a disk like this and its record write failed, `delete_vm` still destroys the disk along with the VM, exactly as it did before, although `detach_disk` now refuses it. No new attach can create the shape, because `attach_disk` now refuses it. With `pve.destroy_unreferenced_disks` on, two cases stay open as well, because `create_vm` reads only the storages its target node can list when it draws the VMID. A volume on storage local to another node that the VM later migrates onto, and a volume on a storage that was inactive on the node when the VMID was drawn, can still be freed by that sweep when we delete the VM. See [VMID ranges](docs/configuration.md#vmid-ranges).

- A `delete_vm` with `retain_ephemeral_on_delete` set no longer fails on every attempt when the VM's ephemeral disk sits on an unused slot. Each attempt failed with `retained ephemeral ownership is ambiguous`, and the sweep that finishes stalled fast-path deletes skipped the VM on every pass, so it stayed tagged `bosh-deleting`. Nothing was lost, because the CPI refused before it destroyed anything. This affected deployments that don't use storage sets, and a disk could land on an unused slot in two ways. A retention transfer can stop after it detaches the disk and before it moves the disk to a parker, and once the transfer's record on that parker is more than an hour old, the next park on the same parker clears it. Someone can also detach the disk by hand, because PVE keeps a disk detached without force as an unused entry on the VM. Releases 0.6.0 through 0.8.0 refused this way. They also refused a delete that 0.5.2 or an earlier release had stopped between its unlink and its sweep, when that delete was retried after an upgrade. The CPI now moves the disk to a parker when the VM's own config is the only place in the cluster that names it and that place is an unused slot, and it still refuses when anything else references the disk.

- A persistent disk whose move to a parker failed partway is no longer lost from view. A disk with a stable ID moves in three steps. The CPI records the transfer on the parker, deletes the disk's slot on the VM, and then moves the volume. When the move fails, PVE leaves the volume on an unused entry of the VM with no serial, and the parker's record is the only link from the disk's CID to that volume. In 0.5.1 through 0.8.0, the next write to that parker removed the record once it was an hour old. After that, `detach_disk` could report success while the disk stayed on the VM, `attach_disk` could attach it to a second VM, and removing the unused entry by hand deleted the volume, because its name carries the VM's VMID. The record now stays for as long as the VM still names the volume on any slot, so a retried `detach_disk` finishes the move and parks the disk. For a record that an earlier release already removed, the runbook section gives the checks to run first and the way to reattach the volume with the disk's serial before retrying the detach. Never remove the unused entry or destroy the VM by hand. The `delete_vm` refusal for unused slots now says so and points at that section. See [delete_vm refuses to destroy VM with attached unused disks](docs/troubleshooting.md#delete_vm-refuses-to-destroy-vm-with-attached-unused-disks).

## [0.8.0] - 2026-09-15

### Added

- Every set-managed create now charges what its in-flight siblings have already claimed. Placement ranks members against the capacity PVE reports, and PVE reports a volume only once that volume exists, so two creates that started seconds apart used to see the same free space and choose the same share, which is how several VMs of one instance group landed together. Each create now reads the allocation journal before it ranks and seeds the ranking with the bytes the other open allocations have claimed on each member and each capacity domain. See [Charge in-flight siblings against a placement](docs/multi-storage-placement.md#charge-in-flight-siblings-against-a-placement).

  Four record states charge their bytes, and they are `planned`, `submitted`, `observed`, and `reconciliation_required`. In those four the volume is neither absent nor yet counted in any storage status. The resting states charge nothing, because in `ready_to_return`, `adopted`, and `vm_deleted_retained` the volume exists and the capacity snapshot already carries it, while in `deleted` and `cleaned` it does not exist at all.

- The bytes one sibling charges come from two sources, and for each capacity key the CPI takes the larger of the two rather than adding them. The first source is the plan's own claim, which a record in `planned` carries before it has written any step, and the second is the sum of the record's step charges. Once a step exists, its charges restate what the plan claimed, so adding the two would double the sibling's weight. Outstanding bytes always count, and acquired bytes count only when the record was last updated less than two minutes before the capacity snapshot started, or at any time after it. That two-minute tolerance absorbs clock offset between the host that wrote the record and the host that took the snapshot.

- A `create_vm` that places for the first time now leaves no window for a peer to slip through, because the journal read, the ranking, and the record write all run inside the journal's exclusive index lock. A retry is different, since it lists the journal with no index lock held, re-plans from that listing, and then writes the new attempt under its own record lock, so it keeps a narrow window of its own. On `create_disk` the read runs before planning while the record is written after it, so a persistent set with more than one member keeps a window of the same shape in this release.

  The journal already holds the index lock for the whole of its own body on a disk create, while discovery, ranking, and the PVE calls all run outside it, so a later release can close these windows the way the first VM placement closes its own.

- Sibling bytes change feasibility under every strategy, but they change the order only under `least_utilized` and `weighted_free_space`. A `spread` set ranks by rendezvous hash and never reads free space, so it gets its spreading from anti-affinity instead.

  The `pve-cid storage-plan` diagnostic opens no journal for its ranking, so it charges no in-flight sibling. It reads no sibling record either, which leaves every sibling count empty and skips the band partition altogether, so what it explains is the strategy's own order over all the candidates. A placement it explains can therefore differ from one a live create makes while peers are in flight.

- A storage set can now declare `anti_affinity`, which asks the planner to prefer a member that does not already hold another allocation of the same instance group. `scope` takes `instance_group`, `deployment`, or `none`, and `utilization_band_pct` takes an integer from 0 to 100. The defaults are `instance_group` and 20 points, and they are read where they are used rather than written onto the set, so a set that declares nothing spreads by default while its policy fingerprint and its context-override cache key stay byte-identical to what they were before the upgrade. The opt-out for one set is `anti_affinity: {scope: none}`. Every `create_vm` plan now records the group its allocation belongs to as `deployment--<name>/instance-group--<name>`, each half sanitized to the CPI's tag alphabet. The group is empty whenever the environment names no instance group, which is the usual `bosh create-env` shape. Records written before this release carry no group, so they count for nothing and a namespace starts spreading from its first create after the upgrade. The preference is bounded by the band. Candidates whose projected utilization sits within the band of the least utilized candidate are bucketed by sibling count. Each non-empty bucket is ranked on its own with the set's strategy, and the buckets are concatenated with the fewest siblings first. Candidates outside the band are ranked once and appended after them, so a much fuller member never wins on a sibling count alone. The partition orders the root disk of a `create_vm` only, and never a dedicated ephemeral disk or a `create_disk`. The winning candidate's reason string now names the band, the bucket, and the sibling count. One consequence is worth planning for. Source choice is per target, so a partition that promotes a member holding no replica of the stemcell turns a linked clone into a full clone, with only a warning in the CPI log. That makes the replica listing a precondition of any deploy onto a share that has not hosted that stemcell before. See [Spread an instance group across members](docs/multi-storage-placement.md#spread-an-instance-group-across-members).

- `storage-journal audit` now timestamps every retained record and says whether its state charges bytes against new creates. Each record summary gained `CreatedAt` and `UpdatedAt` in RFC 3339 and a boolean named `charging`, which comes from the same predicate the planner uses, so the operator's view cannot drift from the ranking's arithmetic. The output also gained a `charging_summary` object holding the number of charging records, the identifier of the oldest one, and its age. Nothing ages a record out of an in-flight state, so a CPI that dies between writing its record and running its first step leaves a `planned` record charging its bytes against every later create until an operator resolves it. This command is what names that record. The output is JSON and the new fields are additive, so a consumer that decodes loosely keeps working while one that decodes strictly has to be updated. See [A crash-abandoned allocation keeps charging capacity](docs/troubleshooting.md#a-crash-abandoned-allocation-keeps-charging-capacity).

### Changed

- A Director must not roll back below this release while grouped allocation records are non-terminal. A plan this release writes for a `create_vm` carries the allocation's anti-affinity group whenever that group is non-empty, and a CPI decodes its own plans with unknown fields disallowed, so an older binary reading one of those plans fails it with an audit-required error rather than mis-parsing it. Every plan carrying a non-empty group is affected that way. A plan whose group is empty omits the field altogether, which is the usual `bosh create-env` shape, and an older binary decodes such a plan without trouble. Records an older binary wrote carry no group at all and are unaffected too. The same hazard does not arise again in the other direction, because each create now decodes a sibling's plan leniently and only its own plan strictly, so a field a later release adds to the plan does not break this release's creates.

- `create_disk` now opens the allocation journal before it plans, so the admission audit that authorizes the create scans every node in the cluster rather than only the nodes the discovered inventory covered. That costs one cluster-wide scan per disk create, and it strengthens the absence proof the audit rests on. The narrower node lists that decide where a disk lands are unchanged, because they follow the hinted VM's node or the availability zone's candidates, and they are the planning scope rather than the audit scope.

- The `cpi.storage.candidate_rejections` counter reads higher after this release without anything being wrong. Sibling bytes push more candidates through the capacity gate's rejection path, and that gate now records a rejection where it used to drop a member silently, so a member the ceiling excluded leaves a trace in the plan instead of dropping out of it unremarked.

## [0.7.3] - 2026-09-15

### Added

- An empty storage content listing no longer proves an absence on its own. The CPI settles whether a volume is gone by reading the storage's content listing, and on NFS and CIFS it trusts an empty listing, because PVE refuses to activate those storages when their backing is unreachable. An export that mounts but serves the wrong tree defeats that rule, because the mount succeeds and the listing comes back empty while the real content sits somewhere else. That is how a filer which lost its dataset, and now exports the empty parent directory, looks from the API. When a listing comes back empty on a storage the CPI would otherwise trust, it now asks three sources whether anything contradicts that emptiness, and it stops at the first source that answers. The cluster's VM configs come first, and a config that still references a volume on the storage is a contradiction. That check costs no extra call on `delete_disk`, `attach_disk`, and a `create_vm` carrying `disk_cids`, because those calls already read every VM config to find the disk's holder, and it has nothing to say on the callers that never run such a scan. The allocation journal comes next, and it contradicts an empty listing when the CPI recorded allocating some other volume on the storage and never recorded deleting it, because the journal still holds an open allocation record for the disk whose absence we are proving, whether that volume is gone or not, so that disk never counts against itself. That source answers on every caller without touching the cluster. Both record-based sources judge per node on node-pinned storage, because a storage name such as `local-lvm` is a different tree on every node, and on shared storage a record from any node counts. The storage's own status on the node comes last, because it is the only source that spends an API call, and it contradicts an empty listing only when the storage is not active on that node. A used figure cannot contradict a listing, since PVE reports the used bytes of the whole mounted filesystem while the listing covers only the content types the storage is configured for, so one export carrying a backup storage's `dump` directory beside an images storage would have made every honest empty listing on the images storage look contradicted. A status that reports at least 1 GiB in use with nothing listed is logged as a warning naming the storage, the node, and the byte counts, and the proof then succeeds. A wrong-tree export that no config references and no journal record names therefore still proves absent, and that warning is the trail to it. A source that fails rather than answers leaves the absence unproven, and every refusal names the source and what it saw. A storage that nothing contradicts still proves an absence exactly as before, and the rule for a plain `dir` storage with no `is_mountpoint` is unchanged. See [Absence unproven because an empty listing was contradicted](docs/troubleshooting.md#absence-unproven-because-an-empty-listing-was-contradicted).

### Fixed

- The local-backend cluster scan now classifies a storage from a live read of the PVE storage index rather than from the classification its backend was built with. That scan proves a volume absent on node-pinned storage, and how much an empty content listing proves depends on the storage's type and on its `is_mountpoint` flag, so a stale classification decided the question. One CPI process can outlive an operator's `storage.cfg` edit, because the multi-request stdin loop keeps a process alive across calls while the classification cache holds its entries for a TTL, and `pvesm set <storage> --is_mountpoint yes` now takes effect on the next call instead of waiting for that cache. The live read happens at most once per backend and only after a point probe has already failed, so a scan that never reaches a content listing never pays for it. When the index lookup misses, the CPI hands the backend a fabricated record holding nothing but the storage name. The scan used to report that as a successful classification of a storage with no type, which the proof read as an unrecognized storage rather than as one we never classified at all. It now reports no classification, which leaves the absence unproven and keeps the caller failing closed.

- `delete_disk` no longer refuses a parked-anchor disk whose volume is already gone from `dir`, NFS, or CIFS storage. PVE does not answer a missing file on those backends with a 404. It answers with an HTTP 500 that names `volume_size_info` and reports no format. That same wording also covers a denied read, a stale NFS handle, an unmounted export, and an I/O error, so the CPI could not read the reply either way, and it failed closed. The CPI now settles the question with a storage content listing rather than with the error text. A volid that is absent from a listing the CPI was allowed to read counts as proof that the volume is gone. The same proof unblocks `has_disk`, which `bosh cck` relies on to learn that a disk no longer exists. It also unblocks the stale-unused-slot check in `delete_vm` and the local-backend cluster scan that used to turn a deleted volume into a retriable error. An absence the CPI cannot prove still leaves the refusal in place, and the CPI now logs a warning that names why the proof did not land. Proving an absence needs `Sys.Audit` at `/access` on the CPI's token, because the listing has to be one PVE did not filter by permission. On a plain `dir` storage with no `is_mountpoint`, an empty listing counts as unproven. When the mount under such a storage drops, PVE lists the storage as empty rather than failing the call, so operators who run `dir` storage should set `is_mountpoint` on it.

- `create_vm` and `attach_disk` now report that the data is gone when a disk's CID promises a parker anchor, no VM in the cluster references the volume, and the volume is provably not on storage. Both calls used to point at `pve.parked_anchor_strict: false`, which cannot bring back a volume that is not there. The new message asks the operator to remove the disk from the Director's records with `bosh -d <deployment> cck`, or to drop it from the create-env state file, and then to redeploy so that a fresh disk is created. The refusal stays permanent and non-retriable, and an attach whose volume is not provably gone keeps the original message and its strict-mode advice.

- The orphan sweeps that run after a failed `create_disk` or a failed ephemeral disk create now use the same content-listing proof to decide whether a partial volume was left behind. Both used to ask the bare existence probe. On `dir`, NFS, and CIFS storage the `volume_size_info` reply made them skip a sweep they should have run, and on `lvmthin` and `zfspool` the missing-volume text did the same, so the partially committed volume stayed on storage. A volume the listing shows is swept as before, a proven absence skips the sweep, and an absence the CPI cannot prove skips it with the same warning as before, which now names where the CPI looked.

## [0.7.2] - 2026-09-15

### Added

- A VM the CPI creates now records the stemcell it booted from, as a `stemcell--<name>-<version>` tag and as a `bosh_stemcell` key in the VM's Notes, which covers every VM built from a stemcell the CPI uploaded. Nothing on the PVE side named the stemcell before, because a Director's `set_vm_metadata` payload carries the deployment, instance group, job, index, and name, and never the stemcell, so the only way to tell which guests still ran an old stemcell after a bump was to log into each one. `create_vm` is the one call that knows, so it writes both. A create-env Director gets the same treatment, and that is the case where no `set_vm_metadata` call arrives at all. The tag uses the CPI's usual tag alphabet, so `bosh-openstack-kvm-ubuntu-noble-1.585` is tagged `stemcell--bosh-openstack-kvm-ubuntu-noble-1-585`; the Notes record keeps the exact version alongside the full stemcell CID, its kind, and its content sha8. `set_vm_metadata` carries the label into the regenerated human-readable notes as a `stemcell:` line, and never strips the tag, so both survive every later metadata sync. Both are written once at create time, so a VM whose tag names an old stemcell genuinely has not been recreated since. VMs created by an earlier release carry neither until they are recreated.

  The identity comes from the stemcell's qcow2 filename, which is always present for a `:heavy:` stemcell the CPI uploaded, and present for a `:light:` one only when the operator named the file as `bosh-stemcell-<name>-<version>-<sha8>.qcow2`. A file named anything else, a derived label longer than 96 characters, or one carrying anything outside `A-Za-z0-9._-`, yields no tag and no record rather than a guess. - `set_disk_metadata` now refuses an operator disk tag whose key would render the `stemcell--` prefix, the same way it already refuses one that would render `director--` or `deployment--`, so a tag keyed `stemcell` cannot overwrite the record of what a guest booted from. The refusal is logged and applies whatever the key's case.

### Fixed

- The allocation journal no longer refuses a record file because another process was saving it at that moment. The safety check that rejects a journal file something else also hard-links tested the link count against exactly one, and a file being replaced by an atomic rename is briefly reachable by name while its link count reads zero, so a reader that looked at the wrong instant was rejected as multiply linked when nothing had linked it at all. On a shared journal that surfaced as a `create_vm` failing outright, because the managed storage path inspects the journal before it does anything else. The check now rejects a link count above one, which is the hard-link case it always claimed to catch and the only one an attacker can create; a reader that loses the rename race reopens the file instead. Measured on APFS, the rejection fired on roughly one lookup in five hundred under concurrent load and now does not fire at all. A hard-linked record is still refused, and a test now pins that.

### Changed

- `create_vm` writes the pool-membership and stemcell records in a single description update rather than one per record, so provenance costs one config read and one write per VM on a deploy of any size. That write now goes to the unguarded PVE client. On the managed storage-placement path it previously rode the allocation guard, where a transient failure on a purely advisory description update could poison the allocation, fail a `create_vm` that had otherwise succeeded, and leave a record in `ReconciliationRequired` for an operator to clear.
- The stemcell tag is appended after the advertised-route provenance tags rather than ahead of them. The 350-byte tag budget truncates from the tail, and an evicted `advrt-` tag is an SDN subnet `delete_vm` can no longer withdraw, so cleanup-critical tags keep their place and the stemcell label is the first thing to go. `create_vm` warns when the cap drops the stemcell tag, naming the tag, and that VM still answers a `bosh_stemcell` Notes query even though a tag query misses it. `set_vm_metadata` still names every dropped entry in a warning.

## [0.6.0] - 2026-09-14

### Added

- Multi-storage placement spreads a deployment's disks over a named group of shared NFS storages, rather than over the single storage name every role used to resolve to. `pve.storage_sets` declares the groups. A storage set names existing PVE storage IDs, either as a list or through a Go RE2 `name_pattern`, and pairs them with a versioned selection strategy. Three strategies ship at version 1. `spread` places by deterministic rendezvous hashing, `weighted_free_space` biases each pick toward the members with more room, and `least_utilized` takes the member whose projected utilization after the allocation is lowest. A set can narrow what it will accept through `types` (which has to be exactly `[nfs]`), `shared` (which has to be true), `min_free_mb`, and `max_utilization_pct`, and it can carry an `encrypted` assertion the operator makes about the backing. `pve.ephemeral_storage_set` binds the placement of new VM root disks and dedicated ephemeral disks, `pve.persistent_storage_set` binds every new persistent disk including one created with no VM to hint from, and `pve.root_storage_set` splits the root disk off from the ephemeral one for a deployment that wants them apart. A `disk_type`'s own `storage_set` cloud property then picks a named set inside whichever global boundary applies, so a deployment can steer one disk class without moving the rest. `pve.storage_capacity_domains` groups storage IDs that share physical capacity, so a set whose members live on one filer counts that free space once. It takes the most conservative observation among the members rather than counting the same space once per member. `pve.require_disjoint_storage_sets` keeps persistent disks and VM-lifetime disks on different backings, and it defaults to true whenever both global bindings exist, so an operator who wants them to overlap has to say `false` and accept the combined capacity accounting that comes with the overlap. `pve.storage_placement_namespace` names the allocation authority that set-managed placement records its allocations under. `pve.storage_allocation_journal_dir` gives the CPI an absolute, durable directory for the allocation journal it keeps while a set-managed placement is in flight, and on a Director that directory belongs on the persistent disk at `/var/vcap/store/pve_cpi/allocations`. A set-managed allocation refuses to run until the namespace is not blank and the journal directory is an absolute path the process can lock. `pve.storage_status_max_age_seconds` bounds how stale a storage observation may be when a strategy reads it, accepts 1 through 60 seconds, and defaults to 5 when it is omitted. Eight of the nine properties are overridable per cpi-config entry, as `pve_storage_sets`, `pve_storage_capacity_domains`, `pve_ephemeral_storage_set`, `pve_persistent_storage_set`, `pve_root_storage_set`, `pve_storage_placement_namespace`, `pve_require_disjoint_storage_sets`, and `pve_storage_status_max_age_seconds`, so one cluster in a multi-cluster deployment can run on storage sets while the rest stay on their scalar storage names. The journal directory is a process-level setting that no request context can redirect. Strict validation at load rejects a set that gives both `names` and `name_pattern` or neither, a pattern that does not compile, a blank or duplicated storage ID, a `types` list that is anything other than `[nfs]`, `shared: false`, an unknown strategy or version, a `max_utilization_pct` outside 1 through 100, a binding that references a set nobody defined, a capacity domain with no members, and a storage ID two domains both claim. Nothing here changes a deployment that sets none of these properties, and that deployment keeps resolving storage from `pve.vm_storage`, `pve.disk_storage`, and their cloud-property layers exactly as it did before. Declaring a set that no binding references does not turn placement on either. See [Multi-storage placement](docs/multi-storage-placement.md) for the model and the worked scenarios under `manifests/examples/multi-storage-placement/`.
- New properties `pve.parker_prefix` and `pve.parker_pool` name the parker VMs that hold detached persistent disks and place them in a PVE resource pool of their own. A parker is called `<prefix>-parker-<vmid>`, and the prefix resolves from `pve.parker_prefix` when it is set, from `pve.vm_prefix` when it is not, and from the literal `bosh` when neither is set, so a deployment that sets neither property still gets the `bosh-parker-<vmid>` names that every earlier release produced. A value set on `pve.parker_prefix` itself has to match `^[A-Za-z0-9]([A-Za-z0-9-]*[A-Za-z0-9])?$`, stay within 46 bytes, and keep clear of the `bosh-lock-` prefix that belongs to the cluster-lock sentinel pools, while a prefix that arrives by inheritance from `pve.vm_prefix` is sanitized to the VM name character set and truncated to 46 bytes with a warning instead, since that property answers to rules of its own. `pve.parker_pool` names the pool as a template whose only token is `{prefix}`, which stands for the resolved parker prefix and not for the `{prefix}` of `pve.vm_pool_template`, and its default `{prefix}-parker` renders to `bosh-parker` on a stock deployment. The CPI creates that pool the first time it needs one and writes into its comment the same `managed by bosh-proxmox-cpi` provenance it writes on every other pool it owns. A configuration whose parker pool renders onto `pve.vm_pool` or `pve.stemcell_template_pool` is refused at load, and a workload pool that renders onto the parker pool is refused at `create_vm`, because a workload VM sharing the parker pool would hold that pool open long after the deployment that created it is gone. Both properties are overridable per cpi-config entry, as `pve_parker_prefix` and `pve_parker_pool`, and `pve.parker_pool: ""` turns parker pool assignment off altogether. See [Parker VM properties](docs/persistent-disk-strategy.md#parker-vm-properties) for the resolved shapes and [PVE API permissions](docs/pve-api-permissions.md) for the grants the pool needs.

### Changed

- The library behind the OCI stemcell source, go-containerregistry, moves from v0.22.0 to v0.22.1. That patch release verifies a manifest against the digest algorithm the reference names instead of assuming SHA-256, refuses an image reference that carries an `http://` or `https://` scheme with a message that says to drop it, no longer writes an empty `auth` field into a Docker config that has no username or password, and classifies loopback, link-local, and private registry addresses before it follows a redirect or a bearer challenge to them. Pulling a stemcell from a public registry behaves as before.
- Parkers now take their name from the resolved parker prefix, join the pool `pve.parker_pool` names, and carry a `vm-prefix--<prefix>` identity tag. The rendered default is unchanged only for a deployment that leaves `pve.vm_prefix` empty. A deployment that already sets `pve.vm_prefix` and does not set `pve.parker_prefix` inherits it here, so every parker created from the upgrade onward is named `<vm_prefix>-parker-<vmid>` and lands in a `<vm_prefix>-parker` pool, and nothing renames the parkers that same deployment created before the upgrade. Such a cluster carries both shapes side by side, and no deployment fills both. A park reuses only a parker whose prefix matches the deployment's resolved prefix, so two deployments share parkers only when their resolved prefixes are equal, and a deployment creates a fresh parker rather than filling a parker that another prefix created. A parker's prefix comes from its `vm-prefix--<prefix>` tag, or from its `<prefix>-parker-<vmid>` name when it carries no such tag, and a parker that has neither counts as a `bosh` parker, so an untagged parker from before this release belongs to the `bosh` prefix. The old parkers keep holding the disks they already hold, and those disks attach, unpark, and delete exactly as they did. Pool assignment happens in a best-effort sweep that runs after every successful park, once the guarded allocation window around that park has closed. It creates the pool when the pool is missing. It then asks the pool itself which parkers already belong to it, rather than trusting the cluster index, which lags by minutes, and it assigns the parkers on that node that share the deployment's resolved prefix and are not in the pool yet. Every failure in the sweep, a permission denial among them, logs a warning and leaves the park itself successful, so the sweep can never fail a `create_disk` or a `detach_disk`. Nothing moves a parker out of a pool it already belongs to, so renaming `pve.parker_pool` later leaves the existing parkers in the old pool until an operator moves them by hand, and the disk movers that carry a disk across nodes take the same prefix but stay out of every pool on purpose. The reduced pool-scoped token described in [PVE API permissions](docs/pve-api-permissions.md) still cannot park, because the parker create passes its tags and PVE checks those against `/vms/{vmid}` before any pool registration, so pool membership arrives too late to stand in for a `/vms` grant. The pool shows up in three other places. The empty-pool reaper refuses the parker pool by name, alongside `pve.vm_pool` and `pve.stemcell_template_pool`. The startup preflight probes the parker pool whenever the parked strategy is on, and it treats a permission denial there as a warning rather than as the boot failure that a denial on either workload pool still is. `scripts/disk-audit` reports each parker's pool in its table and in every finding it raises. The `vm-prefix--` tag key joins the reserved set the CPI rewrites on every `set_vm_metadata` call, beside `director--`, `deployment--`, `instance-group--`, `job--`, and `index--`. A parker carries `vm-prefix--<prefix>` behind its `director--` tag from the moment it is created, a workload VM picks the tag up at its first `set_vm_metadata`, and filtering the PVE UI on one prefix therefore shows the workload VMs that share it and the parkers holding their detached disks in a single listing. A tag an operator supplies under that key is refused the way a `director--` tag always was, and `set_disk_metadata` drops any reserved key out of a disk's tags with a warning rather than letting it overwrite the holder VM's own. Because a parker's tag list gained a member, the managed-disk readback guard now compares the tags it sent against the tags PVE hands back as sets rather than as ordered strings, so a reordering by PVE no longer reads as a write that did not take. No migration is needed for any of this. A deployment that sets `pve.vm_prefix` and wants the old parker names back, and wants its older parkers filling again, sets `pve.parker_prefix: bosh` explicitly, and a deployment that wants no parker pool at all sets `pve.parker_pool: ""`.

### Fixed

- The `pve.vm_disk_format` job property now reaches the VM root disk and the ephemeral disk. `create_vm` resolved its format from the call's `cloud_properties`, then from a `vm_type` or `disk_type` profile, and then fell straight through to the built-in `qcow2`, skipping the job property entirely. `create_disk` and `attach_disk` had always read the same field, so the two VM-owned disks were the only ones ignoring it. An operator whose `vm_storage` is block-native (`lvm`, `lvmthin`, `zfspool`, `rbd`) sets the property to `raw` because those pools reject qcow2, and unless a cloud-config `vm_type` repeated the value, the CPI asked PVE for a format the pool cannot hold. A `cpi-config` entry overriding `vm_disk_format` for its own cluster was stranded the same way. The property now sits between the cloud-property layers and the `qcow2` default, so an explicit cloud property still wins and an unset property still lands on `qcow2`.

### Documentation

- [Operations](docs/operations.md) gains a section on where a disk format comes from, covering the four-rung resolution order, the rule that block-native pools always record `raw` while file-backed pools get the resolved format verbatim (and carry it in the volume filename), and the fact that the CPI never downgrades a requested `qcow2` to `raw`. Proxmox supports qcow2 on NFS and the CPI classifies NFS as file-backed in every format decision, so a raw volume on an NFS pool means raw was requested; the section explains how to find the layer that asked for it, starting with the `disk_type` the deployment actually uses rather than the CPI job properties.

- The Dynamic Load Balancer's cluster CRS check now reads the setting PVE actually returns. `GET /cluster/options` hands back the parsed `datacenter.cfg`, so `crs` arrives as an object keyed by sub-option with its flags as unquoted integers, not as the single property string the check decoded. That decode failed on every cluster that had a CRS setting configured and was discarded silently, leaving the CPI to believe no CRS setting was configured at all. With `pve.placement.dlb.manage_cluster_crs` false, the CPI warned that CRS was not dynamic, and printed an empty current setting, on clusters where it was already correct. With the knob true, the CPI never recognized the required setting as already present, so it rewrote the cluster-wide CRS option on every `create_vm` that registered a DLB member, and because the merge started from an empty setting, any other CRS sub-option the operator had configured was dropped on the first such write. PVE's API is Perl-backed, so a boolean the spec declares arrives as `1`, `true`, or `"1"` depending on the endpoint and version, and counters such as `maxmem`, `avail`, or an SDN `tag` sometimes arrive as quoted strings. Our structs for `/cluster/status`, `/cluster/resources`, `/nodes/{node}/qemu`, `/nodes/{node}/storage`, `/storage`, `/pools/{pool}`, `/cluster/sdn/zones`, and `/cluster/sdn/vnets` decoded those fields, and every `vmid`, as strict Go `bool` and `int64`, and the loops around them dropped any row that failed to decode without a trace. Those reads now go through one helper that renders any scalar value as the string PVE would show, so a numeric-shaped name, tag, or description is handled the same as any other.

The relaxation covers every `create_stemcell` mode the same way (tarball upload, `source_url` server-side fetch, `image_url` CPI-side fetch, and pre-uploaded `image_id`), a `stemcell_template_node` that cannot read the node-local staging pool is rejected with guidance instead of failing opaquely at template build, `delete_stemcell` sweeps stray per-node qcow2 copies that the replica list cannot name, and a `create_vm` import fallback on a node the staging pool cannot serve now returns a retriable error explaining the topology and the rebuild remedy instead of misleading re-upload guidance.

- New property `pve.node_endpoints_discovery` controls `/cluster/status` node-address discovery for direct-to-node uploads independently of `verify_ssl`. Unset preserves the existing default (discovery is on exactly when `verify_ssl` is `false`); set it to `false` to keep uploads on the configured endpoint when the discovered corosync addresses are not reachable from the CPI's network, or to `true` to allow discovery on a `verify_ssl: true` deployment whose node certificates cover their cluster addresses.

### Fixed

- Transport and API errors no longer reach the Director with the wrong retriability. Mid-lifecycle connection races (a server-closed idle connection, `net.ErrClosed`) now classify as transient in the CPI's own stemcell-fetch client, not only inside the SDK; a resolved non-429 4xx is a permanent verdict even when its body contains a pushback phrase such as "got timeout"; failed task exits under adaptive polling route through the same classifier as the default poller, and a non-OK task exit delivered as a bare status field rather than an SDK error now routes through it too, so storage-lock and quorum contention in a task exit stays retriable; node-scoped template lookups and the offline-member status probe retry transient faults like every other cluster read; two internal classifier wraps now preserve the underlying error chain, keeping downstream not-found and HTTP-status detection working; and a dozen terminal wraps that flattened an established retriable classification into a permanent cloud error now preserve it, so exhausted-but-transient storage faults surface as retriable to the Director. The JSON-RPC dispatcher's fallback consults the transient classifier before minting a permanent error from a raw transport failure.

- Every destructive branch now proves VM absence with authoritative per-node config probes. The `/cluster/resources` index can trail node-local state by minutes, and an index miss was read as "the VM is gone" by `delete_vm`, `has_vm`, `get_disks`, `set_vm_metadata`, `reboot_vm`, `delete_snapshot`, `attach_disk`, and `detach_disk`. On a miss, cluster membership is now enumerated from corosync-backed `/cluster/config/nodes` and every node's own config is probed; absence is concluded only when every node answers cleanly, and any unreachable node yields a retriable error instead. On a standalone (never-clustered) host, whose corosync node list is empty, membership enumeration falls back to the node listing, so absence proofs and `delete_stemcell`'s cluster-wide template sweep complete there instead of refusing forever. The `delete_vm` straggler sweep re-reads the authoritative config and re-tests its tags before destroying, so a reused VMID with a stale index row is never destroyed, and `delete_stemcell` refuses the branch that deletes the backing qcow2 unless its cluster-wide template sweep completed.

- Retried PVE mutations no longer replay an already-committed request destructively. A POST can commit server-side while its response drops in transit; each retried site now converges on the goal state, sweeps its own committed partial, or adopts the resource it created: `resize_disk` re-reads the size and treats at-target as success instead of re-submitting a landed grow; the stemcell upload re-awaits its own task after a drop and sweeps the committed partial before re-uploading; `reboot_vm` and the `create_vm` start convert a failed start into success when the VM is already running, and a start answered without a task to await is accepted instead of failing; `snapshot_disk` accepts a fully committed snapshot on replay; the disk-migrate mover is adopted only on an exact nonce match; and a destroy rejected by a config lock waits a bounded window for the lock to clear and re-issues once before tagging the VM for the reaper.

- Cleanup paths retry through the same storage-lock contention that triggered them. Rollback destroys, template destroys, orphan and ephemeral volume sweeps, replica sweeps, pool operations, the disk-migrate submit, and the unused-slot detach sweep were all single-shot, so one cfs-lock timeout permanently leaked the resource being reclaimed; each now rides the storage-lock retry curve with a role-scoped attempt budget, and resolved 500-text verdicts (pool already exists, VM already a pool member, config already gone) short-circuit as answers instead of spending the budget.

- Cluster-wide decision paths read authoritative per-node guest listings instead of the lagging index. The VMID allocator unions the per-node listings into its used-set, so a VMID a peer created moments ago can no longer be reallocated inside the index lag window; the `create_vm` rollback sweep refuses to destroy a VM whose identity it cannot prove, and parallel attempts carry an agent-derived name discriminator so one instance's sweep can never match a sibling attempt's live VM; disk-holder scans, the advertised-route sole-owner refcount, template lookups, and the IP-conflict guards all enumerate per node, with absence proofs failing loudly on any unlistable member and advisory readers tolerating members the quorate cluster itself reports offline; `delete_stemcell` compares director refs through the create-env sentinel and feeds its orphan prune from the VMIDs this call destroyed; and anti-affinity rules drop a member only when a complete enumeration proves its guest gone. A member the quorate cluster itself reports offline no longer blocks disk operations cluster-wide: a disk located on any listed node proves its single holder, and a disk-not-found verdict is concluded only when no member had to be excluded, with a retriable error otherwise.

- A lagging `/cluster/resources` index no longer hides a freshly built cache template. On a loaded cluster the index can trail a just-frozen template by minutes, and both consumers of the cluster-scoped sha-tag lookup mistook that lag for absence: `create_vm` fell through to the import fallback (which fails outright when the staging qcow2 lives on another node's local storage), and `delete_stemcell` took the no-template branch, deleting the staging qcow2 while orphaning the live template. The sha-tag lookup itself now reads authoritative `GET /nodes/<node>/qemu` listings, which serve node-local guest configs and do not lag, so neither consumer touches `/cluster/resources` at all; on top of that, `create_vm` probes the placement node and the template's home node (`stemcell_template_node`, or the configured `node`) inside its bounded re-check and clones the template it finds, and `delete_stemcell` sweeps every cluster node (create_stemcell can legitimately build on a non-default node) so the template and all its per-node replicas are found and destroyed.

- The `create_vm` rollback no longer destroys an attached persistent disk. When a create failed after the persistent disk was already attached (agent configure, VM start, or a post-start check, including the node-fallback retry), the rollback purged the VM with disk destruction enabled and PVE destroyed every referenced volume, including the persistent disk a `bosh recreate` was re-attaching. The rollback now detaches foreign persistent disks to safety first, exactly as `delete_vm` does, and when that protection cannot complete it preserves and tags the VM instead of purging it — an orphaned VM is recoverable, a purged persistent volume is not. The fast-path delete's straggler sweep gained the same protection: a `bosh-deleting` VM whose foreign-disk detach failed on the original delete is now deferred to the `delete_vm` retry instead of being destroyed with the disk still attached. Both paths also treat pmxcfs's "Configuration file ... does not exist" answer as the vanished-VM condition it is, rather than refusing to proceed.

- A connection dropped mid-request is retried instead of failing `create_vm`. Under a bursty deploy pveproxy can close an in-flight connection (the configdrive ISO upload was the live victim, surfacing as `Post ...: EOF` after one attempt), and that shape fell through every transient classifier: the upload was not retried and the error reached the Director as non-retriable. Mid-request drops (EOF, unexpected EOF, connection reset, broken pipe) now classify as transient transport faults, so the configdrive upload retries with a fresh body stream (clearing the target filename first, in case the dropped request actually committed the file; a clear that itself hits a retryable fault rides the same backoff curve instead of pressing into a guaranteed duplicate rejection), and an exhausted retry budget surfaces retriable.

- Storage uploads no longer traverse the cross-node pveproxy hop, and they carry their own retry budget. An upload targeting storage on a node other than the configured endpoint was proxied by the endpoint node's pveproxy to the target node's pveproxy, and under a many-VM deploy burst that hop shed connections mid-request (`EOF`) while uploads to the endpoint node itself kept working; the roughly one-minute upload retry window then ran out before the burst did. Stemcell image and per-VM ConfigDrive ISO uploads now dial the target node's own pveproxy directly, resolving its address from the new `pve.node_endpoints` map (node name to `host` or `host:port`; explicit entries always win) and falling back to `/cluster/status` discovery when `verify_ssl` is `false`, since the discovered corosync address is usually absent from stock node certificate SANs. A routed attempt that fails TLS certificate verification, any other TLS handshake failure (a non-TLS listener answering the routed port, for example), the dial itself, or a network fault while the routed connection is still being established logs a warning, falls back to the configured endpoint, and skips that node's direct route for the rest of the process, so a wrong entry degrades to the proxied path instead of failing the deploy. Map entries are validated at config parse; a node name or address with surrounding whitespace is rejected. The uploads also moved to a dedicated retry class, `pve.retry.storage_upload.max_attempts`, whose built-in budget of 30 attempts (roughly six minutes on the transient curve, roughly twelve when storage-lock contention dominates) outlasts a burst window the previous 10-attempt default did not.

- Surfaced errors no longer print the underlying cause twice. Wrapped errors carried the cause text inside the wrap message while the error chain appended the same text again, producing shapes like `failed to upload ... EOF: failed to upload ... EOF` in Director output (and, on some `create_vm` paths, three copies). Wrap messages now state only their own context and the chain renders the cause exactly once; classification and retriability are unchanged.

- An unresolved task poll timeout is no longer mistaken for a transport fault. When polling a PVE task times out without a verdict the task may still be running, but the timeout satisfied the transient-transport classifiers, and the disk-move, configdrive-upload, snapshot, and stemcell-template-freeze sites resubmitted their mutation on retry, double-applying it (and, for the configdrive, deleting an upload still in flight). The timeout now carries its own classification, retriable to the Director but not transport-shaped, and each of those sites re-awaits the original task on the next attempt instead of resubmitting; the configdrive target sweep runs only on evidence that the upload actually failed or its request dropped.

- Pool assignment no longer reports success on an unconfirmed membership verdict. When the pool-membership probe could not answer (a token missing `Pool.Audit`, for example), `create_vm`'s pool assignment treated the ambiguity as "already a member" and returned success with the VM outside its pool. The probe's failure is now classified: a permanent denial falls back to the cluster-index check, a transient fault retries, and a definitive "not a member" answer from PVE's own membership endpoint is never overturned by the lagging cluster index.

- Exponential retry backoff saturates at its configured ceiling instead of overflowing into a zero-delay retry storm at very high attempt counts, and config validation now caps every `pve.retry.*.max_attempts` at 100.

- Ephemeral-disk allocation backs off in place on storage lock contention. Parallel `create_vm` calls allocating ephemeral volumes on one shared pool contend on the cluster storage lock, and the losers failed the whole call back to the Director, which re-ran clone, boot, and configure only to re-enter the same contention window. The allocation now retries in place on the same storage-lock backoff curve `create_disk` uses (with the default attempt budget), and when every attempt fails, a volume the failed request may still have committed is swept best-effort before the error surfaces, so the Director's redo does not leave an orphan behind. A replayed attempt that finds the volume its own dropped request already committed adopts it and proceeds instead of spending the rest of the budget colliding with it.

- Storage lock contention on shared pools is retried instead of failing the deploy. PVE's cluster-wide storage lock surfaces as `cfs-lock 'storage-<pool>' error: got lock request timeout` when concurrent clone, create, or destroy tasks contend on one shared pool — routine during mass VM creation from a single template on RBD. That shape now classifies as a transient storage-lock timeout everywhere the existing file-lock timeout does, so `create_vm` retries the clone rather than surfacing a terminal error.

- Retriable errors now cross the wire as classes the Director recognizes, so its own retries engage. The dispatcher previously serialized `Bosh::Clouds::RetriableCloudError`, which the Director knows only as an abstract base class: it rejected the response as `Unknown CPI error`, discarded `ok_to_retry`, and failed the task on the spot, so a transient fault that outlived the CPI's internal retries (a mass-create burst exhausting the configdrive upload budget, for example) killed the deployment instead of triggering the Director's create retry. A retriable error escaping `create_vm` now serializes as `Bosh::Clouds::VMCreationFailed` with `ok_to_retry: true`, which the Director's create step retries up to `max_vm_create_tries` (default 5) with fresh CPI calls; retriable errors from other methods serialize as `Bosh::Clouds::CloudError` with the flag preserved, since the Director has no retry loop for them. The same translation maps the internal `DetachedDisk` type to the Director's `DiskNotAttached` and the internal stemcell-validation and snapshot-guard types to plain `CloudError`, so no CPI response can surface as `Unknown CPI error`.

- A destroy task that completes with `WARNINGS: N` no longer fails `delete_vm`. PVE ends `qmdestroy` with a warnings exit when the VM was removed but a disk could not be deleted under storage-lock contention ("Could not remove disk ..., check manually"); the plain task await treated any non-OK exit as failure, turning a completed delete into a CPI error. Both await paths now accept completed-with-warnings, matching the PVE UI's own reading; any leftover volume is left to `scripts/disk-audit`.

### Changed

- The release is renamed from `bosh-pve-cpi` to `bosh-proxmox-cpi`; this is the first release published under the new name, and the GitHub repository moves to `fivetwenty-io/bosh-proxmox-cpi-release` (old URLs redirect). To a Director the renamed release is a new release, and the tarball's embedded release name must match the manifest's release name exactly or create-env/delete-env refuses with a name-mismatch error. `manifests/bosh/cpi.yml` sets the release name from a new var, `((pve_cpi_release_name))`, instead of a literal string. `scripts/bosh create-env` and `scripts/bosh teardown` read the name from the tarball's `release.MF` and supply the var automatically (`bosh-proxmox-cpi` for a release built from this repo, `bosh-pve-cpi` for a published tarball through v0.4.0), so operators using `scripts/bosh` need no manifest edits. A hand-rolled ops file that skips `scripts/bosh` must supply `pve_cpi_release_name` itself: `manifests/bosh/vars.yml.example` now sets a `bosh-proxmox-cpi` default, which we override to `bosh-pve-cpi` when deploying a v0.4.0-or-earlier tarball, then optionally run `bosh delete-release bosh-pve-cpi` once nothing references the old name. The job name `pve_cpi`, every `pve.*` property, the `PVE_CPI_RELEASE_PATH`/`PVE_CPI_CONFIG` environment variables, cpi_ids, and all CIDs are unchanged. Release assets for v0.4.0 and earlier keep their `bosh-pve-cpi-<version>.tgz` filenames, and `scripts/certify` and the acceptance workflow accept both names when fetching old versions.

- New var `pve_cpi_release_name`, consumed by `manifests/bosh/cpi.yml` to set the release name in the create-env/delete-env manifest instead of a hardcoded `bosh-proxmox-cpi`. `manifests/bosh/vars.yml.example` documents it and defaults it to `bosh-proxmox-cpi`; a raw `bosh create-env`/`delete-env` invocation that loads that vars file picks up the default, and only needs to override it to `bosh-pve-cpi` when deploying a published tarball through v0.4.0. `scripts/bosh create-env`/`teardown` bypass the vars-file default and pass the name read from the tarball directly via `-v`, which wins over a `-l` vars-file value.

- Third-party dependencies are refreshed to their latest patch releases, including the AWS SDK for Go v2 modules behind the S3 stemcell fetcher.

- `pve.api_idle_conn_timeout_sec` now defaults to 15 seconds when unset, instead of inheriting the SDK's 90-second idle window, which outlives pveproxy's server-side keep-alive and sets up a reused-dead-connection race; explicit values pass through, and `90` restores the previous behavior.

- The `create_vm` rollback cleanup budget grows from two minutes to ten. Everything the rollback does draws on one bounded context (the stop and destroy task awaits, foreign-disk protection with per-disk detaches, the bounded config-lock-clear wait, and the destroy retry budgets), and the old bound could expire mid-cleanup on a loaded node, orphaning the VM it existed to reclaim. Exhausting the bound still fails closed: the purge is refused and the VM is preserved and tagged.

- The packaged Go toolchain moves from 1.26.6 to 1.27.0: the `golang-1.26` BOSH package is now `golang-1.27` with the `go1.27.0.linux-amd64.tar.gz` blob, `src/pve_cpi/go.mod` requires `go 1.27.0`, and CI builds in the digest-pinned `golang:1.27` image.

## [0.3.0] - 2026-08-21

### Added

- Stable disk identity. `create_disk` mints a `bpd-` plus 16-hex identity token that rides the drive's `serial=` attribute for the life of the disk, and attach resolves a disk by serial scan first, provenance sentinel second, and birth volid last, so a disk keeps its CID across the volume renames that parking and reassignment cause. Ownership moves by `move_disk` reassignment between the holder and the parker slot rather than by config-line surgery. CIDs minted before this release carry no token and resolve by volid forever. See [Stable disk identity and ownership transfer](docs/persistent-disk-strategy.md#stable-disk-identity-and-ownership-transfer).

- `create_disk` parks fresh disks under the parked strategy, fail-closed: a disk that cannot be parked at creation is not left floating.

- The disk CID records its create-time format, and block-native storage records `raw`, so later attaches rebuild the drive string from what was actually created rather than from current config.

- Operations on a parked disk whose parker anchor has vanished are refused with the repair path named, instead of proceeding against storage the parker no longer references.

- IPv6 dual-stack networks. Networks that share a `nic_group` plan onto one NIC with both `ip=` and `ip6=` addresses, and the BATS runner grows an opt-in dual-stack pass (`--only ipv6`).

- Offline wire-protocol conformance suite. `make test` now drives the compiled CPI binary against a refused endpoint and asserts exactly one well-formed response envelope per request, exit 0, retriable error typing with `ok_to_retry`, an `api_version` handshake matrix pinned to 2, and a stdout that carries nothing but envelopes, with no lab required.

- Consolidated [Known Limitations](docs/limitations.md) page stating every scope limit in one place.

- `update_disk` option updates are now durable. Every option change is recorded as a per-disk override map, and each attach builds the drive string by merging global `disk_performance` config, then the options recorded in the disk CID at `create_disk` time, then the recorded overrides — rightmost wins, and an empty-string value deletes the key. Previously a detach/attach cycle rebuilt the drive string from config and CID options alone, silently reverting every operator update. The record lives on the holder VM's description (`bosh_disk_opt_overlays` sentinel key) while attached and rides the parker's `bosh_parked_disks` provenance entry (new optional `opts` field) while parked; `update_disk` writes it fail-closed before touching the drive, and the invariant guard (`pve.disk_perf_invariant_mode`) treats recorded updates as part of the expected baseline rather than as divergence. A parked disk can now be updated too: the change is recorded (and `size` applied to the volume directly) and takes effect at the next attach, where the old behavior wrote options onto the parker's drive string and lost them at unpark. Two paths still drop the record, with a logged warning: a detach under `detached_disk_strategy: free` (no carrier exists for it), and `delete_vm`'s plain detach of a still-attached legacy foreign disk. See [Durable disk option updates](docs/persistent-disk-strategy.md#durable-disk-option-updates).

### Changed

- The gzip-compressed `pvz-` disk CID fallback now engages automatically whenever the plain `pvd-` envelope would exceed the 255-character bound of MySQL-backed Directors, instead of failing `create_disk` unless `pve.disk_cid_compression` was set. The stable-identity field made richly-annotated envelopes overflow in ordinary configurations, so the opt-in became a trap: a default-config `create_disk` under the parked strategy could fail outright. CIDs that fit stay `pvd-` and byte-identical, decode has always accepted both forms, and `pve.disk_cid_compression` is retained as an accepted no-op.

- `pve.vm_pool_template` now defaults to `bosh-{director}-{deployment}`, so every deployment gets its own auto-created resource pool (`bosh-<director>-<deployment>`; `bosh-create-env` for `bosh create-env` environments) instead of everything landing in the single static `bosh` pool. Each VM records how its pool was resolved in a `bosh_pool` sentinel on its PVE description, and `set_vm_metadata` re-renders the template from that record on every deploy, moving a template-placed VM whose pool has drifted; VMs placed by `cloud_properties.pool`, a `vm_type` profile, or the static `pve.vm_pool` are never moved. Existing VMs sitting in the static `bosh` pool are adopted into their deployment's pool on the next deploy. Upgrade notes: the CPI token needs `Pool.Allocate` and `Pool.Audit` at the `/pool` parent (per-deployment names are dynamic, so a per-poolid grant cannot cover them); reduced-ACL clusters whose token cannot create pools should set `pve.vm_pool_template: ""` to keep the single-pool model, and `create_vm` names that exact fix when pool creation is denied. A resolved pool name equal to `pve.stemcell_template_pool` is now rejected at `create_vm` time.

- `pve.pool_reap_empty` now defaults to `true`: a per-deployment pool is deleted when the synchronous `delete_vm` path destroys its last VM. Only pools carrying the CPI's `managed by bosh-pve-cpi` provenance comment are ever reaped, the static `pve.vm_pool` and `pve.stemcell_template_pool` are refused by name, and the fast-path delete still skips the reaper. Set the property to `false` explicitly to keep empty pools; the key is now always rendered into the CPI config, so an explicit `false` takes effect (previously the template could not express it).

- The parker VMID band now resolves under every `detached_disk_strategy`, at the job level and in every cpi-config entry alike: unset bounds fill with the built-in `90000`–`90999` whether the strategy is `parked`, `free`, or stood down by a band collision. Under `free` the band is read-only: nothing allocates a parker VMID in it, a band overlap is accepted rather than rejected at load, and disks parked while `parked` was in effect are recognized and unparked on their next `attach_disk` or `delete_disk` instead of being refused until an operator restores the band by hand. Switching to `free` no longer needs the band carried forward, and the load-time warning for `free` without a band is gone with the state it warned about. The stranded-parker refusal remains for a band moved away from VMIDs where parker VMs still live.

### Added

- BOSH Director Upgrade Test runner: `./scripts/certify`, which stands a Director up on the previous CPI release, deploys the upstream [certification release](https://github.com/cloudfoundry/bosh-cpi-certification) under it, upgrades the Director onto the latest release over the same state, and recreates the deployment, asserting that disk CIDs and the disk attachment survive the version change. Ships with the [BOSH Director Upgrade Test](docs/certification/upgrade.md) guide and a committed [run record](docs/certification/upgrade/README.md).

### Changed

- `pve.detached_disk_strategy` now defaults to `parked`: a detached persistent disk is held on a protected parker VM instead of floating as an unattached storage volume, so PVE shows who owns it and `protection=1` blocks an accidental delete. The previous free-floating behavior is still available by setting the property to `free`. Three consequences for existing deployments that never set the property: detach and attach each spend more PVE API calls, and `attach_disk` and `delete_disk` now resolve the volume's holder on every call, which costs one cluster listing plus a config read per VM in the cluster; each PVE node accrues one protected `bosh-parker-<n>` VM once a disk is parked there, which no CPI call ever deletes (`scripts/disk-audit` reports empty parkers along with the two commands that remove one); and the parker VMID band (`90000`–`90999` by default) must not overlap the VM, persistent-disk, or stemcell-template bands. A config that sets neither the strategy nor a parker band and whose other bands already reach into that window keeps the previous free-floating behavior for that load and says so in a warning, rather than failing to load, so the upgrade cannot take a running deployment down. Disks already detached stay free-floating and are picked up normally by the next `attach_disk` or `delete_disk`; `manifests/cpi-config.yml` shows the per-entry parker bands a shared-storage multi-cluster layout needs.

- **Before rolling back to a release older than this one, drain the parkers.** A release without the parked strategy has no unpark step, so it would attach a volume the parker still references and leave two VM configs pointing at one volume. Set `pve.detached_disk_strategy: free`; on 0.2.0 itself also set `pve.parked_disk_vmid_range_start: 90000` / `_end: 90999` explicitly so the unpark probes keep running (releases after 0.2.0 resolve an unset band on their own). Nothing drains a parker on its own: each disk comes off when the Director next attaches or deletes it, so redeploy the instance groups that own them and `bosh delete-disk` any orphans. Run `scripts/disk-audit` until it reports no parked disks, and roll back after that.

- `delete_disk` now refuses to free a volume still held by a parker VM the configuration can no longer recognize, naming the property to set. Freeing it would leave the parker's slot referencing storage that no longer exists.

- `attach_disk` now refuses a volume that is already attached to a VM other than the target, naming the holder. PVE permits two VM configs referencing one volume and nothing downstream detects it, until whichever holder is destroyed takes the volume with it. When the holder turns out to be a parker VM outside the configured band, the message says which property to set to make the disk reachable again.

- `pve.detached_disk_strategy` is overridable per cpi-config entry as `pve_detached_disk_strategy`, so one cluster whose VMID topology has no room for a parker band can opt out while the rest of the deployment keeps the default.

- Parker VMs are adopted only by the director that created them. Each carries a `director--<uuid>` tag, and a park now skips parkers attributed to another director rather than filling them, which keeps two directors sharing one PVE cluster from entangling their volumes. Parkers with no attribution tag stay adoptable by anyone.

- Unparking a disk now clears the parker VM's `protection` flag for the length of the detach and restores it immediately after. PVE treats detaching a disk as a "remove disk" operation, which that flag blocks, so `attach_disk` and `delete_disk` could not retrieve a parked disk while it was set. The flag is restored even when the detach fails, and a failed restore is logged with the command that repairs it.

- Parking a disk resolves its current holder with a single cluster scan instead of two. The scan reads every VM config in the cluster, so this halves the dominant cost of `detach_disk` under the parked strategy.

- `snapshot_disk` and `delete_vm` recognize a parker VM by its `bosh-parker` tag rather than by the configured VMID band (`delete_vm` reads the tag from the cluster-resources row, falling back to the VM config when that row carries no tags at all). An operator who turns parking off without carrying the band forward would otherwise disarm both guards over exactly the parkers that change stranded: a PVE snapshot takes the whole VM, entangling every deployment's disks held on that parker, and the fast delete path issues a purge that bypasses `protection=1`. Neither guard costs an extra API call.

- Each cpi-config entry decides the parked default against its own VMID bands. An entry that widens `pve_vmid_range`, `pve_disk_vmid_range`, or `pve_stemcell_template_vmid_range` over the built-in parker band stands the default down for that entry with a warning, rather than failing every request routed to that cluster; an entry that narrows those bands back gets the default it would have had on its own. An entry that names `parked` itself, or that sets a parker bound of its own, is honored as written. The parker band ApplyDefaults fills in is no longer inherited as though the entry had typed it, so an entry that moves one bound gets the built-in fallback for the other instead of a value meant for a different cluster.

- The parker band's overlap check now applies only under the `parked` strategy. It exists to stop the CPI allocating a parker VMID another band will claim, and nothing allocates one under `free`, where the band is read-only and every parker classification also requires the `bosh-parker` tag. A deployment that opts out precisely because its VMID layout has no room for a parker band is no longer rejected for the overlap.

- Unparking a disk re-resolves its slot inside the protection window. `DetachDisk` names a slot, not a volume, so a slot looked up before the lock was a blind write by the time the detach ran: two overlapping unparks of one disk could detach a volume a concurrent park had just placed in the freed slot, silently un-parking a disk whose own `detach_disk` had already reported success. A volume found off the active bus but still named by an `unusedN` key is swept instead, and one already gone is an idempotent no-op.

- Parking and unparking one parker VM are serialized against each other by a per-VMID lock. Both write its `protection` flag, and PVE clears a detached disk in two requests: a park restoring `protection=1` between an unpark's two halves made PVE refuse the second one, leaving the volume referenced by an `unusedN` key no probe matches on while the unpark reported a retriable failure. The same lock stops a park claiming a slot an unpark is about to detach by name. The lock is the same `bosh-lock-<name>` sentinel-pool mechanism the anti-affinity and VMID locks use, and it is taken on every park and unpark rather than behind an opt-in, so the CPI's PVE identity needs `Pool.Allocate` on `bosh-lock-*`. Without it the window runs unserialized, with a warning, rather than failing the call; see [PVE API permissions](docs/pve-api-permissions.md).

- An unpark that detaches the volume but cannot clear the `unusedN` key PVE demotes it to now fails permanently, naming the parker and carrying the `qm unlink` sequence that clears the reference. The detach has already succeeded at that point, so a retriable failure would send the Director's retry past the holder scan (which matches active-bus slots only) and on to attaching a volume the parker still references. Two paths that previously reported such a sweep as clean, a config read that failed mid-sweep and a parker band overlapping the disk band, now report it as the unswept reference it is.

- LXC containers no longer break parking, unparking, or the holder scan. The cluster listing both use covers containers as well as VMs, and every read behind it goes through the QEMU config endpoint, which answers for a container with a pmxcfs "Configuration file ... does not exist" error rather than a 404. One container in the parker band used to fail every park and unpark on its node; one container anywhere in the cluster used to fail every `attach_disk`, `detach_disk`, and `delete_disk` of a persistent disk, retriably and forever, once parking became the default.

- A park that strands a reference now fails permanently on every exit, not just the one that ran out of slots. A slot lost to a concurrent park leaves the volume on an `unusedN` key; when the sweep that clears it fails, the park used to hand back a retriable error, or `ErrNoSlots`, either of which sends the volume to another parker or another attempt while the first parker still references it. Both references are invisible to the holder scan, and destroying either parker frees a live volume.

- A sweep that removes the `unusedN` key but cannot read the config back to confirm it now fails permanently and keeps the provenance entry. It used to report success on the grounds that a later read would catch a surviving reference; no later read happens, since an unpark of a volume already off the bus returns early and a park only sweeps a slot it lost in that same call.

- A full parker that still references the volume on an `unusedN` key is swept rather than skipped. Walking past it to the next parker is what puts one volume in two parkers' configs.

- Failures on the parker paths are classified rather than reported retriable by default. A missing `VM.Config.Disk` or `VM.Audit` grant never comes right on its own, and the Director was driving the park against it forever instead of surfacing the permission to grant. Config reads and mutating calls are classified separately: a read defaults to permanent, since its failure shapes are enumerable, while a mutating call defaults to retriable, since PVE reports plenty of transient conditions as prose no classifier recognizes and a park that failed permanently on one of those would leave the disk free-floating. `detach_disk` no longer flattens the result: a denied grant or an exhausted VMID band reaches the Director as the permanent condition it is, naming what to fix.

- Work inside a parker's protection window runs under a deadline derived from the window lock's own TTL, and every retry loop inside it is bounded. Bounding the loops alone was not enough, because their worst cases compose: the storage-lock curve alone would have slept past two minutes, and a protection write under PVE pushback past four, long enough for another park or unpark to steal the lock and enter the window while the first caller was still inside it. Releasing a lock whose claim has already lapsed no longer deletes the sentinel, which used to remove a stealer's claim and let a third caller in while they were mid-window.

- `set_disk_metadata` falls back to the VM config when a cluster-resources row carries no tags at all, as `delete_vm` already did. An empty tags field cannot tell an untagged VM from a PVE that does not populate the field, and treating a parker as an ordinary holder writes deployment metadata into the description carrying its provenance sentinel.

- The `detach_disk` retry path resolves the disk's holder once instead of twice. It asked the same cluster-wide sweep two questions, "is it parked?" and "does a real VM hold it?", that are two readings of one answer.

- `attach_disk` and `delete_disk` now resolve the volume's holder on every call, whatever the strategy says, and refuse when that holder is a parker the configuration can no longer recognize. The refusal reads the tags the holder scan already returned, so it costs no extra API call and has no failure mode of its own: an earlier shape read the holder's config a second time and treated an unreadable config as "not a parker", which sent `delete_disk` on to destroy a volume a parker's slot still referenced. One consequence to plan for: because the scan reads every VM's config, a node that is down fails both calls retriably cluster-wide until it returns. A cluster-endpoint fault that outlives the retry budget is now reported retriably too, so the Director re-drives instead of giving up on a corosync blip or a quorum loss.

- Parker tags are recognized whatever separator PVE stored them with (`;`, `,`, or a space, the three its tag format accepts). A tag string the CPI failed to tokenize was a guard that silently did not fire, which for `delete_vm` meant a `skiplock` purge over a VM holding up to 31 other deployments' disks.

- `scripts/disk-audit` counts `unusedN` references when deciding whether a parker is empty, and never calls a parker empty when its config could not be read. A parker whose only remaining reference was an unswept `unusedN` key was reported as empty and offered as a teardown candidate with `qm destroy --purge`, which frees exactly that volume. A stranded reference now draws its own warning naming the `qm unlink` sequence that clears it.

- Consolidated the certification documentation under `docs/certification/`: the certification overview, the BATS guide, and the BATS run record moved there, joined by the Director upgrade guide and its run record.

- The create-env harness and example manifests now pin work to the configured node, which multi-node clusters with node-local storage require. The light stemcell manifests the harness generates carry `cloud_properties.node` (the light preuploaded validation demands one on a multi-node cluster), and `manifests/bosh/cloud-config.yml` and `manifests/bosh/cpi.yml` pin the AZ and the Director's resource pool to `((pve_node))` — without the pin, placement can pick a node that holds neither the stemcell cache template nor the VM's persistent disk, and an operator-owned preuploaded qcow2 is nothing the CPI can replicate across nodes. Single-node clusters and shared-storage layouts are unaffected; shared-storage clusters may drop the pins.

## [0.1.1] - 2026-08-18 [YANKED]

while `go.mod` required 1.26.6, and the packaging script pins `GOTOOLCHAIN=local`, so

it pointed at (`b7ead4a`) stays reachable on `main`. Upgrade straight from 0.1.0 to
0.1.2, which packages a matching toolchain. The blob drift gate that now fails the build
on this mismatch landed after the tag was cut.

## [0.1.0] - 2026-08-04

First feature-complete release: full BOSH CPI v2 coverage against PVE 9.x, validated end
to end against a live cluster.

### Added

- Complete BOSH CPI v2 method set (`api_version: 2`) over the JSON-RPC stdin/stdout envelope, shipped as a single static Go binary in a BOSH release.

- Stemcells: template cloning instead of per-VM import, digest verification, cross-node replication, provenance metadata with orphaned-template collection, deduplication, and DNS-safe template names.

- Light stemcells in both pre-uploaded and CPI-fetch modes, with node pinning and storage requirements documented.

- Placement: availability-aware node scoring on reserved memory, same-instance-group anti-affinity spreading, disk fault-domain co-location, storage-pool selection, resource-pool assignment with create-if-missing and an opt-in reaper, and opt-in PVE 9.2 Dynamic Load Balancer awareness.

- Networking: `create_network` and `delete_network` via PVE SDN with Linux bridge fallback, layered `cloud_properties`, per-NIC overrides, per-VM firewall and security-group attachment, allowed-address-pairs VIP ipfilter, pre-create IP-conflict detection, and opt-in SDN eventual-consistency gates.

- Persistent disks: the `pvd-` CID envelope with legacy decode, per-disk performance options, creation-time performance invariants enforced on re-attach, an opt-in parked-disk detachment strategy with provenance sentinels, `get_disks` backed by attach-time recording, and the `scripts/disk-audit` tool.

- Agent bootstrap by ConfigDrive ISO with no external registry, agent-mode auto-selection, stemcell-driven disk sizing, and a boot-path agent integrity checksum assertion.

- Resilience: opt-in progress-aware adaptive task polling, per-method timeout envelopes with configurable retry and poll cadence, transport tuning for parallel deploys, opt-in fast-path delete with a self-healing straggler sweep, alternate-node retry on transient `create_vm` failures, and PVE pushback handling.

- Safety: `delete_vm` guarded against destroying attached persistent disks, `delete_disk` guarded against in-flight VMs, cross-process VMID and anti-affinity race tolerance, dispatch hooks with a rollback contract, and a keep-failed-VMs debug mode.

- Security: minimum-privilege `bosh@pve` role documentation and API-token support (preferred over password when both are set), SSRF and allow-list closure on stemcell fetch, log scrubbing of credentials and presigned signatures, strict config validation, and a frozen exec allow-list.

- Observability: opt-in `pve.otel.*` tracing, logs, and metrics with OTLP HTTP and gRPC exporters, per-request correlated logging, an opt-in redacted request/response trace at the dispatcher boundary, and duration metrics with outcome classification.

- Operations: soft and hard `reboot_vm` with graceful fallback, an `unstick-agent` subcommand, HA node-affinity pinning, multi-cluster (multi-CPI) support with disjoint VMID banding, and configurable VMID bands.

- Test and CI infrastructure: a tiered live-PVE integration harness, an end-to-end runner with per-phase timings, a JSON-RPC fuzz target, GitHub Actions check and security gates, and an 80% coverage gate.

- The documentation set: architecture, CPI methods, configuration, networks, persistent disks, permissions, best practices, troubleshooting, and the operations runbook.

### Changed

- VMs are named `{prefix}-{deployment}-{job}-{index}`.

- `create_vm` accepts `ram` as an alias for `memory` and `env.bosh.mbus` as a flat string.

- Task status polls target the node embedded in the UPID, and attach and detach target the VM's current node.

### Removed

- BOSH registry agent mode. Supported modes are `cloudinit`, `noagent`, and `auto`; `registry_*` properties now fail fast.
